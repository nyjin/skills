# harness-loop retro 재설계: 결정 대상만 보고

- 작성일: 2026-11-06 (범위 조정 2026-11-13)
- 상태: 사용자 검토 대기
- 대체 범위: `2026-10-16-harness-loop-design.md` 의 4장(흐름) 중 판정·보고, 5장(감지 조건), 6장(채점), 7장(action item 형식). 저장 위치 원칙(3장)·반영 대상 판정(7장 표)·실측 결과(8장)는 그대로 쓴다.
- 근거 자료: 2026-10-19 명시 회고 분석(13세션 23항목), 레퍼런스 조사(claude-reflect, hansvangent reflect-skill, Claudeception, Anthropic claude-md-management·hookify, claude-mem, ACE, Reflexion), Claude Code hooks 문서(2026-11-06 확인)

## 1. 의도

지금 retro 는 C1~C11 증상 신호를 넓게 모아 점수를 매기므로, 바꿀 파일이 없거나 비용이 없는 항목(메모리를 전역으로 옮기기, 응답 품질 지적, 환경 함정 메모)이 많이 올라온다. 재설계의 목표는 사용자가 **결정해야 하는 것만** 보고하는 것이다.

retro 의 범위는 문제를 발견하고 수정안을 안내하는 데까지다(사용자 결정). 수정은 사용자가 하고, retro 는 수정안을 받아들였는지를 기록한다. 이 기록이 제안이 유효했다는 증거이고, 다음 판정을 다듬는 라벨이다.

원칙:

1. 보고는 사용자의 결정 대상만 한다. 단순 보고용 항목은 없다.
2. 결정 대상마다 정해진 조치가 있다(스크립트화, 스킬 보완, 지침 보완, 지침·스크립트 수정).
3. 조치는 실측 뒤에만 낸다. retro 가 실제 스킬 파일·스크립트를 읽어 확인하고, 근거는 경로와 원문으로 전달한다.
4. 결정적 처리는 꼭 필요한 곳에만 쓴다. 훅은 어떤 이벤트를 받을지, 무엇을 기록할지만 정하고 문구 해석은 하지 않는다. 해석은 retro 때 AI 가 한다. 판정 품질은 비용보다 F1 로 본다.
5. 전체 transcript 를 읽지 않는다. retro 는 훅이 남긴 근거 기록과, 그 기록이 가리키는 위치의 앞뒤 발췌만 읽는다.

## 2. 목표, 비목표, 실패로 보는 것

목표:

- 다섯 가지 관찰을 훅 근거로 기록하고, retro 때 판정·묶기·파일 검증을 거쳐 네 가지 결정 대상으로 보고한다.
- 보고마다 수정안(diff)을 안내하고, 사용자의 수락·거절(사유 라벨)을 기록한다.
- 수락·거절 기록으로 제안의 유효성(수락률)을 보이고, rubric·replay 로 판정 기준을 계속 다듬는다.

비목표:

- 수정 반영과 티켓 생성. 수정안을 받은 사용자가 직접 한다.
- 스킬·지침 수정 전후 평가(버전 추적, 수정 뒤 재발 판정). 평가 기준이 따로 필요해 회고 범위를 벗어난다(사용자 결정).
- 권한 프롬프트 줄이기(`fewer-permission-prompts` 담당), 대화 기억·검색.

실패로 보는 것(기술적으로 동작해도):

- 바꿀 파일이 없는 항목, 일반론("테스트를 꼼꼼히") 수정안이 결정 대상으로 올라옴.
- 되돌리기 어렵거나 외부로 나가는 동작 앞의 확인을 "승인용 질문"이나 "결정 패턴"으로 올림.
- 상황마다 다르게 고른 결정을 기본값으로 굳히자고 올림.
- 훅이 세션을 눈에 띄게 느리게 함.

## 3. 흐름

```
[세션 중]  훅 → 근거 기록 (해석 없음)
[/harness-loop:retro]
   1. 근거 읽기: 지난 retro 이후 근거 + 관문을 못 넘어 남아 있는 관찰
   2. 관찰 판정 (AI): 근거마다 해당/아님 + 이유 한 줄. 필요하면 transcript 앞뒤 발췌를 스크립트로 가져옴
   3. 묶기 (AI): 같은 대상 파일·같은 문제끼리. 이미 결정된 묶음과 대조
   4. 파일 검증 (AI): 현재 스킬 파일·지침·스크립트를 읽고 결정 대상을 정함
   5. 관문 (결정적): 횟수·검증 여부로 결정 대상 여부를 정함
   6. 보고: 결정 항목과 수정안
   7. 결정: 수락 / 거절 기록
```

- 백그라운드 판정은 없다. 판정은 retro 실행 때만 한다.
- 범위(내 판단): `/harness-loop:retro` 한 번은 모든 세션의 아직 판정하지 않은 근거를 다룬다(현재 세션 포함). 반복은 세션을 넘어 세야 하므로 세션 단위로 나누지 않는다. 세션마다 `harness/evidence.cursor` 에 판정한 줄 번호를 둔다. 모드는 기본, `backfill`(훅 설치 전 기록을 근거화), 결정, rubric 갱신이다.
- 판정한 관찰은 결과(해당/아님, 이유)를 저장하고 다시 판정하지 않는다. 다음 retro 는 새 근거만 판정하고, 묶기와 관문은 저장된 관찰 전체로 다시 계산한다.
- 관찰의 유효 기간(내 판단): 관문 횟수는 `window_days`(기본 30일, `cleanupPeriodDays` 와 같음) 안의 관찰로 센다.
- 2~4단계는 retro 가 모델을 Opus 로 지정한 서브에이전트에게 근거 묶음만 넘겨 실행한다(내 판단: retro 세션 맥락을 깨끗하게 두고 판정 모델을 고정하기 위해).
- SessionStart 는 LLM 없이, 아직 판정하지 않은 근거가 있으면 건수를 하루 한 번 한 줄로 알린다(내 판단).

## 4. 관찰(중간 분류)

관찰은 사실만 적고 처방은 적지 않는다. 관찰 유형은 근거 종류로 정해지고(결정 패턴만 예외, 아래), AI 는 해당 여부를 판정한다.

| 관찰 | 받는 훅 | 판정 원칙 (retro 때 AI) | 의도 |
|---|---|---|---|
| 교정 | `UserPromptSubmit` | 사용자가 AI 가 이미 내린 판단이나 동작을 뒤집거나 바로잡았는가. 새 요청·추가 지시는 아님. 스킬 실행 중과 일반 작업 모두 본다(사용자 결정) | 스킬이나 지침 파일이 사용자 판단 기준을 담지 못한 지점 |
| 반복 실행 | `PreToolUse`(Bash) | 같은 목적의 명령·inline 스크립트를 다시 작성했는가 | 스크립트로 굳힐 반복 노동 |
| 실패·이탈 | `PostToolUseFailure`, 스킬 실행 구간의 근거 | 스킬 실행 중 도구가 실패했거나, AI 가 스킬이 정한 절차와 다르게 움직였는가 | 스킬·스크립트 자체의 결함 |
| 승인용 질문 | `PostToolUse`(AskUserQuestion), `UserPromptSubmit`(글로 물은 질문의 답) | AI 가 이미 결정해 놓고 승인만 남긴 질문인가: 대안 없는 "이대로 진행할까요?", 선택지가 진행·취소뿐이고 취소하면 다음 경로가 없음, 계획을 다 정한 뒤 "괜찮을까요?" | 결과를 바꾸지 않는 마찰 |
| 결정 패턴 | `PostToolUse`(AskUserQuestion), `UserPromptSubmit`(글로 물은 질문의 답) | AI 가 실제로 다른 결과를 낳는 선택지를 주었고 사용자가 그중 하나를 골랐는가(직접 입력한 답 포함). 해당이면 "<상황>이면 <선택>" 형식의 규칙 문장 하나로 정리한다 | 사용자 결정 방식을 기본값으로 적어 질문을 줄일 지점 (사용자 제안) |

- 관찰 판정은 해당/아님 두 값과 이유 한 줄이다. 중간 등급은 두지 않는다.
- 질문에 대한 답(`ask` 근거, 질문의 답인 `prompt` 근거)은 질문의 성격으로 둘을 가른다: 선택지가 사실상 하나면 승인용 질문, 실제로 여럿이면 결정 패턴. 한 근거는 둘 중 하나로만 판정한다.
- 결정 패턴의 규칙 문장은 반복 실행의 목적 문구처럼, 같은 규칙이면 같은 문구를 쓴다(최근 문구 목록을 판정 입력에 넣는다). 관문은 이 문구로 횟수를 센다.
- 승인용 질문은 질문 원문의 형태로 판정한다. 사용자가 긍정으로 답했다는 사실은 보조 근거다.
- 승인용 질문과 결정 패턴에서 제외: 되돌리기 어렵거나 외부로 나가는 동작 앞의 확인(push, 삭제, 메시지 전송, 티켓 생성, 배포 등). 사용자 결정.
- 모든 관찰에서 제외: 환경 원인(인증, 네트워크, 권한 프롬프트), 바꿀 파일이 없는 것(말투, 응답 품질), 정리 제안(메모리를 전역으로 등).

## 5. 훅이 남기는 근거

### 받는 이벤트

| 이벤트 | 기록 |
|---|---|
| `UserPromptSubmit` | 프롬프트 원문, 직전 AI 메시지 위치(transcript 바이트 위치), 현재 스킬, 직전 도구 호출이 거절됐는지(아래 참고) |
| `UserPromptExpansion` | 슬래시 명령으로 실행된 스킬. `/skillname` 직접 입력은 `PreToolUse` 를 거치지 않는다(문서) |
| `PreToolUse`(Skill) | 스킬 이름. 현재 스킬 상태를 바꾼다 |
| `PreToolUse`(Bash) | 명령 원문. inline 스크립트(heredoc, `python -c`, `node -e` 등)는 본문을 파일로 저장하고 경로를 남긴다. 명령이 스킬 디렉터리 안 스크립트를 부르면 그 경로 |
| `PostToolUseFailure` | 도구 이름, 입력 요약, `error` 첫 몇 줄. 문서상 `error` 형식은 안정적이지 않으므로 해석하지 않고 원문만 둔다 |
| `PostToolUse`(AskUserQuestion) | 질문, 선택지, 고른 답 |

- 서브에이전트(`agent_id` 있음), 워커 세션, `HARNESS_RETRO=1`, 스킬 eval 세션(`eval_markers`) 처리는 기존 규칙을 따른다.
- 도구 거절: 훅으로 사용자의 도구 거절을 받는 이벤트는 문서에 없다(`PermissionDenied` 는 auto mode 분류기 거절만). transcript 에는 `tool_result` 가 `is_error: true` 이고 내용이 `The user doesn't want to proceed with this tool use` 로 시작하며 `toolUseResult` 가 `"User rejected tool use"` 로 남는다(실측). `UserPromptSubmit` 훅이 transcript 꼬리를 읽어 직전 도구 결과가 이 형태면 `after_rejection: true` 를 붙인다. 교정 관찰의 강한 보조 근거다.
- 현재 스킬: 스킬 종료 이벤트는 없다. 세션별 상태 파일에 마지막으로 실행된 스킬과 그 뒤 사람 프롬프트 수를 둔다. 근거에는 스킬 이름과 "실행 후 N번째 프롬프트"를 남기고, 어느 스킬에 속하는지는 retro 때 AI 가 발췌를 보고 정한다.
- 스킬 경로: 훅 입력에 스킬 파일 경로는 없다(문서). 스킬 로드 때 transcript 에 남는 `Base directory for this skill: <경로>` 줄에서 결정적으로 얻는다. 없으면 스킬 디렉터리 탐색으로 푼다.
- 지침 파일: `prompt` 근거에 그 cwd 에 적용되는 지침 파일 경로 목록(`meta.guidelines`)과 프로젝트 루트(`meta.project_root`, 같은 저장소의 하위 디렉터리·worktree 는 한 프로젝트)를 남긴다. 지침 보완의 대상과 범위를 정하는 데 쓴다.
- `PostToolUse`(AskUserQuestion) 의 `tool_response` 형태는 문서에 없다. 답이 없으면 transcript 의 해당 `tool_result` 에서 읽는다.

### 근거 기록 형식

세션 디렉터리 `harness/evidence.jsonl` 에 한 줄씩 덧붙인다.

| 필드 | 뜻 |
|---|---|
| `id` | 근거 ID |
| `kind` | `prompt` · `bash` · `failure` · `ask` · `skill_start` |
| `at` | 시각 |
| `session`, `transcript`, `pos` | 세션 ID, 기록 경로, 위치 |
| `skill` | `{name, path, prompts_since}` 또는 없음 |
| `text` | 원문(프롬프트, 명령, 오류, 질문·선택지·답) |
| `file` | 저장한 inline 스크립트 경로 |
| `flags` | `after_rejection` 등 결정적으로 정한 표시 |
| `meta` | `guidelines`, `project_root`, `scripts`, `tool_use_id` 등 |

### 성능·저장

- 훅은 파일에 한 줄 덧붙이는 것만 한다. LLM·네트워크 호출 없음. 실패해도 항상 `exit 0`, 오류는 `hook-errors.log`.
- 훅과 스크립트는 `uv run --script` 로 실행한다(사용자 결정). 설정은 `${CLAUDE_PLUGIN_DATA}/config.yaml` 이다.
- 근거·inline 스크립트 사본은 세션 디렉터리(`harness/`)에 두어 기록과 같이 `cleanupPeriodDays` 로 지워진다. 판정된 관찰·묶음·결정·replay 보관본은 `${CLAUDE_PLUGIN_DATA}` 에 둔다. 둘 다 push 되는 저장소에는 넣지 않는다.

## 6. 결정 대상

| 결정 대상 | 원칙 | 사용자가 결정할 것 | 근거 형식 |
|---|---|---|---|
| 스크립트화 | 같은 목적의 명령·inline 스크립트를 매번 새로 작성하고, 담을 스킬·스크립트가 없음 | 스크립트로 만들지, 어느 스킬에 넣을지 | 반복된 스크립트 파일 경로들, 횟수, 세션 |
| 스킬 보완 | 스킬은 지시대로 했으나 지시에 없는 판단에서 문제가 남, 또는 스킬 안에서 같은 결정을 반복해서 물음 | 판단 기준·기본값·단계를 스킬에 더할지 | 스킬 이름·위치, 근거 위치들, 더할 범위와 의견, diff |
| 지침 보완 | 스킬 밖 일반 작업에서 같은 교정이나 같은 결정이 반복되고 지침 파일에 규칙이 없음 | 규칙을 어느 지침 파일에 더할지 | 대상 파일 경로, 근거 위치들(프로젝트별), 더할 문구, diff |
| 지침·스크립트 수정 | 스킬·지침에 적힌 지시·스크립트가 틀렸거나 AI 를 다르게 움직이게 만듦 | 그 줄·파일을 고칠지 | 스킬 이름·위치, 문제 줄·파일, 수정 범위와 의견, diff |

### 관찰 → 결정 대상

| 관찰 | 파일 검증 결과 | 결정 대상 |
|---|---|---|
| 교정(스킬 실행 중) | 지시가 없음 | 스킬 보완 |
| 교정(스킬 실행 중) | 지시가 틀렸거나 AI 가 지시를 무시함 | 지침·스크립트 수정 |
| 교정(일반 작업) | 적용되는 지침 파일 어디에도 규칙이 없음, 또는 메모리에만 있는데 재발함 | 지침 보완 |
| 교정(일반 작업) | 지침 파일에 규칙이 있는데 틀렸거나 AI 가 무시함 | 지침·스크립트 수정(대상이 지침 파일) |
| 반복 실행 | 담을 스크립트가 없음 | 스크립트화 |
| 반복 실행 | 스킬에 이미 스크립트가 있는데 쓰지 않음 | 지침·스크립트 수정 |
| 실패·이탈 | 원인이 지시·스크립트에 있음 | 지침·스크립트 수정 |
| 어떤 관찰이든 | 원인이 환경에 있음 | 버림 |
| 승인용 질문 | 묻게 만든 지시 줄이 있음 | 지침·스크립트 수정 |
| 승인용 질문 | 지시 없이 AI 가 스스로 물음 | 스킬 보완("이 단계는 묻지 않는다") |
| 결정 패턴(스킬 실행 중) | 스킬에 그 결정의 기준·기본값이 없음 | 스킬 보완("<상황>이면 <선택>으로 한다") |
| 결정 패턴(스킬 실행 중) | 스킬이 그 결정을 사용자에게 묻도록 지시함 | 지침·스크립트 수정(그 지시 줄을 기본값으로 바꿈) |
| 결정 패턴(일반 작업) | 적용되는 지침 파일에 기준이 없음 | 지침 보완 |
| 결정 패턴(일반 작업) | 지침 파일의 기준이 사용자 선택과 반대임 | 지침·스크립트 수정(대상이 지침 파일) |

일반 작업 교정·결정 패턴의 대상(사용자 결정: 일반 작업도 포함, 세부는 내 판단):

- 대상 파일은 사용자가 소유한 지침 파일이다: 프로젝트 `CLAUDE.md`(cwd 에서 위로 올라가며 적용되는 것), 프로젝트 `.claude/rules/`, 전역 `~/.claude/CLAUDE.md`.
- 자동 메모리(`memory/`)는 검증 때 읽기만 하고 대상으로 삼지 않는다. 메모리에만 있는 규칙이 재발했다면 메모리로는 부족하다는 근거이므로 지침 파일에 넣는 "지침 보완"이 된다. 메모리 사이의 이동·정리는 결정 대상이 아니다(옛 C7 소음 방지).
- 범위는 관찰이 나온 프로젝트 수로 정한다: 한 프로젝트에서만 나오면 그 프로젝트 지침, 2개 이상 프로젝트에서 같은 교정·결정이면 전역 `~/.claude/CLAUDE.md`. 프로젝트 수는 근거의 `meta.project_root` 로 결정적으로 센다.
- 승인용 질문은 스킬 실행 중만 본다(내 판단: 일반 작업의 질문은 고칠 지시 지점이 없다). 결정 패턴은 지침에 기본값을 적을 수 있으므로 일반 작업도 본다.

승인용 질문의 수정안 선택지: 묻지 않고 진행 후 결과 알림 / 실제 대안을 담은 결정 질문으로 바꿈 / 흩어진 승인을 맨 앞 한 번으로 모음.

## 7. 관문(강도)

강도는 점수가 아니라 관문이다. 넘으면 결정 대상, 근거는 있지만 못 넘으면 쌓아 두고 보고하지 않는다, 파일로 검증이 안 되면 버린다. 가중합과 propose·watch 단계는 없다.

패턴 감지는 모두 같은 기준을 쓴다(사용자 결정): `pattern_min_count`(2)회 이상, `pattern_min_sessions`(2)개 이상 세션.

| 결정 대상 | 관문 |
|---|---|
| 스크립트화 | 같은 목적의 스크립트가 패턴 기준을 넘음 |
| 스킬 보완·지침 보완(교정) | 같은 스킬(또는 같은 지침 범위)·같은 종류의 교정이 패턴 기준을 넘음 + 대상 파일에 해당 규칙 없음 확인 |
| 스킬 보완·지침 보완·수정(결정 패턴) | 같은 규칙 문장의 결정이 패턴 기준을 넘음 + 같은 상황에서 다르게 고른 관찰이 `window_days` 안에 없음 + 대상 파일 확인 |
| 스킬 보완·지침 수정(승인용 질문) | 1회 + 질문을 만든 지점 특정 (사용자 결정: 횟수가 아니라 질문 형태. 패턴 감지가 아님) |
| 지침·스크립트 수정(실패·교정의 결함) | 1회 + 파일에서 결함 위치 특정 (결함 확인이지 패턴 감지가 아님) |

- 결정 패턴의 반대 선택(내 판단): 묶기 서브에이전트가 같은 상황에서 다른 선택을 한 관찰을 묶음의 `conflicts` 에 넣는다. 하나라도 있으면 그 묶음은 보고하지 않고 `dropped`(`conflicting_choice`)로 둔다. 상황마다 판단해야 하는 결정이라 계속 묻는 것이 맞다.

올리기 전 공통 확인(하나라도 아니면 올리지 않음, 내 판단):

- 구체성: 수정안에 이 스킬·프로젝트에만 있는 사실(경로, 명령, 이름, 순서)이 있다.
- 실패 근거: 이 규칙이 없어서(또는 틀려서) AI 가 실제로 다르게 움직인 장면(결정 패턴이면 사용자에게 다시 물은 장면)을 근거 위치로 가리킬 수 있다.

## 8. 보고와 결정

보고 항목 형식: `번호. [결정 대상] 스킬 이름(경로) — 문제 한 줄`, 이어서 근거(경로·발췌), 횟수, 검증 위치, 수정 범위와 의견, diff. 사용자는 항목마다 수락·거절을 답한다(`1 수락, 2 거절 사소함` 처럼 한 번에 답할 수 있다).

| 결정 | retro 가 하는 일 | 기록 |
|---|---|---|
| 수락 | 수정안이 유효하다고 기록한다. 고치지 않는다. 대상이 외부 플러그인 캐시면 원본 저장소에서 고쳐야 한다고 보고에 적는다 | 결정, 당시 rubric 버전 |
| 거절 | 사유 선택: 결함 아님 / 사소함 / 안 고침 | 결정, 사유 라벨, 이유 문장 |

- 결정이 난 묶음은 다시 보고하지 않는다. 그 묶음에 맞는 새 관찰은 같은 id 로 묶여 쌓이기만 한다. 수정했는지는 추적하지 않는다.
- 묶음 키(내 판단): 묶음은 `${CLAUDE_PLUGIN_DATA}/groups.json` 에 `id`(처음 만들 때 정하는 짧은 슬러그, 이후 고정), 결정 대상, 대상 경로, 문제 한 줄, 관찰 ID 목록을 둔다. 새 관찰은 AI 가 기존 묶음(결정된 묶음 포함)에 넣을지 새로 만들지 정한다. 라벨과 train/test 분할은 묶음 `id` 로 한다.
- 라벨: 수락은 양성, 결함 아님·사소함은 음성, 안 고침은 라벨에서 뺀다(제안은 맞았으나 사용자 사정으로 고치지 않음).
- 유효성: `metrics` 가 수락률 = 수락 ÷ (수락 + 결함 아님·사소함)을 전체, 결정 대상별, rubric 버전별로 보인다.
- 재구성(사용자 결정): 옛 파일·데이터·이력과의 호환을 두지 않는다. 옛 데이터(플러그인 데이터 디렉터리 전체, 세션 `harness/` 디렉터리)는 새 버전 적용 때 지우고 새로 시작한다. 라벨·수락률 기준선도 새로 쌓는다.

## 10. rubric 과 replay

rubric 은 `${CLAUDE_PLUGIN_DATA}/rubric.md` 에 둔다(처음 실행 때 `defaults/rubric.md` 를 복사). 첫 줄 `<!-- rubric-version: N -->`, 변경은 `rubric-changes.jsonl` 에 남긴다.

분류 기준과 rubric 은 연동한다(사용자 결정). 분류는 되는데 rubric 에 없는 기준은 거절로 고칠 수 없어, 개선할 의지가 없는 기준이 된다.

- rubric 이 판정 기준의 단일 원천이다. 4장(관찰)·6장(결정 대상, 대상 파일·범위)·7장(관문, 공통 확인)의 기준이 모두 rubric 에 있다. retro 스킬 문서의 서브에이전트 프롬프트는 "rubric 을 따른다"와 출력 형식만 둔다.
- 스크립트가 적용하는 기준(횟수, 기간, 범위, 반대 선택, 버림 이유)도 rubric 에 설정 이름·코드와 함께 적는다. 값은 `config.yaml` 이 정한다.
- 파일 검증 결과는 코드로 적는다: `missing`·`no_instruction`·`wrong`·`ignored`·`has_script`·`asks_here`·`asks_user`(스킬이 결정을 묻도록 지시)·`opposite`(지침 기준이 사용자 선택과 반대)·`environment`(원인이 환경, 버림). rubric 의 코드 → 결정 대상 표가 관문 스크립트의 허용 짝과 같아야 한다.
- 연동 테스트: 관찰 유형, 근거 종류, 결정 대상, 검증 결과 코드와 허용 짝, 버림 이유, 관문 설정 이름이 모두 `defaults/rubric.md` 에 있는지 확인한다. 기준을 더하고 rubric 을 고치지 않으면 테스트가 실패한다.

| 거절 사유 | 고칠 곳 |
|---|---|
| 결함 아님 | "관찰로 보지 않는 경우" 절에 규칙을 더함(해당 관찰의 판정 기준을 좁힘) |
| 사소함 | "결정 대상으로 올리지 않는 경우" 절에 규칙을 더함(관문·공통 확인을 좁힘) |
| 안 고침 | 반영 안 함 |

- 단기 반영: 최근 라벨 예시(train 분할)를 판정 서브에이전트 입력에 넣는다.
- rubric 수정안: 같은 패턴의 거절(train 분할)이 `rubric_min_evidence`(3) 건 이상이면 retro 보고 끝에 수정안을 올린다. 사용자가 승인하면 반영하고 버전을 올린다.
- 판정 입력 보관: 결정할 때 그 묶음의 판정 입력 전체(근거 줄, 발췌, 검증 때 읽은 대상 파일의 결정 시점 내용, 당시 rubric 버전)를 `${CLAUDE_PLUGIN_DATA}/replay/<묶음 id>/` 에 보관한다. 근거는 30일 뒤 지워지지만 replay 는 이 보관본으로 같은 입력을 다시 판정한다. 결정 정보는 입력에 넣지 않는다.
- 회귀 검사(항상): 후보 rubric 으로 지금까지의 양성(수락) 묶음을 모두 다시 판정해, 더 이상 결정 대상으로 올라오지 않는 묶음을 보인다.
- 정확도 비교: test 분할 양성·음성 라벨이 `replay_min_labels`(30, 내 판단: 결정 대상만 보고하면 라벨이 느리게 쌓인다) 이상이면 지금 rubric 과 후보 rubric 의 TPR·TNR 을 비교해 보인다. 업계 권장(약 100)보다 적어 참고 수치로만 보인다.
- 적용 규칙(초기값, 실사용 후 조정. 사용자: 해봐야 안다): 회귀 검사에서 빠지는 양성 묶음이 있으면 그 묶음을 보이고, 사용자가 명시적으로 확인할 때만 적용한다. 확인하고 적용했는지와 빠진 묶음 수를 `rubric-changes.jsonl` 에 남겨, 나중에 이 규칙이 너무 엄격한지 기록으로 판단한다.

## 11. 성공 기준

1. 2026-10-19 명시 회고(13세션)의 기록을 백필 스크립트(훅과 같은 추출 함수를 기록에 적용)로 근거화하고 retro 를 돌리면, "메모리에만 있다 → 전역으로" 류와 응답 품질 지적은 결정 대상으로 올라오지 않는다. 같은 분석에서 비용이 있었다고 본 항목(ADR 번호, 테스트 재요구, run_eval 충돌, inline-helper)은 결정 대상으로 올라오거나, 관문 미달로 쌓인 관찰로 남는다. 옛 라벨은 이 비교의 참고 목록일 뿐 채점 정답으로 쓰지 않는다.
2. 고정 기록 조각: 승인용 질문(대안 없는 진행 확인 → 올라옴, push 확인 → 안 올라옴), 도구 거절 후 교정, 반복 heredoc(2회·2세션 → 올라옴, 1세션 → 안 올라옴), 결정 패턴(같은 규칙 2회·2세션 → 올라옴, 반대 선택 있음 → 안 올라옴).
3. 훅 하나의 실행 시간(프로세스 시작부터 종료까지) p95 100ms 이하(내 판단).
4. 수락률은 결정 라벨로 잰다(8장). 재현율은 놓친 사례를 표본으로 사람이 확인하는 별도 절차가 필요하며 이번 범위에서는 절차만 정한다.
