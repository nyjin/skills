# `asr` 스킬 설계

작성일: 2026-11-10

## 1. 의도

녹음 파일을 받아 **화자별로 나뉜 한국어 전사본**을 만드는 Claude Code 스킬이다. 주로 쓰이는 녹음은 **회의**와 **면접**이다.

사용자는 이 전사본을 그대로 보관하기도 하고, 요약이나 면접 평가의 재료로도 쓴다. 다만 **요약과 평가는 이 스킬이 하지 않는다.** 별도 스킬이 맡아 단일 책임을 지킨다. 이 스킬의 책임은 "정확한 화자별 전사본"까지다.

## 2. 목표 · 비목표 · 실패 조건

**목표**
- 녹음 파일 하나를 주면 화자분리와 타임스탬프가 붙은 한국어 전사본(`.md`)을 만든다. 길이 제한은 없다. 사용자의 음성 메모에는 최대 120분 녹음이 있다.
- 긴 녹음은 묵음 지점에서 나눠 처리하되, **조각이 달라져도 같은 사람은 같은 화자로 이어 붙인다.** 중간에 참석자가 늘어나는 경우도 처리한다.
- 결과를 보여 주기 전에 잘못 쪼개진 화자를 자동으로 합친다.
- 분석이 끝나면 화자 목록을 보여 주고, 사용자가 원하면 화자에 실제 이름을 붙인다.
- 녹음이 매우 작게(멀리서) 녹음됐으면 스스로 판단해 보정한 뒤 분석하고, 보정했다는 사실을 알린다.
- 처음 실행할 때 필요한 구성 요소가 없으면, 용량과 기능을 알리고 동의를 받은 뒤 자동으로 설치한다.

**비목표**
- 요약, 회의록 정리, 면접 평가
- 녹음 사이에서 같은 사람을 알아보는 기능. 예: 지난 면접의 김철수를 이번 녹음에서 자동으로 식별하기
- 사용자가 화자를 직접 합치는 기능. 같은 이름을 주면 자연스럽게 해결되므로 따로 만들지 않는다(§4-⑦).
- 실시간(마이크) 전사
- Windows, Intel Mac, Linux 지원

**실패 조건** (동작은 해도 실패로 본다)
- **원본 녹음 파일을 수정하거나 덮어쓴다.**
- 사용자가 설치에 동의하지 않았는데 설치를 진행한다. 또는 설치하지 않은 상태로 다음 단계를 진행한다.
- 녹음의 일부를 알리지 않고 빼먹는다. 예: 길이 상한에서 잘리거나 `max_tokens`에 걸려 끊기는 경우
- 음질 보정이나 화자 자동 통합을 했는데 알리지 않는다.
- 서로 다른 두 사람을 한 화자로 합친다. 한 사람이 둘로 나뉘는 것보다 나쁜 오류로 본다.
- 지원하지 않는 환경이나 메모리 부족 상황에서 알 수 없는 오류를 내며 죽는다. 이 경우 명확한 안내와 함께 멈춰야 한다.

## 3. 결정된 기술 선택

검토 과정에서 사용자가 직접 결정한 사항이다.

| 항목 | 결정 | 근거 |
|---|---|---|
| ASR · 화자분리 엔진 | **VibeVoice-ASR**, MLX 8bit 양자화본 `mlx-community/VibeVoice-ASR-8bit`, 실행 라이브러리 **mlx-audio**(0.6.2 이상, 검증 버전 0.6.5) | 실제 회의 녹음(12분, 2인)을 비교했을 때 Whisper large-v3 + pyannote보다 낫다고 사용자가 판단했다. Whisper는 앞부분 누락, "Q." 환각, 문장 중간 화자 분할 문제가 있었다. |
| 제외한 엔진 | Whisper(mlx-whisper, WhisperX), pyannote | 위 비교 결과로 제외했다. 관련 모델과 환경은 이미 삭제했다. PyTorch 계열은 다시 들이지 않는 방향이다. |
| 긴 녹음 처리 | **조각당 최대 10분**(사용자 지정). 묵음 지점 기준으로 나눠 여러 번 호출한다. 파일을 실제로 자르지 않고, 메모리에 올린 음성 배열을 구간별로 잘라 넘긴다. | 메모리가 녹음 길이에 비례해 늘어나는 문제(§3 실측)와 mlx-audio의 59분 상한을 함께 해결한다. |
| 조각 간 화자 연결 | 화자별 **목소리 지문**(ECAPA-TDNN 임베딩)과 조각 겹침 구간을 함께 쓴다(§4-⑤). | 사용자가 결정했다. 검증 실험 없이 구조를 잘 잡는 것으로 갈음한다. |
| 가속 | Apple Silicon GPU(MLX) | M5 Pro에서 `Device(gpu, 0)` 사용을 확인했다. |
| 지원 환경 | macOS + Apple Silicon 전용 | 사용자 본인 맥에서 쓰고, 다른 환경에서는 게이트에서 막는다. |
| 스킬 이름과 위치 | `asr`, `~/.claude/skills/asr/` | 사용자 지정 |
| 설치 게이트 | SKILL.md 본문이 아니라 별도 reference 문서로 분리하고, 설치 여부 점검 스크립트를 둔다. | 사용자 지정 |
| Python | 시스템에 3.12 이상이 있으면 쓴다. 없으면 `brew install python@3.12`를 설치 고지에 넣고 동의를 받아 설치한다. Homebrew가 없으면 안내하고 멈춘다. | 사용자 승인 |

### 실측 데이터 (M5 Pro, 48GB, mlx-audio 0.6.5, 8bit)

| 입력 | 처리 시간 | 피크 메모리 | 결과 |
|---|---|---|---|
| 합성 음성 22초, 3화자 | 29초 (모델 로드 12.5초 별도) | 10.0GB | 화자 3명이 2명으로 합쳐짐. 같은 합성 목소리의 피치만 바꾼 극단적 조건이다. |
| 실제 회의 12분(727초), 2화자 | 177초 | 15.1GB | 화자 2명 정확. 침묵·잡음 구간은 `speaker_id=None`에 텍스트 `[Silence]` / `[Environmental Sounds]`로 나옴(96개 구간 중 12개) |

- 모델 크기: 9.52GB(HF 캐시). mlx-audio 실행 환경(Python 3.12 venv): 약 0.48GB.
- `generate()`의 `max_tokens` 기본값 8192는 약 25분 분량에서 잘린다. 12분 녹음은 `max_tokens=32768`로 처리했다.
- **메모리가 늘어나는 이유**
  - 모델 가중치(약 9.5GB)는 녹음 길이와 관계없이 고정이다.
  - 오디오 인코더의 중간 계산 결과는 녹음 길이에 비례해 늘어난다. 24kHz 파형을 3,200배 압축해 초당 토큰 7.5개로 만드는 과정이다.
  - KV 캐시는 토큰당 약 56KB로 작다(28층, KV 헤드 4개, 차원 128, bf16 기준).
  - 12분 실측에서 길이에 비례해 늘어난 부분은 약 5.6GB였다. 단순 비례로 늘리면 60분은 35~40GB로 추정된다.
  - 외부 보고로는 60분에서 61.5GB도 관측됐다. 그래서 **조각 길이로 메모리를 묶어 두는 것**이 이 설계의 전제다.

## 4. 동작 흐름

```
사용자: "이 녹음 전사해줘 (경로)"
  │
  ├─ ① 환경·설치 점검 (references/install.md + 점검 스크립트)
  ├─ ② 입력 검사 (파일, 디코딩 가능 여부)
  ├─ ③ 음질 판정 → 매우 작게 녹음됐으면 메모리 안에서 보정본을 만들어 분석
  ├─ ④ 조각 나누기 (VAD로 찾은 묵음 지점, 겹침 포함)
  ├─ ⑤ 조각별 VibeVoice 전사 → 목소리 지문으로 전역 화자에 연결
  ├─ ⑥ 화자 통합 (잘못 쪼개진 화자 자동 합치기) → 번호 다시 매기기
  ├─ ⑦ 저장: <이름>.json (기록 원본) → <이름>.md (보기용, json에서 생성)
  └─ ⑧ 안내: 화자 목록 + 화자별 첫 발언 + 보정·통합 사실
        └─ 사용자가 이름을 주면 json의 name만 고치고 md를 다시 만든다
```

### ① 환경·설치 게이트

**지원 환경 검사**
- `uname -s`가 `Darwin`이 아니거나 Apple Silicon이 아니면 다음과 같이 안내하고 멈춘다.
  > 이 스킬은 Apple Silicon(M1 이상) Mac 전용입니다. 현재 환경(…)은 지원하지 않습니다.
- Rosetta로 실행 중인 x86 셸에서는 `uname -m`이 `x86_64`로 나온다. 그래서 `sysctl -n hw.optional.arm64`도 함께 확인한다.

**메모리 검사**
- 조각은 **최대 10분**이다(사용자 지정, 겹침 포함). 12분 실측 피크가 15.1GB였으므로 10분 조각은 약 14GB 안쪽으로 예상된다.
- 메모리가 너무 작아 가장 짧은 조각도 처리하기 어려우면 실행 전에 안내하고 멈춘다.
- 구체적인 기준은 빌더가 정한다(§6).

**설치 상태 점검** (점검 스크립트가 확인할 항목)
1. `ffmpeg`가 PATH에 있는지
2. Python 3.12 이상이 있는지
3. 스킬 전용 venv(`~/.local/share/asr/venv`)가 있고, 그 안에 `mlx-audio`가 0.6.2 이상으로 import 되는지
4. 필요한 모델이 HF 캐시에 완전히 내려받아져 있는지(파일 누락이나 `.incomplete` 없음)
   - VibeVoice-ASR 8bit
   - VAD 모델
   - 목소리 지문(ECAPA) 모델

**설치 고지**

빠진 항목이 하나라도 있으면, 설치 전에 사용자에게 다음 내용을 알리고 동의를 받는다.
- **설치할 항목과 예상 용량:**
  - Python 실행 환경(mlx-audio 등): 약 0.5GB
  - VibeVoice-ASR 8bit: 약 9.5GB
  - VAD·ECAPA 모델: 수십 MB 수준이며, 빌더가 실측해 채운다.
  - 이미 설치된 항목은 빼고 계산한다.
- **설치 위치:** `~/.local/share/asr/venv`, `~/.cache/huggingface/hub`
- **제공 기능:**
  - 한국어 받아쓰기, 화자분리, 타임스탬프
  - 긴 녹음 처리와 조각 간 화자 연결
  - Apple Silicon GPU 가속
- **기타:**
  - 디스크 여유 공간이 부족하면 설치 전에 알린다.
  - 다운로드에 시간이 걸릴 수 있다고 알린다. 실측에서는 약 6MB/s로 수십 분이 걸렸다.

**설치와 그 이후**
- 동의하면 자동으로 설치하고, 끝나면 점검 스크립트를 다시 돌려 설치를 검증한다.
- 거절하면 그 자리에서 끝내고 이후 단계로 넘어가지 않는다.
- ffmpeg나 Python 3.12가 없으면 Homebrew로 설치한다. 이것도 설치 고지에 포함한다.
- Homebrew도 없으면 직접 설치하라고 안내하고 멈춘다. Homebrew 설치까지 자동으로 하지는 않는다.
- 설치 지침은 `references/install.md`로 분리하고, SKILL.md에는 "점검 스크립트를 먼저 돌리고, 미설치면 install.md를 따른다"는 포인터만 둔다.

### ② 입력 검사
- 파일이 없거나 ffmpeg로 디코딩할 수 없으면 안내하고 멈춘다.
- ffmpeg가 읽는 형식(m4a, mp3, wav, mp4 등)은 그대로 받는다.
- 원본은 읽기만 하고, 분석용 음성 배열로 디코딩해 메모리에 올린다.

### ③ 음질 판정과 보정

**대상**
- 사용자가 겪은 문제 유형은 "멀리서 작게 녹음된 경우"다.
- 판정은 ffmpeg `ebur128`의 통합 음량(LUFS)과 `volumedetect`를 기준으로 한다.

**판정 기준 참고 자료**
- 실제 회의 녹음(memo12)은 **-34.9 LUFS**(mean -36.3dB)였다. 보정 없이도 결과가 좋았다.
- 그래서 보정 임계값은 이보다 낮게 잡는다. 예를 들어 -40 LUFS 미만이다.
- **VibeVoice는 소폭의 게인 변경이나 노이즈 제거만으로도 화자 수 추정이 흔들린다**는 보고가 있다(VibeVoice 이슈 #407).
- 그러므로 정말 나쁠 때만 보정한다. 애매하면 보정하지 않는 쪽이 안전하다.

**보정 방식**
- 원본이 아닌 복제본에만 적용한다. 메모리 안의 배열이든 임시 파일이든 상관없다. 임시 파일이면 분석이 끝난 뒤 지운다.
- 처리 내용은 다음과 같다.
  - 저역 잡음 제거(high-pass)
  - 음량 정규화(loudnorm 또는 dynaudnorm)
  - 필요하면 약한 컴프레션

**알림**
- 보정 여부는 묻지 않고 스스로 판단한다.
- 대신 결과 안내 때 반드시 알린다. 예: "녹음 음량이 매우 낮아(-46 LUFS) 보정본으로 분석했습니다. 원본은 그대로입니다."

### ④ 조각 나누기
- 10분 이하 녹음은 나누지 않고 한 번에 처리한다.
- 10분을 넘는 녹음은 **조각 하나가 겹침을 포함해 10분을 넘지 않도록**(사용자 지정) 자른다. 10분 한계 안쪽에서 **VAD로 찾은 묵음 지점**을 고른다. 발화 중간에서 자르지 않기 위해서다. 한계 안쪽에 묵음이 없으면 10분 지점에서 자른다.
- 인접 조각은 **약 30~60초 겹치게** 자른다. 겹친 구간은 화자 연결의 근거로 쓴다(⑤).
- 조각마다 `max_tokens`를 조각 길이에 맞게 넉넉히 잡는다.
- 결과가 토큰 한도에 걸려 끊겼는지(마지막 구간의 끝 시각이 조각 끝보다 훨씬 앞인지 등) 확인한다. 끊겼으면 알리거나 다시 처리한다. 녹음 일부를 조용히 잃지 않기 위해서다.
- 겹친 구간의 발화는 최종 전사본에 한 번만 남긴다. 어느 쪽 조각을 남길지는 빌더가 정한다.

### ⑤ 조각별 전사와 화자 연결

**전사**
- 각 조각을 VibeVoice로 처리하면 구간마다 `start`, `end`, `speaker_id`(조각 안에서만 유효한 번호), `text`가 나온다.
- 타임스탬프는 조각 시작 시각을 더해 원본 녹음 기준으로 바꾼다.
- `speaker_id`가 `None`인 구간(`[Silence]`, `[Environmental Sounds]` 등)은 전사본에서 뺀다.

**목소리 지문**
- 조각 안 화자마다 깨끗한 구간만 골라 ECAPA 임베딩을 뽑아 평균을 낸다.
  - 2~3초 이상인 구간만 쓴다.
  - 화자가 바뀌는 경계 바로 앞뒤는 뺀다.

**전역 화자 명부에 연결**
- 첫 조각의 화자들로 명부(S1, S2, …)를 만든다.
- 다음 조각부터는 다음 순서로 연결한다.
  1. **겹침 구간 근거**: 겹친 구간에서 같은 시각에 같은 발화를 한 조각 내 화자는 그 명부 화자에 바로 연결한다.
  2. **지문 근거**: 남은 화자는 명부의 각 화자와 코사인 유사도를 계산해 **일대일**로 짝짓는다. 한 조각의 두 화자가 같은 명부 화자에 동시에 붙지 않게 한다.
  3. 짝의 유사도가 **연결 기준값(예: 0.5)** 미만이면 새 참석자로 보고 명부에 새 ID(S3…)를 추가한다. **2명으로 시작해 중간에 3명이 되는 경우가 여기서 처리된다.**
  4. 연결되면 명부 화자의 대표 지문을 새 지문과 섞어 갱신한다. 녹음 중 목소리 상태나 마이크 거리 변화에 따라가게 한다.
- 전역 ID는 처음 등장한 순서대로 매기고, 한 번 정하면 바꾸지 않는다.

### ⑥ 화자 통합 (결과를 보여 주기 전에)
- 모든 조각을 처리한 뒤, 명부의 **모든 화자 쌍**의 지문 유사도를 비교한다.
  - 조각 연결 단계에서 비교하지 않은 쌍도 포함한다.
  - VibeVoice가 같은 조각 안에서 한 사람을 둘로 쪼갠 경우도 여기서 잡는다.
- **통합 기준값**을 넘는 쌍은 합친다. 이 값은 연결 기준값보다 높게 잡는다(예: 0.7).
  - 이유: 다른 두 사람을 합치는 오류가 한 사람이 둘로 나뉘는 오류보다 나쁘다.
- 합칠 때는 먼저 등장한 쪽을 남긴다. 합쳐진 쪽에는 `merged_into`와 근거 유사도를 기록한다.
- 이 단계는 조각을 나누지 않은 짧은 녹음에도 똑같이 적용한다.
- 통합 후 남은 화자에게 등장 순서대로 표시 번호(화자 1, 2, 3…)를 빈 번호 없이 다시 매긴다.

### ⑦ 저장: `.json`이 기록 원본, `.md`는 보기용

**저장 위치**
- 기본은 입력 파일과 같은 폴더, 같은 이름이다.
- 입력이 시스템이 관리하는 위치에 있으면 현재 작업 폴더에 저장한다.
  - 예: 음성 메모 앱 폴더 `~/Library/Group Containers/group.com.apple.VoiceMemos.shared/`
  - 쓰기 권한이 없는 폴더도 마찬가지다.
- 같은 이름의 결과 파일이 이미 있으면 덮어쓰지 않는다. 처리 방식은 빌더가 정한다.

**`<이름>.json` 구조**

```jsonc
{
  "source": { "file": "20261106 164354.m4a", "duration": 3480.2 },
  "enhanced": null,                    // 보정 시 { "lufs_before": -46.1, "filters": "..." }

  "chunks": [                          // 어떻게 나눠 처리했는지
    { "index": 0, "start": 0.0,    "end": 1502.3 },
    { "index": 1, "start": 1442.3, "end": 2950.8 }
  ],

  "speakers": {                        // 전역 화자 명부
    "S1": { "name": null, "label_no": 1, "first_seen": 0.0,    "speech_sec": 812.4, "voiceprint": [/* 192차원 */] },
    "S2": { "name": null, "label_no": 2, "first_seen": 3.1,    "speech_sec": 640.0, "voiceprint": [...] },
    "S3": { "name": null, "label_no": 3, "first_seen": 1611.8, "speech_sec": 203.5, "voiceprint": [...] },
    "S4": { "merged_into": "S2", "merge_similarity": 0.83, "first_seen": 2100.4, "voiceprint": [...] }
  },

  "links": [                           // 조각 내 번호 → 전역 ID 연결 근거
    { "chunk": 0, "local": 0, "speaker": "S1", "how": "seed" },
    { "chunk": 1, "local": 1, "speaker": "S1", "how": "overlap+voice", "similarity": 0.81 },
    { "chunk": 1, "local": 2, "speaker": "S3", "how": "new",           "similarity": 0.29 }
  ],

  "segments": [                        // 발화. 전역 ID만 가리킨다(이름 직접 기록 안 함)
    { "start": 1.2, "end": 12.5, "speaker": "S1", "text": "어, 일단 현재 업무 리뷰 먼저…" }
  ]
}
```

- `voiceprint`는 해시가 아니라 비교 가능한 벡터다. 유사도를 계산할 수 있어야 하기 때문이다.
- **목소리 지문은 생체 정보다.** 해당 녹음의 `.json` 안에만 두고, 다른 곳에 모으거나 녹음 사이에 공유하지 않는다.
- 필드 이름과 세부 구조는 빌더가 다듬어도 된다. 다만 다음 원칙은 지킨다.
  - 명부, 연결 근거, 발화를 분리한다.
  - 발화는 전역 ID만 가리킨다.
  - 이름은 명부에만 기록한다.

**`<이름>.md` 생성 규칙**
- `segments`를 시간순으로 훑으며 각 `speaker`를 표시 이름으로 바꾼다.
  - `merged_into`가 있으면 그 대상을 따라간다.
  - 표시 이름은 `name`이 있으면 그 이름, 없으면 `"화자 {label_no}"`다.
- **표시 이름이 같은 발화가 연달아 나오면 한 단락으로 합친다.** 단락의 타임스탬프는 첫 발화 시각으로 쓴다.
  - 사용자가 두 화자에게 같은 이름을 주면 자연스럽게 하나로 보이게 하려는 것이다. 그래서 수동 합치기 기능이 필요 없다.

```markdown
**[00:00:01] 화자 1:** 어, 일단 현재 업무 리뷰 먼저 좀 하고 …

**[00:26:51] 화자 3:** 늦어서 죄송합니다 …
```

### ⑧ 결과 안내와 이름 바꾸기

**분석이 끝나면 안내하는 내용**
1. 저장된 파일 경로
2. 화자 목록과 화자별 첫 발언 1~2문장(누가 누구인지 알아보기 쉽게)
3. 보정을 했다면 그 사실
4. 화자 자동 통합을 했다면 그 사실. 예: "목소리가 같은 화자 1쌍을 하나로 합쳤습니다."
5. 안내 문구: "화자는 화자1, 화자2, 화자3입니다. 이름을 바꾸려면 원하는 이름을 알려 주세요."

**이름 바꾸기**
- 사용자가 이름을 주면(예: "화자1은 김철수, 화자3은 박지민") `.json`의 `speakers[*].name`만 고치고 `.md`를 다시 만든다. 다시 분석하지는 않는다.
- 이름을 주지 않으면 그대로 끝낸다.
- 일부 화자만 이름을 주면 나머지는 "화자 N"으로 둔다.

## 5. 스킬 구조(제안)

```
~/.claude/skills/asr/
├── SKILL.md                 # 트리거 설명, 전체 흐름, 결과 안내 문구
├── references/
│   └── install.md           # 환경 게이트·설치 고지·설치 절차(사용자 지정: 별도 분리)
└── scripts/
    ├── check_env.sh         # 지원 환경·메모리·ffmpeg·Python·venv·모델 점검. 결과를 기계가 읽을 수 있게 출력
    ├── install.sh           # (필요 시 brew로 ffmpeg/python) → venv 생성 → mlx-audio 설치 → 모델 다운로드
    ├── transcribe.py        # 입력 검사 → 음질 판정·보정 → 조각 나누기 → 전사 → 화자 연결·통합 → json 저장 → md 생성
    └── rename.py            # json의 name 갱신 → md 재생성
```

- 스크립트 분할(예: 화자 연결 로직을 별도 모듈로)은 빌더가 바꿔도 된다.
- **설치 점검 스크립트**와 **install reference 분리**는 사용자 요구라 바꿀 수 없다.
- md 생성 로직은 `transcribe.py`와 `rename.py`가 같은 코드를 쓰게 한다. 두 경로의 출력이 달라지지 않게 하기 위해서다.

## 6. 빌더에게 맡기는 것

**ECAPA 모델 선택**
- mlx-audio 0.6.5 안에 ECAPA-TDNN이 두 군데 있다.
  - `lid/models/ecapa_tdnn`: 언어 식별용
  - `codec/models/ecapa_tdnn/speaker.py`: 음성 합성 코덱용 화자 특징
- 둘 중 화자 구분에 쓸 만한 것이 있는지, 가중치를 어디서 받는지는 확인하지 않았다.
- 둘 다 맞지 않으면 화자 인증용으로 학습된 ECAPA 가중치를 MLX로 쓰는 방법을 찾는다.
- PyTorch·pyannote를 다시 들이는 방안은 마지막 수단이다. 택하면 설치 용량 고지에 반영한다.

**VAD 모델**
- mlx-audio의 `vad/models/silero_vad`를 우선 검토한다.

**수치와 세부 동작**
- 연결 기준값과 통합 기준값. 예시값 0.5/0.7은 출발점일 뿐이고 실제 녹음으로 조정한다.
- 10분 한계 안에서의 조각 목표 길이, 겹침 길이, 겹친 구간 발화의 중복 제거 방식
- 음질 보정 임계값과 ffmpeg 필터 체인. 단, §3의 실측(-34.9 LUFS는 보정 불필요)과 이슈 #407을 고려한다.
- `max_tokens` 값, 반복 루프(VibeVoice 이슈 #373)와 토큰 한도 끊김 감지·재시도 방식
- 결과 파일 이름 충돌 처리, 점검 스크립트 출력 형식, 처리 시간이 길 때 진행 상황을 보여 주는 방식

**테스트 구성**
- 참고용 자료
  - `vibevoice-test/test_ko.wav`: 합성, 22초, 3화자
  - `vibevoice-test/memo12.m4a`: 실제 회의 12분, 2화자. **사용자 개인 녹음이므로 외부 반출 금지**
  - `memo12_vibevoice.md`: 이전 실행 결과
- 긴 녹음 검증에는 음성 메모 폴더의 51~120분 녹음 복제본을 쓸 수 있다. 원본은 건드리지 않는다.
