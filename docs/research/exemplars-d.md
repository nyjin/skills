# 한국어 기술 문서 본보기 후보 D — 사용자 선정 4편의 구성 분석

작성일: 2026-10-15. 평가 기준은 `synthesis.md`의 원칙 ID(C 독자, D 유형, E 정보 구조, M 시각화, S 왜·결정 맥락, F 구체성 등)를 따른다. 점수 척도는 `exemplars-b.md`와 같다.

이 4편은 사용자가 "구성이 좋은 예"로 직접 골랐다. 그래서 문장보다 **구성(뼈대·전개·연결 장치)** 을 중심으로 분석했다. 원문은 스킬에 넣지 않고, 일반화한 구조 패턴만 가져간다.

## 1. Agentic AI 시대, 기업의 AI 활용 전략은?

- URL: https://www.samsungsds.com/kr/insights/ai-strategy-for-your-company.html
- 출처: 삼성SDS 인사이트 리포트(AX), 홍은주(전략마케팅팀), 2025-04-18. 사내 연구팀 임원의 대외 포럼 발표를 글로 옮겼다.
- 추정 독자: 기업 IT 리더와 의사결정자(포럼 청중인 대외 고객사). 기술 실무자는 부차 독자다.
- 유형: **설명(개념·동향) + 전략 제언**. 실무 유형으로는 "의사결정자용 인사이트 리포트·브리핑"이다.
- **점수: 4.** 비개발 의사결정자에게 "개념 → 시장 변화 → 사례 → 우리가 할 일"을 한 흐름으로 보여 주는 뼈대가 탄탄하다. 그림마다 번호·제목·출처를 붙이는 규칙도 일관된다.

### 골격

```
(H2) Agentic AI 시대, 기업의 AI 활용 전략은?            ← 글 제목
  리드 문단 1개 (요약 소개)
  [Executive Summary] 불릿: 핵심 / 핵심 요소 3 / 주요 효과 3 / 핵심 메시지 1
  출처 고지 1문단 (어느 발표를 바탕으로 썼는지)
  도입 2문단 (최근 발언 → 10여 년 기술 연혁)                         ≈ 9%
H2 Generative AI에서 Agentic AI로                                       ≈ 51%
  (1) GPU 사용은 여전히 늘어날 것으로 예상됩니다
  (2) AI 기업들의 전략이 변화하고 있습니다
  (3) 다들 같은 Agent를 말하고 있나요?
  (4) Agentic AI, 다양한 사례가 개발되고 있습니다
  (5) 다양한 Agentic AI 유형, 최적의 선택이 중요합니다
H2 기업의 AI 활용 전략                                                  ≈ 34%
  (도입 문단: 이 절에서 다룰 요소를 한 번에 나열)
  (1) 전사적 AI 도입을 시도하면 개선점이 보입니다
  (2) 시스템과 솔루션을 연결하면 AI 적용 효과와 범위가 확대됩니다
  (3) 기업 내 다양한 시스템과 데이터 접근, 전체적 보안이 필요합니다
  (4) AI 활용, 사람의 역할이 더욱 중요해집니다
H2 Agentic AI 시대, 데이터 기반 혁신 추진   (결론)                     ≈ 6%
  발표자 표기
H2 FAQ (질문 7개, 사이트 템플릿으로 추정)                               (분량 제외)
```

### 구성 분석

- **도입부가 여는 방식.** 세 겹으로 연다. ① 리드 문단 한 개가 글의 범위(유형·사례·도입 전략)를 예고한다. ② **Executive Summary 불릿**이 결론("기술보다 비즈니스 연결")과 요소·효과를 먼저 준다. ③ 출처 고지 문단이 이 글이 어느 발표에 기반했는지 밝힌다. 그 뒤 도입 두 문단은 "지금 왜 이 이야기인가"를 맡는다. 첫 문단은 최근 업계 발언으로 시의성을 잡고, 둘째 문단은 퍼셉션 → 생성형 → 에이전틱으로 이어지는 10여 년 연혁으로 독자를 같은 출발선에 세운다.
- **전개 논리.** 크게 "세상이 이렇게 바뀌었다(H2-1)"에서 "그러니 기업은 이렇게 하라(H2-2)"로 간다. H2-1 안의 순서는 인프라(GPU) → 공급자 전략 → 개념 정의의 혼란 → 사례 → 유형 선택이다. 바깥(시장)에서 안(선택)으로 좁혀 들어가며, 마지막 소절이 "최적의 선택"으로 끝나 H2-2의 "전략"으로 자연스럽게 넘어간다. H2-2는 도입 → 연결 → 보안 → 사람으로 이어진다. 기술적 확장에서 위험 통제로, 다시 조직·사람으로 넓어진다.
- **섹션 간 연결 장치.**
  - H2-2 첫 문단이 이 절에서 다룰 요소(경영진 의지, 데이터 체계, 보안, 임직원 역량, 효과 평가)를 미리 나열하는 **절 단위 로드맵** 역할을 한다.
  - 뒤 절에서 앞 그림을 다시 부른다. 보안 소절이 "앞서 설명한 대로"라며 H2-1의 OWASP 유형 그림으로 돌아간다.
  - 소제목 "(N) ~합니다"가 그 소절의 결론 문장이다. 소제목만 이어 읽어도 논지가 선다.
- **요약·결론의 위치.** 앞(ES)과 뒤(결론 H2)에 **이중 배치**했다. 결론 절은 기술 진화 연혁을 한 번 더 짚은 뒤 "문제 정의·데이터·사람"이라는 메시지로 닫는다. ES의 핵심 메시지와 대칭을 이룬다(북엔드).
- **시각 자료.** 그림 8개. 모두 `[그림 N] 제목 (출처: 작성자/발표자/외부 기관)` 형식이다. 바로 아래에 그림 내용을 글로 다시 적은 대체 텍스트 블록이 있다.

  | 그림 | 보여 주는 것 | 배치 |
  |---|---|---|
  | 1 | 생성형 vs 에이전틱 특징 대비 | 두 개념 정의 문단 직후 |
  | 2 | 모델 학습·활용 3단계별 GPU 사용 | 소절 첫 문단 뒤. 그림 → 번호 목록 3개 → 단계별 설명 문단 3개로 풀어 감 |
  | 3 | LLM 중심 vs 에이전트 중심 전략 | 변화 이유를 설명한 문단 뒤 |
  | 4 | 에이전틱 시스템 구성(Agent 중심에 Prompt·메모리·LLM·Tool) | 구성 요소를 문장으로 소개한 직후 |
  | 5 | OWASP 기준 에이전트 10유형 | 유형 몇 개를 문장으로 예시한 뒤 전체 목록으로 |
  | 6 | 월평균 LLM 호출 빈도 × 활용도로 본 업무 자동화 사례 | 호출 빈도 차이를 문장으로 말한 직후 |
  | 7 | 자사 오퍼링 계층도(인프라~에이전트) | "연결이 필요하다"는 주장 뒤 |
  | 8 | 결과 생성 → 검토 → 피드백 → 정제 → 학습 → 업데이트 순환 | 순환을 문장으로 설명한 직후 |

  패턴은 **"문장으로 먼저 말하고, 그림으로 확인시키고, 대체 텍스트로 다시 한 줄 요약"** 이다.
- **표·목록 사용.** ES는 2단 중첩 불릿이다. 단계 설명은 번호 목록(그림 2), 대등한 유형 나열은 글머리 기호(그림 5)로 쓴다. 본문 문단은 길고 산문 위주다.
- **독자 수준 맞춤.** 영어 용어는 한국어와 원어를 병기한다('에이전틱 AI(Agentic AI)'). 비유("똑똑한 비서", "두뇌 역할")를 쓰고, 벤치마크는 괄호 삽입으로 그 자리에서 풀이한다. 비개발 의사결정자에 맞춰 코드·설정은 전혀 없다.

### 잘한 점

1. **E-1·E-2·C, ES 불릿 블록.** 결론, 요소 3개, 효과 3개, 한 줄 메시지를 본문보다 먼저 준다. 의사결정자는 여기서 읽기를 멈춰도 된다. 확장 C 행("의사결정자는 영향·결정 먼저")의 실물 사례다.
2. **E-5, 문장형 소제목 "(N) ~합니다".** "GPU 사용은 여전히 늘어날 것" 같은 소제목이 그 소절의 결론이다. 번호와 평서문 어미를 맞춰 같은 수준을 같은 형태로 유지한다.
3. **M·P, 그림 규칙의 일관성.** 그림 번호, 제목, 출처 구분(작성자 제작 / 발표자 제작 / 외부 기관)을 그림 8개에 똑같이 적용했다. 외부 그림(OWASP)은 출처 문서명까지 적는다.
4. **E-4, 바깥에서 안으로 좁히는 전개.** 시장 → 공급자 → 개념 → 사례 → 선택 → 우리 전략 순서라서, 독자가 "그래서 우리는?"이라는 질문에 도달할 때 마침 H2-2가 시작된다.
5. **P·S, 한계를 함께 말한다.** 에이전트 성공률이 100%가 아니므로 선별적으로 써야 한다는 점, 연결 설계가 잘못되면 레거시처럼 복잡해진다는 점, 사람의 검수가 필요하다는 점을 주장 바로 뒤에 둔다.
6. **I, 용어 병기와 즉석 풀이.** 처음 나오는 용어는 한국어(원어)로 쓰고, 낯선 지표는 괄호로 그 자리에서 정의한다.

### 아쉬운 점

- **ES와 본문이 어긋난다.** ES는 "Use Case 정의·거버넌스"를 핵심 요소로 꼽는데, 본문 H2-2는 연결·보안·사람을 다룬다. ES를 나중에 사이트 템플릿으로 덧붙인 것으로 보인다. 요약 블록은 본문 소제목과 1:1로 맞아야 한다(E-1). FAQ도 같은 템플릿으로 보이며, 본문에 없는 주장(ROI 검증 등)이 섞여 있다.
- **"(N)" 소제목이 실제 제목 태그가 아니다.** 목차·앵커로 훑을 수 없고(E-7), 소절 문단 하나가 600자를 넘는 경우가 있어 G·E-9 기준에 못 미친다. 제목도 질문형이다(E-5).

### 우리 모범 문서로 가져올 구조 패턴

1. **의사결정자용 앞머리 3종: 리드 1문장 → ES 불릿(결론 / 요소 / 효과 / 한 줄 메시지) → 출처·근거 고지.** 본문을 읽지 않아도 결정에 필요한 것을 얻게 한다. ES 항목은 본문 H2·H3와 1:1로 대응시킨다.
2. **"세상의 변화 → 우리의 대응" 2부 구성.** 1부는 바깥에서 안으로 좁혀(시장 → 개념 → 사례 → 선택지), 1부 마지막 소절이 2부의 질문을 연다. 2부 첫 문단에서 이 절의 요소를 미리 나열한다.
3. **결론 문장형 소제목.** 같은 수준 소제목을 "주어 + 서술어" 평서문으로 통일해, 소제목만 이어 읽어도 요약이 되게 한다.
4. **그림 캡션 규칙: `[그림 N] 무엇을 보여 주는가 (출처: 작성자/외부)` + 바로 앞 문장에서 주장, 뒤에 한 줄 텍스트 요약.**

## 2. 쿠버네티스 pod, 2026년 효율적인 컨테이너 관리 핵심 5가지

- URL: https://wikidocs.net/blog/@history/21439/
- 출처: 위키독스 블로그 "모든 것의 역사"(@history), 2026-07-02, 분류 "유용한정보"
- 추정 독자: 쿠버네티스를 이미 쓰고 있는 입문~중급 운영자·개발자. Pod 정의부터 다시 짚어 주므로 입문자도 읽을 수 있다.
- 유형: **설명 + How-to 혼합**. 실무 유형으로는 "모범 사례(베스트 프랙티스) 가이드"다.
- **점수: 3(뼈대만 4).** "요약 → 정의 → 원칙 N개 → 한계 → FAQ → 참고 자료"라는 가이드 뼈대가 이번 4편 중 가장 깔끔하다. 다만 생성형 글의 흔적이 있고, 예제가 없다.

### 골격

```
(H1) 쿠버네티스 pod, 2026년 효율적인 컨테이너 관리 핵심 5가지
  도입 1: 결론 요약 문단 (5요소 나열 + 최신 문서 확인 권고)
  도입 2: Pod 정의 + 왜 지금 중요한가(설문 수치)                       ≈ 9%
H2 리소스 효율성 극대화: Pod 리소스 요청 및 제한 최적화               ≈ 13%
  (불릿 2 + 표 1 + 도구 문단)
H2 자동화된 스케일링 전략: 변화에 유연한 Pod 운영                     ≈ 9%
  (불릿 3 + [잘못 놓인] "이 글은 5대 원칙을 제시" 문단)
H2 강력한 보안 및 거버넌스: Pod의 안정적인 생명 주기 관리             ≈ 11%
H2 효과적인 모니터링 및 로깅: Pod 상태 실시간 파악                    ≈ 11%
H2 GitOps 기반의 선언적 배포: Pod 관리의 일관성과 자동화              ≈ 9%
H2 한계 및 주의사항: Pod 관리의 실제 도전 과제                        ≈ 10%
  (첫째~마지막으로, 5개)
H2 자주 묻는 질문   (Q1~Q5)                                            ≈ 14%
H2 마무리                                                              ≈ 5%
H2 참고 자료   (5건, 각각 확인일 + 가져온 내용)                        ≈ 8%
H2 함께 보면 좋은 글
```

### 구성 분석

- **도입부가 여는 방식.** **첫 문단이 바로 결론**이다. 5요소를 한 문장에 나열하고 "기술은 빨리 바뀌니 공식 문서를 확인하라"는 단서까지 단다(BLUF). 둘째 문단은 대상 정의(Pod = 가장 작은 컴퓨팅 단위)를 하고, 업계 설문 수치로 "왜 지금" 중요한지 근거를 댄다. 요약 → 정의 → 동기, 세 역할이 두 문단에 다 들어 있다.
- **전개 논리.** 원칙 5개의 순서는 Pod 하나의 자원 설정 → 여러 Pod의 확장 → 보호 → 관찰 → 배포 방식이다. 단위가 점점 커지고 운영 수명 주기를 따라간다. 그 뒤 **한계** 절이 원칙 5개와 거의 1:1로 대응한다(오버커밋↔리소스, 보안 설정 복잡성↔보안, 데이터 과부하↔모니터링, 비용 예측 불확실성↔스케일링, 기술 변화↔전체). "하라"를 말한 다음 "하면 생기는 문제"로 균형을 맞춘다.
- **섹션 내부의 반복 틀.** 모든 원칙 H2가 **"왜 중요한가 1문단 → `용어: 설명` 불릿 3~5개"** 로 같은 모양이다. 첫 절만 표와 도구 안내 문단이 더 붙는다.
- **제목 형식.** 원칙 H2 다섯 개가 모두 `무엇을 하나: 얻는 효과` 두 단 구조다(예: 스케일링 전략 + 유연한 운영). 한계 절도 같은 형식을 따른다. 같은 수준 같은 형태(E-5)를 지킨다.
- **연결 장치.** 섹션 사이 전환 문장은 거의 없다. 대신 각 H2 첫 문장이 "2026년에는 …"으로 시작해 시점 프레임을 반복한다. 연결보다 **병렬 독립 섹션**을 택한 구성이다. 한계 절의 서수("첫째 … 마지막으로")가 앞 원칙들을 다시 훑는 장치가 된다.
- **요약·결론의 위치.** 앞(첫 문단)과 뒤(마무리)에 이중 배치했다. 마무리 첫 문단은 5요소를 구체 기술명과 함께 다시 나열하고, 둘째 문단은 행동 권고로 닫는다. FAQ가 본문과 마무리 사이에 있어 "다시 묻기" 층을 하나 더 만든다.
- **시각 자료.** 그림 없음. 시각 요소는 **표 1개**(CPU·메모리 × 요청·제한·중요성·주의사항, 마지막 행은 권장사항)뿐이다. 표 앞에 제목 문장("… 가이드라인 (2026년 기준)")을 붙여 기준 시점을 밝힌다.
- **독자 수준 맞춤.** 단위(밀리코어, 500m = 0.5코어)와 약어(OOMKilled, CVE, HPA/VPA/KEDA)를 첫 등장에서 풀어 쓴다. FAQ Q3은 본문에 없던 **"언제 무엇을 쓰나"** 선택 기준을 덧붙인다. 정의를 원하는 입문자(Q1), 선택에 고민하는 실무자(Q3)를 따로 챙긴다.

### 잘한 점

1. **E-1·E-2, 첫 문단 BLUF.** 제목의 "핵심 5가지"를 첫 문단에서 바로 이름으로 나열한다. 독자는 첫 문단만 읽고도 목차를 안다.
2. **E-5·E-6, 원칙 섹션의 같은 틀 반복.** 제목 형식(`행동: 효과`)과 내부 구조(이유 문단 → 용어 불릿)를 다섯 번 똑같이 써서 예측 가능하다.
3. **P·S, 한계 절이 원칙과 짝을 이룬다.** 권고마다 반작용을 대응시켜, 모범 사례 글이 흔히 빠지는 일방적 권고를 피한다.
4. **I·L, `용어: 설명` 불릿과 첫 등장 풀이.** HPA·VPA·KEDA를 같은 형식으로 나란히 두고 각각 무엇을 기준으로 움직이는지 적는다. 비교 표의 전 단계 역할을 한다.
5. **P·Q, 참고 자료에 확인일과 가져온 내용 범위를 적는다.** 항목마다 "언제 확인했는지"와 "이 자료에서 무엇을 가져왔는지"를 괄호로 적어, 시의성이 중요한 글의 근거 추적과 갱신을 돕는다.

### 아쉬운 점

- **논지 문단이 엉뚱한 곳에 있다.** "이 글은 5대 원칙을 제시한다"는 문단이 스케일링 절 끝에 들어가 있다. 도입부에 있어야 할 문장이다. 각 H2가 "2026년에는"으로 시작하는 반복, 본문을 거의 그대로 다시 말하는 FAQ, 출처 없는 수치 한 건(강화 이미지 개수)과 함께 **생성형 글로 추정되는 근거**다.
- **운영 가이드인데 예제가 없다(N).** requests/limits·PSS 레이블·NetworkPolicy 중 어느 것도 YAML 예시를 보여 주지 않는다. 표의 "권장사항" 행이 다른 행(CPU·메모리)과 성격이 달라 표 구조도 어긋난다(L).

### 우리 모범 문서로 가져올 구조 패턴

1. **모범 사례 가이드 뼈대: BLUF 문단(원칙 N개 이름 나열) → 대상 정의·동기 → 원칙 H2 × N → 한계·주의 → FAQ → 마무리 → 참고 자료.**
2. **원칙 H2 제목은 `행동: 효과` 두 단, 본문은 "왜 1문단 → `용어: 설명` 불릿"으로 고정.** 필요한 원칙에만 표나 예제를 덧붙인다(우리 문서는 예제를 필수로 한다).
3. **"한계" 절은 원칙과 1:1 대응으로 쓴다.** 원칙마다 "이걸 하면 생기는 위험"을 짝지어, 권고 일변도를 막는다.
4. **참고 자료 = 제목 · 출처 · 확인일 · (무엇을 가져왔는지).** 시점에 민감한 문서의 기본 꼬리로 쓴다.

## 3. 데브옵스 도입 성공 전략: 문화, 기술, 그리고 미래를 위한 마스터 플랜

- URL: https://eis501.tistory.com/entry/데브옵스-도입-성공-전략-문화-기술-그리고-미래를-위한-마스터-플랜
- 출처: 티스토리 개인 블로그(필명 "희망벨트"), 2025-07-29, 분류 IT정보
- 추정 독자: 데브옵스 도입을 검토하는 조직의 리더·입문 실무자
- 유형: **설명(개요) + 가이드**. 실무 유형으로는 "도입 전략 종합 개요(입문 가이드)"다.
- **점수: 3(뼈대만).** 목차·정의 박스·섹션 샌드위치(브리지 문단 → 항목 → 마무리 한 줄)라는 **골격 장치**는 교과서처럼 갖췄다. 내용 중복, 출처 없는 수치, 생성 흔적 때문에 문장·내용은 본보기가 아니다.

```

### 구성 분석

- **도입부가 여는 방식.** 첫 문단은 "경쟁력 = 혁신 속도"라는 시대 배경으로 시작해, 데브옵스를 한 문장으로 정의하며 끝난다. 둘째 문단은 "어떻게 성공하나"라는 질문을 던지고, 다룰 범위(개념 → 트렌드 → 전략·사례 → 전문가)를 **문장으로 된 목차**로 예고한다. 바로 이어서 실제 목차(H2)가 번호 목록으로 나온다. 예고 문장과 목차가 겹치지만, 범위를 두 번 확인시키는 효과가 있다.
- **전개 논리.** 무엇인가(정의·3축 전략) → 어디로 가나(트렌드) → 증거(통계) → 어떻게(모범 사례) → 권위(전문가) → 남은 질문(FAQ) → 결론. 설득형 글의 고전 순서다. 1절 안의 3축은 문화 → 기술 → 전략 순인데, 그 이유를 문장으로 밝힌다(핵심은 사람·문화이고, 그 기반 위에 기술이 올라간다).
- **섹션 간 연결 장치(이 글의 가장 큰 장점).** 모든 H2가 똑같은 **샌드위치**다.
  1. **브리지 문단**: 이 절이 왜 필요한지, 무엇을 볼지 말하고 "살펴보겠습니다"나 질문으로 끝낸다.
  2. **항목 H4들**: 각각 짧은 설명 문단.
  3. **마무리 한 줄**: "이처럼 …"으로 절의 결론을 한 문장으로 다시 묶는다.
  1절의 H4 3개도 "어떤 문화적 변화가 필요할까요?"처럼 질문으로 끝나는 도입 문장이 있어 다음 목록을 부른다.
- **요약·결론의 위치.** 앞에는 범위 예고와 목차만 있고, 결론은 맨 끝 H2에 있다. 결론은 절 1~5를 순서대로 한 번씩 되짚고 행동 권고로 닫는다.
- **시각 자료.** 사실상 없음. 목차 아래 스톡 사진(대체 텍스트 "관련 이미지1")과 통계 절의 빈 이미지(src 없음)뿐이다. 정보를 담은 그림은 0개다.
- **표·목록 사용.** 목차는 번호 목록, 1절 항목은 `굵은 이름: 설명` 불릿이다. 2~5절은 불릿 안에 H4를 넣은 구조다. 통계(채택률·시장 규모 등)는 표에 맞는 데이터인데도 문단으로 썼다.
- **독자 수준 맞춤.** 정의 박스, 약어 병기(IaC, MTTR, SAST/DAST, YBIYRI), FAQ의 "애자일과의 관계" 같은 입문자 질문을 둔다. FAQ 3번은 DORA 4지표(배포 빈도, 변경 리드 타임, MTTR, 변경 실패율)를 괄호 정의와 함께 나열한다. 본문보다 FAQ가 더 실용적이다.

### 잘한 점

1. **E-7, 앞머리 목차.** 번호 붙은 H2를 그대로 목차로 보여 주고, 본문 H2에도 같은 번호를 붙여 위치를 알기 쉽게 한다.
2. **E·G, 섹션 샌드위치(브리지 → 항목 → 마무리 한 줄).** 독자가 각 절의 목적과 결론을 처음과 끝에서 확인한다. 긴 개요 글에서 길을 잃지 않게 하는 장치다.
3. **I·C, 정의 박스.** 핵심 용어를 본문 흐름과 분리된 상자에 한 번 정의하고 시작한다.
4. **S, 순서의 이유를 문장으로 말한다.** 문화가 먼저이고 기술은 그 위에 선다는 근거를 대고 3축의 순서를 정한다.
5. **C, FAQ로 입문자 질문을 따로 받는다.** "어떤 기업에 맞나", "성과는 어떻게 재나", "애자일과 관계는" 같은 질문을 본문 밖으로 빼서 본문 흐름을 지킨다.

### 아쉬운 점

- **MECE가 깨졌다.** CI/CD·자동화·모니터링·IaC·DevSecOps가 1절(기술), 2절(트렌드), 4절(모범 사례), 5절(전문가)에 거듭 나온다. 절을 "정보 출처(트렌드·통계·전문가)"로 나눠서 "주제"가 겹친 것이다. 목차는 깔끔해 보여도 실제 정보 구조는 중복이 많다(E-3, E-8).
- **근거와 신뢰성 문제(P·F).** 통계에 출처가 하나도 없고, 시장 규모가 2028년 255억 달러에서 2030년 194억 달러로 줄어드는 모순이 있다. 전문가 인용에 화자가 없다. 맨 끝의 "작성 팁 요약" 목록과 키워드 나열 줄은 **생성 프롬프트의 잔재**로 보인다. H3를 건너뛰고 H4를 쓴 위계 문제도 있다.

### 우리 모범 문서로 가져올 구조 패턴

1. **섹션 샌드위치: 브리지 문단(왜 이 절인가 + 무엇을 볼지) → 항목 → "정리하면" 한 줄.** 긴 개요·온보딩 문서에서 쓴다. 단, 마무리 줄은 새 정보 없이 결론만 담는다.
2. **도입부 = 배경 한 문장 + 한 줄 정의 + 범위 예고, 바로 아래 번호 목차.** 본문 H2에도 같은 번호를 붙인다.
3. **반면교사: 절은 "출처 종류"가 아니라 "주제"로 나눈다.** 트렌드·통계·전문가 의견은 독립 절로 두지 말고, 해당 주제 절 안에 근거로 녹인다.

## 4. 당근페이 백엔드 아키텍처가 걸어온 여정

- URL: https://medium.com/daangn/%EB%8B%B9%EA%B7%BC%ED%8E%98%EC%9D%B4-%EB%B0%B1%EC%97%94%EB%93%9C-%EC%95%84%ED%82%A4%ED%85%8D%EC%B2%98%EA%B0%80-%EA%B1%B8%EC%96%B4%EC%98%A8-%EC%97%AC%EC%A0%95-98615d5a6b06
- 출처: 당근 기술 블로그, Jeremy(당근페이팀 백엔드), 2026-01-15
- 추정 독자: 서비스 성장에 따라 코드베이스 구조를 고민하는 백엔드 엔지니어와 팀 리드(중급 이상). 레이어드·헥사고날·클린 아키텍처를 이름 정도는 아는 수준을 전제한다.
- 유형: **설명(진화사) + 설계 결정 기록**. 실무 유형으로는 "아키텍처 변천 회고 = 다단계 ADR"이다.
- **점수: 5.** 같은 결정 단위(문제 → 선택 이유 → 구조 → 규칙 → 전환 방법 → 결과)를 세 번 시간순으로 반복하고, 앞 단계의 문제를 다음 단계 결과에서 명시적으로 해결 확인한다. 회고와 한계까지 갖췄다.

### 골격

```

### 구성 분석

- **도입부가 여는 방식.** 자기소개 다음 둘째 문단이 **글 전체의 지도**다. 출발점, 거쳐 온 3단계, 현재를 한 문단에 다 말한다. 이어서 콘웨이 법칙 인용으로 "조직이 바뀌면 코드 구조도 바뀐다"는 해석 틀을 준다. 실제 팀 구성과 프로젝트 분할을 그 틀에 대어 보고, 도메인이 늘며 생긴 성장통을 설명한 뒤 "정답은 없지만 각 변화의 배경과 인사이트를 나누겠다"는 약속으로 닫는다. **지도 → 해석 틀 → 문제 제기 → 읽을거리 약속** 순서다.
- **전개 논리.** 시간순이지만 단순 연대기가 아니다. **"단계 H2 → 그 단계의 부작용 H2"** 가 번갈아 나온다(첫 번째 / 두 번째 / 적용 이후(문제) / 세 번째 / 적용 이후(효과)). 각 단계는 앞 단계가 남긴 문제를 풀려고 등장한다. 그래서 독자는 "왜 바꿨나"를 항상 직전 절에서 이미 읽은 상태로 다음 결정을 만난다.
- **단계 내부의 결정 단위(두 번째 단계 기준).** 계기(연말 리팩터링 기간) → 번호 매긴 문제 3개 → "규칙만으로 버티는 대안"의 한계 → 선택 이유("사람이 아니라 구조로 제어") → 모듈 3개 정의 목록 → 모듈 간 의존 규칙 목록 → 전환 전략 2개(각각 용어 풀이 + 참고 링크) → 효과 → 이후 성과. ADR 요소(맥락·대안·결정·결과)가 블로그 문체 안에 다 있다.
- **섹션 간 연결 장치.**
  - 문제 번호를 앞뒤로 잇는다. "문제 1·문제 2" H3가 세 번째 단계의 "목표" 불릿(도메인 모듈화, 배포 독립성)으로 이어지고, "적용 이후" 첫 H3가 **"앞 구조의 문제가 해결됐다"** 로 고리를 닫는다.
  - 각 단계 H2 마지막 문단이 다음 절의 문제를 예고한다(레이어드 절 끝의 "기술 부채로 자리 잡았다", 헥사고날 효과 끝의 이후 확장 이야기).
  - 세 번째 단계 첫 문단이 직전 구조를 한 문장으로 진단한다. 핵심과 외부 구현은 나눴지만 도메인 사이는 나누지 못했다는 내용이다.
  - 독자 상황 가정 문단(엔지니어 셋이 프로젝트 스무 개를 맡은 상황을 상상하게 함)으로 문제 절을 연다.
- **요약·결론의 위치.** 앞(지도 문단)과 뒤(마치며의 여정 재요약)에 이중 배치했다. 도입의 콘웨이 인용과 마무리의 Goldsmith 인용이 **인용 북엔드**를 이룬다. 회고 H3는 KPT 형식으로 남은 문제(빌드 속도, 인지 부하, 경계 해석 차이)를 인정하고, "모노레포가 늘 정답은 아니다"로 결론의 적용 범위를 스스로 제한한다.
- **시각 자료.** 이미지 14개. 캡션 규칙이 뚜렷하다.
  - **구조도 3장이 같은 캡션 틀**이다: "첫 번째 / 두 번째 / 세 번째 프로젝트 구조(아키텍처명)". 세 단계를 같은 시각 문법으로 비교하게 한다. 각 구조도는 모듈 정의 목록 직후에 놓인다.
  - **문제 그림**: 얽힌 레이어드 의존 관계, Adapter 모듈에 쌓인 구현 클래스 목록, 한 서비스 배포에 다른 서비스까지 배포되는 현상. 각각 문제를 문장으로 설명한 직후에 둔다.
  - **수치 그림**: 코드 라인 192% 증가 대비 빌드 시간·배포 횟수, PR·코드 리뷰 수. "효과" H3의 주장 바로 뒤에 둔다.
  - **외부 개념도**: 헥사고날·클린 아키텍처 원전 그림, 모노레포 소개 그림. 캡션이 URL뿐이다.
  - **회고 그림**: KPT 보드.
- **표·목록 사용.** 문제 정의는 번호 목록, 모듈 정의는 `모듈명: 역할` 불릿, 의존 규칙은 `A → B 만 의존` 불릿, 목표는 `이름: 설명` 불릿이다. 같은 종류의 정보에 늘 같은 목록 형식을 쓴다.
- **독자 수준 맞춤.** 아키텍처 이름은 한국어(원어)로 병기한다. Strangler Fig는 덩굴 비유로 풀고 원전 링크를 단다. 클린 아키텍처 핵심을 "의존성은 안쪽으로만"이라는 규칙 한 줄로 압축한다. 사내 명칭(Money 2.0)은 처음 쓸 때 정의한다.

### 잘한 점

1. **E-1·E-2, 도입 둘째 문단이 3단계 여정 전체를 예고한다.** 독자는 첫 화면에서 글의 끝을 안다.
2. **S, 단계마다 "왜 바꿨나 → 무엇을 포기했나"를 적는다.** 문제 3개를 번호로 정의하고, 규칙으로 버티는 대안이 왜 부족했는지 말한 뒤 선택한다.
3. **E-4·S, "단계 → 부작용" 교대 구조와 문제 번호의 고리.** 문제 1·2를 "목표"와 "적용 이후 1번"이 받아서 닫는다. 결정의 인과가 끊기지 않는다.
4. **M, 같은 캡션 틀의 구조도 3장.** 세 시점의 구조를 같은 문법으로 보여 줘 변화가 한눈에 비교된다. 문제 그림과 수치 그림은 해당 주장 바로 뒤에 둔다.
5. **F·M, 효과를 측정값으로 뒷받침한다.** 코드 192% 증가 대비 빌드 시간·배포 횟수, PR·리뷰 수를 그래프로 보여 준다.
6. **P·S, 회고와 한계 인정.** KPT 회고에서 남은 문제를 적고, 선택이 유효한 조건(현재 팀 규모)을 밝힌다.

### 아쉬운 점

- **위계·제목이 단계마다 다르다(E-5·E-6).** 첫째·둘째 단계는 H3 없이 문단으로만 쓰고, 셋째 단계만 목표·기본·모듈 구조 H3로 나눴다. "Hexagonal Architecture 적용 이후"라는 제목은 사실 문제 절인데 그 성격을 숨긴다("적용 이후의 문제"가 낫다). 외부 그림 캡션이 URL뿐이고, 이미지 대체 텍스트가 모두 비어 있다.
- **수치가 그림에만 있다(F).** 본문은 "2배 가까이"처럼 말하고, 정확한 빌드 시간·배포 횟수는 그래프 안에만 있다. 세 아키텍처를 한 번에 비교하는 요약 표도 없다(마지막에 단계 × 목표·구조·해결한 문제·남은 문제 표가 있으면 좋았다).

### 우리 모범 문서로 가져올 구조 패턴

1. **다단계 ADR(변천 기록) 뼈대: 지도 문단 → [단계 N: 계기 → 문제 번호 목록 → 대안의 한계 → 선택 이유 → 구조 정의 → 규칙 → 전환 방법 → 효과] → [단계 N 이후: 문제 1, 문제 2 …] → 반복 → 회고(KPT) → 남은 과제.**
2. **문제 번호를 문서 끝까지 들고 간다.** 문제 절에 붙인 번호를 다음 단계의 목표와 "적용 이후 1. 문제 X 해결"에서 다시 불러 고리를 닫는다.
3. **비교 대상 그림은 같은 캡션 틀로.** "N번째 구조(이름)"처럼 같은 틀을 쓰고, 같은 위치(정의 목록 직후)에 둔다.
4. **효과 H3는 "~할 수 있게 되었다" 평서문 + 바로 뒤 측정 그림.** 주장과 증거를 붙인다(우리 문서는 수치를 본문 문장에도 적는다).

## 4편 공통 구조 패턴

1. **도입부에서 "전체 지도"를 먼저 준다.** 형태는 다르지만 넷 다 첫 화면에 끝까지의 경로를 보여 준다. ES 불릿(1), 결론 요약 문단(2), 범위 예고 + 번호 목차(3), 3단계 여정 한 문단(4). → E-1, E-2
2. **요약을 앞과 뒤에 이중 배치하고, 둘을 대칭으로 맞춘다(북엔드).** 넷 다 결론 절이 도입의 요약을 다시 짚는다. 4는 인용으로, 1은 메시지로 대칭을 만든다. → E-2
3. **병렬 하위 단위는 같은 틀로 반복한다.** 문장형 "(N)" 소제목(1), `행동: 효과` H2 + 이유 문단 + 용어 불릿(2), 브리지 → H4 → 마무리 한 줄(3), 단계마다 같은 결정 단위(4). 독자는 두 번째 단위부터 구조를 예측한다. → E-5, E-6
4. **절과 절 사이에 이음매를 둔다.** 절 도입의 로드맵 문단(1, 3), 앞 내용 다시 부르기(1의 "앞서 설명한"), 절 끝의 다음 문제 예고와 번호 고리(4). 2는 이음매 대신 병렬 독립 섹션을 택했는데, 그래서 넷 중 흐름이 가장 약하다. → E-4
5. **권고 뒤에 한계를 둔다.** 한계 절(2), 회고 KPT(4), 주장 직후 경고(1). 3만 한계가 없고, 그래서 가장 설득력이 약하다. → P, S
6. **꼬리 블록을 정형화한다.** FAQ(1·2·3), 참고 자료(2), 남은 과제(4). FAQ는 본문을 되풀이할 때는 가치가 낮고, **본문에 없는 선택 기준이나 입문 질문**을 받을 때 가치가 있다(2의 Q3, 3의 측정 지표). → C, E-8
