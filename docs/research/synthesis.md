## A. 기술 문서의 목적

- 기술 문서는 **독자가 문제를 풀거나 목표를 이루도록** 정보를 **정확하고 빠르게** 전달하는 글이다. 감동이나 표현이 아니라 전달이 목적이다. [S1, S3, S4, S8] 합의 9
- 출발점은 **지식의 저주**다. 작성자는 독자도 자기 배경지식을 갖고 있다고 무심코 가정한다. 이 가정을 의심하는 것이 모든 원칙의 바탕이다. [S8, S7 "사전 경험을 가정하지 않는다", S3 2-6]
- 문서는 실제 결과를 낳는다. 잘못 쓴 문서는 오작동, 비용, 안전 사고, 법적 책임으로 이어진다. [S5 감전사 판례, S6 Tip 1]
- 좋은 문서의 핵심 속성(출처 공통분모): **명확성·간결성** [S1 3원칙, S11] **·일관성** [S1, S5, S6] + **정확성** [S4, S3 참조] + **훑어보기 쉬움** [S8, S10 F 패턴] + **문제 해결 지향** [S8].

## B. 작성 프로세스

출처들의 단계를 합치면 다음 순서가 된다. [S1 5단계, S10 11장, S6, S7, S2]

1. **계획** — 목적과 독자를 정한다. [S1, S6, S7, S10]
2. **유형 결정** — 독자의 목표로 문서 유형을 고른다. [S3, S9]
3. **구조(개요) 설계** — 쓰기 전에 아웃라인을 만든다. 브레인 덤프는 괜찮지만 반드시 개요로 정리한다. [S6 Tip 4, S1, S7]
4. **초안** — 내용을 빠짐없이 넣는 데 집중한다. 문장 다듬기는 뒤로 미룬다. [S1]
5. **코드 예제·시각 자료 추가** [S10 5·6장, S2]
6. **검토·재작성** — 가장 오래 걸리는 단계(전체의 약 40%). [S1] §O 참고
7. **배포** [S1, S10]
8. **피드백·유지보수** — §Q 참고 [S10, S7, S2]

## C. 독자 파악

- **가장 자주 빠뜨리는 단계**다. 쓰기 전에 반드시 정한다. [S6 Tip 2, S5 계명 1]
- 파악할 항목 [S8 절차, S4 2, S2 2.2]
  - **역할**: 개발자, PM, 운영자, 비개발자 등
  - **수준·선행 지식**: 보유 기술, 언어, 개발 환경
  - **목표**: 문서를 읽고 무엇을 하려는가(엔지니어링 목표 / 비즈니스 목표) [S8]
  - **질문 목록(니즈)**: 무엇인가, 어떤 문제를 푸는가, 어떻게 쓰는가 [S8]
  - **읽는 상황**: 시간·장소·업무 환경 [S4]
- **같은 독자도 상황마다 필요가 다르다.** 절차서는 "무엇을·어떻게", 교육 자료는 "왜"를 더 쓴다. [S6 Tip 3]
- 독자 수준별 작성 전략 [S2 2.2, S7 4.1, S6 Tip 3]

  | 독자 | 전략 |
  |---|---|
  | 초보자 | 용어를 설명하고 완전한 예시를 준다 |
  | 숙련 개발자 | 바로 핵심으로, 참조 링크 제공 |
  | 비기술자 | 비유, 구체적 사실은 주되 세부와 전문 용어는 피한다 [S6] |
  | 의사결정자(확장) | 영향·리스크·결정 사항 먼저 *(출처에 없는 확장, eli5 직무별 프레이밍과 맞춤)* |

- 압축 도구: **페르소나**(이름·숙련도·언어·환경·역할), 사용자 스토리, 여정 지도 [S8], 마찰 로그 [S8, S10]. → 스킬의 독자 config가 페르소나 역할을 한다.
- 검증 방법: 대상 독자와 같은 사람을 리뷰어로 삼는다. [S4 10-5]

## D. 문서 유형과 템플릿

- **독자의 목표**로 유형을 정한다. 유형마다 정해진 구조가 있다. [S3, S9] 다른 출처들도 유형별 구조를 제시한다. [S2 README/API/아키텍처/변경 이력, S7 소개→설치→사용→FAQ→문제 해결]
- 기본 축: 4유형 [S3]

  | 유형 | 독자 목표 | 필수 요소 |
  |---|---|---|
  | 학습(튜토리얼·시작하기) | 처음 배우기 | 학습 목표, 사전 요구사항, 단계, **실행되는 예제**, 결과 확인 |
  | 문제 해결(How-to·트러블슈팅) | 특정 작업·문제 해결 | 문제 정의(원인/현상 구분, 에러 메시지), 즉시 적용 가능한 해결책, 원리, 환경별 차이, 해결 확인 |
  | 참조(API·에러 코드) | 정확한 사실 빠르게 찾기 | 개요, 일관된 구조(시그니처→매개변수→반환값→예제), 검색·앵커, 사전 정보(인증 등) 앞쪽 |
  | 설명(개념·설계 철학) | 깊이 이해 | 한 줄 정의, 등장 배경(문제), 원리, 대안 비교, **시각 자료**, 활용 |

- 유형은 **결합**할 수 있다. [S3]
- 실무 문서 매핑(사용자 요청 범위): 설계 문서·ADR → 설명형(+결정 기록), 런북·트러블슈팅 → 문제 해결형, 장애 보고서 → 설명형+타임라인. *(이 매핑은 출처에 없는 확장이다. 출처 근거는 S2 아키텍처 문서 구조: 시스템 개요 → 다이어그램 → 기술 선택(대안 비교) → 배포.)*
- 여러 페이지 문서는 왼쪽 내비게이션을 짜듯 유형별 디렉터리로 나누고 크로스링크로 잇는다. [S3 4-3]

## E. 정보 구조

1. **개요를 맨 앞에.** 제목 바로 아래 1~2문장으로 "이 문서를 읽으면 무엇을 할 수 있는가"에 답한다. [S3 2-4, S11 개요 1~2문장+구분자, S2 README 한 줄 설명]
2. **중요한 것 먼저(역피라미드).** 배경·연혁보다 독자가 얻을 가치와 결론을 먼저 둔다. 독자는 F 패턴으로 훑는다. [S1 4.1, S3 2-2, S10 3장, S7 4] (S6은 이를 세 전개 방식 중 하나로 제시)
3. **한 문서 한 주제.** 제목 위계가 H4(`####`) 이상으로 깊어지면 문서 분리를 **고려**한다(H3까지는 유지 가능). 넓은 주제는 개요 페이지에서 하위 문서로 연결한다. [S3 2-1, S9]
4. **전개 방식을 독자에 맞게 고른다.** 시간순 / 중요도순 / 단계순. [S6 Tip 4] 설명형은 핵심 개념 → 사용법 → 예제 → 심화. [S3 2-5]
5. **제목** [S1 체크리스트, S3 2-3, S10 3장]
   - 제목만 봐도 내용·목적을 알 수 있다. 핵심 키워드를 넣는다.
   - 30자 이내, 평서문(`?`·`!` 없음). [S3]
   - 명사만 나열하지 않는다. 비표준 약어를 쓰지 않는다. [S1]
   - 같은 수준 제목은 같은 형태(예: 모두 "~하기"). [S3]
6. **예측 가능하게.** 같은 수준은 같은 위계, 섹션 이름·순서를 문서 간에 통일, **설명 → 코드** 순서. [S3 2-5]
7. **훑어볼 수 있게.** 목차, 설명적 제목 [S8, S7 4.3, S11 목차], 앵커 링크 [S3 1-3].
8. **필요한 정보는 빠짐없이.** 새 개념은 한두 문장으로 정의하고, 동작 조건·단위·상태별 차이를 적는다. [S3 2-6] 독자가 궁금해할 정보를 **선택해서** 준다. [S4 2]
9. **문단은 짧게, 소주제별로.** [S5 계명 9]

## F. 명확성·구체성

- 한 번 읽고 이해되어야 한다. 다시 읽게 만들면 명확성이 부족하다. [S11 1.1]
- **단정적으로 쓴다.** "~듯합니다", "~로 볼 수 있다" 대신 확정 표현. [S1 4.2] 모호 표현("가능성이 있다", "일부 경우") 대신 실제 대상을 쓴다. [S3 3-3]
- **구체적 수치·기준**을 쓴다. "많으면" → "10,000건을 넘으면". [S3 3-3, S5 계명 4]
- **누가·무엇을·어디에·어떻게**를 드러낸다. [S3 3-3]
- **대명사("여기", "이")를 구체 명사로.** 링크 텍스트도 마찬가지. [S1 4.5, S3 참조 맥락]
- 모호한 설명 대신 구체적 설명: "데이터를 처리합니다" → "주문 데이터를 청구서 형식으로 변환합니다". [S2 2.1]
- **이중 부정을 피하고 긍정문으로.** [S11]
- 앞뒤로 참조되는 값은 출처와 사용처를 밝힌다. [S3 3-3]

## G. 간결성

- **한 문장에 한 생각.** 호흡이 불편한 긴 문장은 나눈다. [S3 3-2, S4 10-3, S11 정의는 한 줄+부연은 다음 문장] 단, 모든 문장을 단문으로 만들지는 않는다. → §R-8
- **메타 담화를 뺀다**("앞서 설명했듯이", "아시다시피", "결론적으로"). [S3 3-2]
- **중복·군더더기를 뺀다**("성공적으로 전송했습니다" → "전송했습니다", "계속 유지" → "유지"). [S1 5.2, S11 1.2, S5 계명 5, S4 10-8]
- 꾸밈말보다 명사·동사. 거창한 단어 대신 평범한 단어. [S5 계명 7, S4 4]
- 필요한 정보만 고른다(TMI 금지). 단, E-8과 충돌하지 않게 "독자에게 필요한가"가 기준이다. [S5 계명 2, S4 2] → §R-5

## H. 일관성·용어

- **한 개념 = 한 용어.** 스토리지/저장소, 추가/첨부/넣다를 섞지 않는다. [S1 6.1, S3 3-5, S6 Tip 5]
- 숫자, 하이픈, 구두점, 대소문자, 어미, 상세 수준을 문서 전체에서 맞춘다. [S5 계명 6, S6 Tip 5]
- **용어집(glossary)** 을 두고 지킨다. [S3 2-5, S7 4.4, S3 4-3 glossary.md]
- 공식 표기를 따른다(Kubernetes, iPhone, Windows 10). 고유 명사를 줄이거나 임의로 한글화하지 않는다. [S1 4.5, S3 3-5]
- 목록 항목의 문법 형태를 통일한다. [S1 6.2, S11 불릿]
- 지시문(절차)은 같은 형식으로 쓴다. [S6 Tip 5]

## I. 전문 용어·약어

- 전문 용어는 **독자 수준에 맞춰** 쓰고, 꼭 필요하면 본문에서 설명한다. 같은 업계 독자에게는 업계 용어를 써도 된다. [S4 9, S5 계명 3, S1 5.1, S6 Tip 3]
- **약어는 처음 나올 때 풀어 쓴다.** `SSR(Server-Side Rendering)`, `클라이언트 사이드 렌더링(Client-Side Rendering, CSR)`. 이후에는 약어만. [S3 3-5, S4 8, S1 5.1]
- 은어·직역("던진다", "찌른다", "뜨다", "깨지다") 대신 실제 동작을 쓴다. [S3 3-3, S1 4.4]

## J. 능동·주체

- **독자를 행동의 주체로.** "이 라이브러리는 초기화를 수행해요" → "이 명령어를 실행하면 초기화할 수 있어요". [S3 3-1]
- 능동형을 기본으로. [S1, S3, S5 계명 8, S7 4.4, S2 프롬프트]
- 예외: 도구·시스템의 동작 자체를 설명할 때는 도구가 주체가 될 수 있다. [S3 3-1] 기기·소프트웨어 주체면 피동 허용. [S4 5] → §R-2

## K. 한국어 문장 (→ korean-proofreader에 위임)

출처 공통: 번역투("~에 의해", "~를 통해", "~에 대해", "가지고 있다"), 이중 피동("보여지다"), 명사화("진행/수행/처리/실시"), 불필요한 "~적/~의/~들", "~해 주다/해 놓다". [S1 4.3, S3 3-4, S4 6, S9]

> 이 층위는 korean-proofreader의 sentence 기준과 겹친다. 스킬에서는 **기술 문서 특화 규칙(J, I, H, F의 수치·주체)만 직접 적용**하고, 일반 한국어 문장 교정은 proofreader 단계에 맡긴다.

## L. 포매팅

- **번호 목록 = 순서가 있는 절차, 글머리 기호 = 순서 없는 대등 항목.** [S1 5.3]
- 절차는 **한 단계에 한 동작**, 분기는 단계로 나눈다. UI 요소 이름은 정확히 표기한다. [S7 5.2]
- 목록은 필요한 곳에만 쓴다. 기본은 문장, 여러 단계 중첩은 피한다. [S11 불릿]
- **표**: 항목·속성 비교, 매개변수(이름·타입·필수·기본값·설명). [S11, S2 API, S3 참조 템플릿]
- **코드 블록에는 언어를 지정**하고 설명 다음에 둔다. [S3 1-1 개선 포인트, S3 2-5]
- **강조 패널(경고·주의)** 은 절제해서 쓴다. [S11 패널] 위험한 작업의 경고는 눈에 띄게 둔다. [S5 판례]
- 헤딩은 내용 구조에 맞게 H1~H3. [S11, S3 H4 규칙]
- 시각 자료가 많으면(5개 이상) 캡션을 단다. 그림은 아래, 표는 위. [S1 5.3]
- 대문자로만 쓴 문장은 읽기 어렵다. [S10 6장]
- 문장부호 규칙(쌍점, 따옴표, 괄호 병기). [S1 6.3]
- 긴 부가 정보는 접기나 문서 끝 FAQ로 뺀다. [S3 1-1 더 나아가기]

## M. 시각화

- 글보다 그림·도표가 기억에 오래 남는다. 복잡한 구조, 흐름, 관계는 시각화한다. [S5 계명 10, S11 UML, S3 1-4, S7 3.3]
- **언제 쓰나**(출처 공통분모)
  - 전체 구조·컴포넌트 관계 → 아키텍처/배치 다이어그램 [S2, S11]
  - 시간 순서 상호작용 → 시퀀스 다이어그램 [S11]
  - 데이터 흐름·처리 단계 → 흐름도 [S3 1-4, S3 도메인 흐름도]
  - 클래스·데이터 모델 → 클래스 다이어그램/ERD [S11]
  - 비교·속성 나열 → 표 [S1, S11]
- 설명형 문서에서 시각화는 **필수 요소**다. [S3 1-4 체크리스트]
- 다이어그램은 텍스트를 대체하지 않고 **보완**한다. 앞뒤에 무엇을 보여 주는지 한 문장으로 쓴다. [S3 1-4 "다음 다이어그램은 …을 나타내요" 예시]
- 스크린숏은 환경(OS·프로그램)과 크기를 통일한다. [S1 6.2]

## N. 코드 예제

- **실행 가능한 예제가 최고의 문서**다. 입력과 **반환값/출력**까지 보여 준다. [S2 2.3, S3 1-1]
- 모든 예제는 실제로 실행해 검증한다. 학습 문서는 막힘없이 끝까지 따라 할 수 있어야 한다. [S3 1-1, S4 10-6]
- 간단한 것에서 점진적으로 어렵게. [S3 1-1]
- 성공 판정 기준을 쓴다("…가 보이면 정상"). [S3 1-1 개선 포인트]
- 오류 처리·잘못된 예(Don't)를 함께 보여 주면 이해가 빠르다. [S3 Hydration 예시, S2]
- AI가 만든 예제·API 설명은 실제 코드와 대조한다. 존재하지 않는 매개변수를 지어낼 수 있다. [S2 5]

## O. 검토·퇴고

- 검토는 전체 작성 시간의 약 40%를 차지하는 핵심 단계다. [S1]
- **자기 검토** [S4 10, S6 Tip 5]
  - 시간을 두고 다시 읽는다. 매체를 바꿔(게시 후 실제 화면에서) 읽는다. 소리 내 읽는다.
  - 독자 입장에서 한 번에 이해되는지 본다.
  - 어조·상세 수준·용어·지시문 형식이 일관된지 본다.
- **사실 검증**: 기능이 글대로 동작하는지 직접 테스트, 메뉴·화면 이름 대조, 참고 자료 교차 확인. [S4 10-6, S4 3]
- **동료 검토**: 대상 독자와 같은 사람에게 맡긴다. 리뷰어에게 내용을 **요약해서 되말하게** 해 의도가 전달됐는지 확인한다. [S4 10-5, S6 Tip 5]
- 리뷰는 코드 리뷰 도구(PR, diff, 인라인 코멘트)로 한다. 지적에는 제안을 붙인다. [S10 4장, S2 4.1]
- 체크리스트 기반 점검. [S3, S4]

## P. 정확성·안전

- 바르고 확실한 정보만 쓴다. 퇴고 때 교차 확인한다. [S4 3]
- 참조 문서는 누락·오류·모호함이 없어야 하고 항상 최신이어야 한다. [S3 1-3]
- 위험한 작업(데이터 삭제, 운영 반영, 안전 관련)은 경고를 충분히 강조한다. [S5, S6 Tip 1]
- 예외 상황(오류, 재고 부족 등)을 함께 쓴다. [S3 도메인 예시] 오류 응답·예외 조건(@throws)을 빠뜨리지 않는다. [S2 3.0, 3.0-b]

## Q. 유지보수

- **Docs as Code**: 문서를 코드와 같은 저장소·PR로 관리하고, CI로 형식과 링크를 검사한다. [S2 4.1, S10 4·7장]
- 단일 정보 출처(SSOT)를 두고 나머지는 링크한다. 담당자를 지정한다. [S2 4.2]
- 기능 변경을 제때 반영한다. 쓰지 않는 기능은 **deprecated로 표시**한다. [S4 3, S7 6, S10 11장, S1 5단계]
- 피드백 채널(만족도 조사 등)을 둔다. 유효한 피드백은 문서와 관련 있는 피드백이다. [S10 8장, S7 6]

## S. 왜와 결정 맥락을 기록한다

- 코드는 "어떻게"를, 문서는 "왜"를 알려 준다. 무엇을 했는지만이 아니라 **왜 그렇게 결정했는지**를 남긴다. [S2 §0 의사결정 맥락 보존]
- 설명형 문서의 핵심은 배경과 맥락, 의사결정 과정의 공유다. [S3 1-4]
- 독자가 "왜"를 알아야 하는 상황(교육, 설계 이해)에서는 원리를 더 쓴다. [S6 Tip 3]
- 주석도 "무엇"보다 "왜". [S2 3.2]
- 대안과 비교해 선택 이유를 쓴다. [S2 아키텍처 문서 "기술 선택", S3 설명 문서 프롬프트 "다른 접근 방식과의 비교"]
- → 설계 문서·ADR·장애 보고서 템플릿의 근거.

## T. 매체·형식 선택

- 매체에 맞춰 형식을 고른다: 개발자·리포 문서는 Markdown, 공식·오프라인은 PDF, 검색·협업은 위키(Confluence 등). [S7 4.2]
- 위키에서는 그 도구의 양식을 따른다(개요+구분자, 자동 목차, 패널). [S11]
- 시작하기(Getting Started) 진입점을 개념 소개 옆에 둔다. [S10 7장, S3 시작하기 vs 튜토리얼, S2 빠른 시작]
- 학습 문서 끝에 다음 단계를 안내한다. [S3 부록 tutorial 예시 "다음 단계"]
