# 한국어 기술 문서 본보기 후보 (A: 학습·How-to·트러블슈팅·참조)

- 조사일: 2026-10-15. 모든 후보는 본문을 직접 받아 읽었다(curl HTML 추출 또는 사이트가 제공하는 `.md` 원문).
- 원칙 ID는 `synthesis.md` 기준(D 유형별 필수 요소, E 정보 구조, F·G·J 문장, L 포매팅, M 시각화, N 코드 예제).
- 인용은 20자 이내만 썼다. 원문은 스킬에 넣지 않는다. 구조와 패턴을 분석해 근거로만 쓴다.
- 원작 표기: **원작** = 한국어로 처음 작성. **병행** = 같은 팀이 한·영을 함께 운영하며 어느 쪽이 1차인지 판별 불가.

## 1. 학습 문서(튜토리얼·시작하기)

### 1-1. 주문서형 결제 연동하기 — 토스페이먼츠 개발자센터

- URL: https://docs.tosspayments.com/guides/v2/payment-widget/integration (원문 `.md`도 같은 경로)
- 출처: 토스페이먼츠 / 유형: 학습(연동 튜토리얼) + 단계별 트러블슈팅 결합 / 원작 한국어
- **점수: 4/5.** 도입부, 단계 구조, 단계별 FAQ·에러 패널, 성공·실패 응답 확인까지 갖췄다. 다만 핵심 코드(초기화·렌더·승인 API)는 언어를 고르는 인터랙티브 코드 패널에만 있다. HTML·`.md` 어디에서도 그 코드를 확인할 수 없어 D·N의 "실행되는 예제"는 검증하지 못했다. 그래서 5점에서 1점을 뺐다.
- 잘한 점
  1. **E-1·D(학습 목표)**: 제목 바로 아래 한 문단에서 제품 정의, 얻는 것("노코드로 결제수단 설정…"), 시작 행동을 말한다. 이어서 "연동은 네 단계로 진행돼요"와 번호 목록 4개로 전체 지도를 먼저 보여 준다.
  2. **D(사전 요구사항)**: 본문에 들어가기 전에 API 키를 어디서 확인하고 코드의 어느 자리(`{WIDGET_CLIENT_KEY}`)에 넣는지 알려 준다. 회원이 아닐 때 갈 경로도 적었다.
  3. **E-6·L(단계 레이블)**: 각 단계에 번호와 Client/Server 배지를 붙였다. 독자는 지금 어느 쪽 코드를 쓰는지 바로 안다. 단계 제목은 모두 동사형("결제 요청하기", "결제 승인 API 호출하기")으로 형태가 같다.
  4. **D(결과 확인)·N**: 마지막 단계가 "결제 승인 결과 확인하기"다. 성공 응답(HTTP `200 OK`와 Payment 객체)과 실패 응답(4XX·5XX와 에러 객체)을 나눠 설명하고, 저장해야 할 필드(`paymentKey`, `orderId`)도 정해 준다.
  5. **D(유형 결합)·E-8**: 단계 바로 아래에 접이식 FAQ("결제 UI가 렌더링되지 않아요")를 둔다. 그 단계에서 나올 수 있는 에러는 오류원인 → 해결 방법 패널로 붙였다. 학습 흐름을 끊지 않으면서 막히는 지점을 바로 잡아 준다. → 트러블슈팅 패턴으로 3장에서 다시 다룬다.
  6. **M**: 결제 흐름을 mermaid 흐름도(그리기 → 요청·인증 → 승인 → 성공/실패)로 그렸다. 리다이렉트가 왜 생기는지는 그림 앞뒤 문장으로 설명한다.
- 아쉬운 점
  - 단계를 마크다운 헤딩이 아니라 커스텀 컴포넌트로 만들어서 원문에 H2·H3가 없다. 앵커 링크와 목차를 만들 수 없다(E-7).
  - 핵심 코드가 인터랙티브 패널에만 있어 문서만으로는 따라 할 수 없다. 정적 문서로 옮길 때는 단계마다 코드 블록을 본문에 넣어야 한다(N, L 코드 블록 언어 지정).
- 골격(헤딩이 없어 시각 구조로 기록)
  ```
  # 주문서형 결제 연동하기
    (도입 1문단 + "연동은 네 단계" 번호 목록 + 결제수단 이미지 + API 키 안내 + 흐름 이미지)
    [1 · Client] 주문서형 결제 렌더하기 — SDK 설치 / 인스턴스 생성 / 결제 금액 설정 / 결제 영역 정의 / 결제 UI 렌더링 / 이용약관 UI 렌더링 / (선택) 기타 결제 UI
    [2 · Client] 결제 요청하기 — 결제 버튼 이벤트 설정 / 결제창 띄우기 (+mermaid 흐름도)
    [3 · Client] 리다이렉트 URL로 이동하기 — successUrl / failUrl (+트러블슈팅 패널 3개)
    [4 · Server] 결제 승인 API 호출하기 — Basic 인증 헤더 / 승인 API 호출
    [5 · Server] 결제 승인 결과 확인하기 — 성공 응답 / 실패 응답 (+트러블슈팅 패널 4개)
    다음 단계
  ```

### 1-2. React Native 시작하기 — 앱인토스 개발자센터

- URL: https://developers-apps-in-toss.toss.im/ai-vibe-coding/tutorials/react-native (`.md` 제공)
- 출처: 토스 앱인토스 / 유형: 학습(시작하기) / 원작 한국어
- **점수: 4/5.** 프로젝트 생성부터 출시까지 끊김 없이 따라갈 수 있는 단계와 명령어가 있고, 단계마다 성공 판정 기준이 있다. 학습 목표 문장이 없고 헤딩 위계가 깊다.
- 잘한 점
  1. **C·D(대상 독자)**: 도입부에서 이 방식이 맞는 팀을 체크리스트 3개("복잡한 애니메이션이나…")로 보여 준다. 맞지 않는 독자는 "WebView 시작하기"로 보낸다. 독자가 스스로 이 문서를 읽을지 판단할 수 있다.
  2. **L·E-5**: 단계 헤딩이 "1. 프로젝트 만들기 … 9. 출시하기"처럼 모두 번호 + "~하기" 형태다(E-5 같은 수준 같은 형태). 하위 단계도 1-1, 1-2로 번호를 이어 붙였다.
  3. **N(성공 판정)**: 실행 단계마다 성공 기준이 있다. 예를 들어 `Bundling {n}%...` 표시를 "연결이 성공한 거예요"의 신호로 삼아, 화면에서 확인할 것을 적었다.
  4. **L(경고 패널)·P**: 버전 호환성 경고("반드시 `1.x` 버전")를 명령어 바로 아래 warning 패널에 둔다. 흔한 에러("too many open files")는 그 단계 안에 info 패널로 해결 명령과 함께 넣었다.
  5. **N·L**: 모든 명령에 npm·pnpm·yarn 탭을 둔다. 설정 파일 예제의 주석은 "콘솔에서 등록한 앱 이름으로 바꿔주세요"처럼 독자가 바꿀 값을 직접 가리킨다.
- 아쉬운 점
  - "이 문서를 마치면 무엇을 만들 수 있나" 같은 학습 목표 한 문장이 없다(D 학습 목표, E-1).
  - "6. 미니앱 실행하기" 안에 H4와 H1("연결 끊기")이 섞여 위계가 흐트러진다(E-3, L 헤딩 규칙). 7단계 "디버깅하기"는 따로 문서를 분리해도 될 만큼 길다.
- 골격
  ```
  # React Native 시작하기
    (info: 처음이라면 → AI로 미니앱 만들기 / 적합한 팀 체크리스트 / WebView 링크)
  ### 1. 프로젝트 만들기

### 1-3. 시작하기 — use-funnel (토스 오픈소스)

- URL: https://use-funnel.slash.page/ko/docs/get-started
- 출처: Toss Slash / 유형: 학습(라이브러리 시작하기) / **병행**(한·영 문서 동시 운영, 원작 판별 불가)
- **점수: 4/5.** 회원가입 퍼널이라는 구체적인 예제 하나를 따라가며 핵심 API 3개를 차례로 익힌다. 다만 예제의 UI 컴포넌트를 `declare`로만 선언해서 그대로 실행되지 않는다.
- 잘한 점
  1. **E-1·D(학습 목표)**: 첫 두 문장에 무엇을 만들고("간단한 회원가입 흐름") 무엇을 배우는지("단계별로 상태를 안전하게 관리")를 적었다.
  2. **N(점진적 난이도)**: 단계별 타입 정의 → 초기 단계 설정 → context·history 사용 → 편의 컴포넌트(`<funnel.Render />`) 순서다. 앞 단계의 타입을 다음 단계 코드에서 그대로 쓴다.
  3. **E-6(설명 → 코드)·N**: 코드 블록마다 바로 뒤에 요소별 글머리 설명이 붙는다. 코드 주석이 타입 추론 결과("undefined가 아니에요!")를 짚어 준다.
  4. **D(환경별 차이)·L**: 라우터마다(Next.js app/page router, react-router 등) 코드 탭을 둔다. 브라우저 히스토리 기반 패키지에는 SSR 주의 패널과 회피 코드를 함께 준다.
  5. **J**: "~해 볼게요", "~할 수 있어요"처럼 독자를 주어로 삼는 해요체를 처음부터 끝까지 지킨다.
- 아쉬운 점
  - 결과 확인 단계(예: 이메일 입력 후 비밀번호 화면으로 넘어가는지 확인)가 없다. 예제가 `declare` 스텁이라 독자가 실행해 볼 수 없다(N 실행 가능·성공 판정).
  - Next.js용 탭 4개에 같은 코드가 반복되어 탭의 의미가 흐려진다(원문 렌더링 문제일 수 있음).
- 골격
  ```
  # 시작하기
  ### step 별 context 정의하기
  ### 초기 단계 설정하기
  ### 단계별 context와 history 사용하기
  #### 참고: `<funnel.Render />` 컴포넌트를 사용해 쉽게 구현하기
  ```

### 1-4. 회원가입, 사업자번호 없이 결제 테스트하기 — 토스페이먼츠 블로그

- URL: https://docs.tosspayments.com/blog/how-to-test-toss-payments
- 출처: 토스페이먼츠 개발자센터 블로그 / 유형: 학습(입문 안내) / 원작 한국어
- **점수: 3/5.** 입문자의 첫 질문("계약 전에 테스트할 수 있나")에 답하는 진입 문서다. 따라 하는 단계보다 선택지 안내가 중심이라 튜토리얼 본보기로는 약하다. 비교용으로 남긴다.
- 잘한 점
  1. **E-2**: 도입 첫 문장이 독자가 가장 궁금한 결론("회원가입이나 사업자 등록 없이도…")이다.
  2. **I·E-8**: 본론 전에 "테스트 환경이란?"을 두 문장으로 정의하고 안심시킨다(가상 결제라 출금 없음).
  3. **D(난이도별 경로)**: SDK와 API 테스트 각각에 샌드박스(코드 0줄) → 샘플 프로젝트 → 내 프로젝트의 세 갈래를 쉬운 순서로 준다.
  4. **L(FAQ로 빼기)**: 결제수단별 예외(카카오페이·네이버페이·PayPal)는 본문 뒤 FAQ로 모았다.
- 아쉬운 점
  - 단계·코드·결과 확인이 없어서 튜토리얼이라기보다 안내 글이다(D 학습 필수 요소 대부분 부재).
  - "테스트 환경이란?"과 "테스트 연동을 시작하기"가 헤딩이 아니라 굵은 글씨라 목차에 안 잡힌다(E-7).
- 골격

  ## SDK 테스트하는 방법
  ## API 테스트하는 방법
  ## 자주 묻는 질문
  ```

## 2. How-to 가이드(특정 작업 수행)

### 2-1. 장애 인지 가이드 — 토스페이먼츠 개발자센터

- URL: https://docs.tosspayments.com/guides/v2/status-page
- 출처: 토스페이먼츠 / 유형: How-to / 원작 한국어
- **점수: 5/5.** 목적 → 설정 → 데이터 이해 → 상황별 대응 코드 → 전체 예시 → FAQ 순서가 독자의 작업 순서와 같다. 보안 경고와 수치 기준이 정확하다.
- 잘한 점
  1. **E-1·E-2**: 첫 문단에서 이 가이드로 할 수 있는 일을 말하고, 자동화할 수 있는 대응 3가지(구매자 안내, 내부 알림, 빌링 배치 시간 변경)를 굵은 레이블 목록으로 먼저 보여 준다. 이어서 에러 코드만으로는 장애를 구분하기 어렵다는 **왜**(S)를 한 문단으로 덧붙인다.
  2. **E-5·J**: H2 4개가 모두 번호와 명령형 동사다("1. … 구독하세요", "3. 장애를 감지하고 대응하세요"). 제목만 읽어도 작업 순서가 보인다.
  3. **F(구체 수치)·P(안전)**: "30초 안에 2xx 응답"처럼 기준을 숫자로 적는다. 경고 패널은 서명 헤더와 고정 IP가 없다는 사실을 밝히고, 대응책(HTTPS만 허용, 추측하기 어려운 경로, 자동화 전 값 검증)을 구체적으로 준다.
  4. **L(표)·N**: Component ID와 이름, status 값과 의미를 표로 정리했다. JSON 예시는 `// ← 변경된 상태` 같은 화살표 주석으로 핵심 필드만 짚고 나머지는 "생략"으로 줄였다.
  5. **D(상황별 해결)·N**: "원천사 장애"와 "결제 시스템 장애"를 H3로 나누고, 각각 판별 코드(`title="원천사 장애 감지"`)와 본문 템플릿을 준다. 자주 받는 질문(예정 점검 미리 알기 등)은 끝의 FAQ로 뺐다(L 긴 부가 정보는 FAQ로).
- 아쉬운 점
  - 구독이 제대로 됐는지 확인하는 단계가 약하다. 테스트 웹훅이 오지 않으니 샘플로 직접 검증하라고만 하고, 검증 명령(예: curl로 샘플 POST)은 주지 않는다(D 해결 확인).
- 골격
  ```
  # 장애 인지 가이드
  ## 1. Status Page에서 웹훅을 구독하세요
  ## 2. 웹훅 Payload를 이해하세요
  ### Component Update
  ### Incident Update
  ## 3. 장애를 감지하고 대응하세요
  ### 원천사(카드사·은행) 장애
  ### 토스페이먼츠 결제 시스템 장애
  ## 4. Payload 예시
  ## 자주 묻는 질문
  ```

  1. **E-1·I**: 제목 아래 한 문장으로 언제 무엇을 받는지 말하고, 다음 문장에서 "웹훅"을 정의하며 용어집으로 링크한다.

### 2-4. TLS 1.2로 업그레이드하는 방법 — 토스페이먼츠 블로그

- URL: https://docs.tosspayments.com/blog/how-to-raise-tls-version
- 출처: 토스페이먼츠 개발자센터 블로그 / 유형: How-to(마이그레이션) / 원작 한국어
- **점수: 3/5.** 환경별 지원 표는 좋은 본보기다. 그러나 확인 방법, 코드 블록 언어, 완료 판정이 부실해서 비교용으로 남긴다.
- 잘한 점

- 아쉬운 점
  - 서버의 현재 TLS 버전을 확인하는 방법(명령·도구)과 전환 후 검증 방법이 없다(D 해결 확인, N 성공 판정).

  ### JSP

## 3. 트러블슈팅(오류 진단·해결)

트러블슈팅 후보는 두 종류로 나눴다. **(a) 문서형**은 증상별로 원인과 조치를 찾아보는 문서이고, 스킬이 쓸 모범 문서는 이쪽에 가깝다. **(b) 회고형**은 진단 과정을 서사로 풀어 쓴 기술 블로그 글이다. 가설 세우기, 교차 검증, 진단 순서를 서술하는 패턴을 참고할 때만 쓴다.

> **유형 공통 공백**: 이번에 읽은 문서형 후보(카카오, NHN Cloud, 토스 CORS)는 모두 현상 → 원인 → 조치에서 끝난다. D 표의 "해결 확인"("이렇게 하면 해결된 것")을 갖춘 문서는 찾지 못했다. 토스 주문서형 연동 문서(1-1)의 인라인 패널도 마찬가지다. 모범 문서를 쓸 때는 이 지점을 채워야 한다.

> **교차 참조(결합 패턴)**: 1-1 토스 주문서형 연동 문서는 각 단계 아래에 `트러블슈팅 · 에러코드` 패널을 붙인다. 패널은 **오류원인 → 해결 방법** 두 칸 구조다. 해결 방법은 확인할 항목을 글머리 목록으로 나열하고, 숫자 기준(예: 결제 요청 후 10분 안에 승인)을 넣는다. 튜토리얼 안에 트러블슈팅을 결합하는 본보기다(D 유형 결합).

### 3-1. FAQ › 문제 해결 — 카카오 developers (카카오 로그인)

- URL: https://developers.kakao.com/docs/latest/ko/kakaologin/faq (H2 "문제 해결" 섹션)

- **점수: 4/5.** 독자가 겪는 현상이나 에러 메시지를 그대로 제목으로 삼았다. "정상 동작"과 "고칠 문제"를 구분하고, 원인 후보를 분류해 준다. 해결 확인 단계와 일관된 하위 구조가 없다.

  4. **L·H**: 콘솔 메뉴 경로를 "[앱] > [플랫폼 키]"처럼 대괄호와 `>`로 일관되게 적는다(L UI 요소 정확히 표기).
  5. **D(환경별 차이)**: 웹 브라우저와 네이티브 앱, REST API와 SDK를 나눠 원인과 조치가 어떻게 다른지 쓴다.
- 아쉬운 점
  - 항목마다 구조가 다르다. 원인/해결 소제목을 단 곳은 한 항목뿐이고 나머지는 문단이다(E-6 예측 가능성). 해결 확인 기준이 없다.
  - "가능성이 높습니다", "~일 수 있습니다" 같은 유보 표현이 몇 군데 있다(F 단정).

- **점수: 3.5/5.** 원리 설명과 표, 그림이 훌륭하다. 하지만 정작 이 제품에서 생기는 CORS 에러의 원인과 조치는 글 마지막 H3에 있다. 트러블슈팅 문서로 보면 E-2(중요한 것 먼저)를 어긴다.
- 잘한 점
  1. **D(문제 정의)·M**: 첫 화면에 콘솔 에러 캡처를 보여 주고 "이런 에러를 만나본 적 있으시죠?"로 시작한다. 독자가 자기 증상과 맞춰 볼 수 있다.
  2. **M·L(표)**: SOP 판정 표(URL × 허용 여부 × 이유 6행)가 "출처가 다르다"는 개념을 예시로 보여 준다. 각 행에 왜 다른지(프로토콜/도메인/포트)를 적었다.
  3. **D(즉시 적용 해결책)·N**: 일반 해결책 두 가지(응답 헤더 설정, 프락시)를 H4로 나눴다. 헤더 설정에서는 `*`이 위험하다는 이유와 권장 형태를 함께 준다.
  4. **D(환경별 차이)**: 제품 사례에서 localhost:8080과 운영 도메인의 차이를 프로토콜·호스트·포트 세 항목으로 짚는다. 1차 조치가 안 될 때 2차로 확인할 것(iframe, `windowTarget`)도 이어서 준다.
- 아쉬운 점
  - 제품 사례가 맨 뒤에 있다. 트러블슈팅이라면 "결제창에서 CORS가 나면: 원인 → 조치"를 먼저 두고 원리를 뒤로 보내야 한다(E-2).
  - 해결 확인 기준이 없고, 코드 블록 언어가 `plain`이다(D, L).
- 골격
  ```
  # 결제창에서 CORS 대응하기
  ### 이 에러, 대체 왜 발생하나요?
  ### 웹의 발달과 CORS
  ### '출처가 교차한다'?
  ### CORS 에러 대응하기
  #### 서버에서 `Access-Control-Allow-Origin` 응답 헤더 세팅하기
  #### 프락시 서버 사용하기
  ### 예제: 토스페이먼츠 결제창에서 CORS 에러를 만났을 때
  ```

### 3-4. R2DBC Connection Pool 실종 사건 — 카카오페이 기술 블로그

- URL: https://tech.kakaopay.com/post/r2dbc-connection-pool-missing/
- 출처: 카카오페이 / 유형: 트러블슈팅(b, 회고형) / 원작 한국어
- **점수: 4/5(회고형 기준).** 요약, 재현, 가설, 코드 추적, 해결, 교차 검증, 회고가 모두 있다. 진단 과정을 쓰는 본보기로 가장 완성도가 높다. 문서형 본보기로는 쓰지 않는다.
- 잘한 점
  1. **E-1·E-2**: 맨 위 "요약" 한 문단에 문제, 원인, 해결(명시적 warmup), 교훈을 모두 담았다. 바쁜 독자는 여기서 멈춰도 된다.
  2. **D(원인/현상 구분)·F**: 재현 조건을 실행 환경별로 나눠 적는다(IntelliJ 실행 vs jar 실행). `lsof -i`, netstat 결과 같은 관찰 근거를 붙인다.
  3. **M**: "기대 vs 현실" 흐름도로 시작해, 해결 뒤 "기본 동작 vs 웜업 사용" 흐름도로 갱신한다. 문제와 해결을 같은 그림 틀로 비교한다.
  4. **D(원리)·N**: 라이브러리 생성자부터 `drainLoop`까지 호출을 따라가며 코드마다 한국어 주석을 단다. HikariCP와 대조해 차이가 어디서 오는지 보여 준다.
  5. **O·F(가설 검증)**: 의문("왜 IntelliJ에서는 정상인가")을 가설로 세우고 교차 검증한다. 빌드 후 헬스체크를 호출해 보고, 의존성을 제거해 보고, JMX 노출을 막아 본다.
- 아쉬운 점
  - "사건/탐문/범인" 은유와 감정 표현("숨이 가빠집니다")이 길어서, 해결 코드가 글의 70% 지점에 나온다(G 간결성, E-2).
  - 같은 증상을 겪는 독자를 위한 체크리스트나 해결 확인 방법이 없다.
- 골격
  ```
  # R2DBC Connection Pool 실종 사건
  ## 시작하며
  ## 사건 발생
  ### R2DBC 커넥션 풀 실종 제보 / 커넥션 풀이란? / 커넥션 풀에 기대하는 동작 / 기대와는 다른 R2DBC 커넥션 풀의 동작
  ## 사건 조사
  ### 현상 파악 / 탐문 계획 / 현장 방문 (#### r2dbc-pool 내부 코드 분석 / HikariCP와 차이점)
  ## 사건 해결
  ### 범인 추리 / 설정을 통한 명시적 해결 / IntelliJ로 인해 가리어진 문제
  ## 사건 회고
  ## 마치며
  ```

> 예비 후보(회고형): 토스 「Reactor Netty Memory Leak 이슈 탐방기」(https://toss.tech/article/reactor-netty-memory-leak, 4/5). 본문을 끝까지 읽었다. 증상(OOMKilled, RSS 우상향)에서 관찰(한쪽 데이터센터만 증가, 특정 라우트만)을 거쳐 범인(필터·`.cache()`)과 수정 코드, 원리 해설로 이어진다. 회고형치고 짧고 단정적이다. 다만 도입부에 요약이 없다(E-1).
> 제외: 우아한형제들 「HikariCP Dead lock에서 벗어나기(실전편)」은 앞부분만 읽어 평가에서 뺐다.

### 4-1. REST API (카카오 로그인) — 카카오 developers

- URL: https://developers.kakao.com/docs/latest/ko/kakaologin/rest-api
- 출처: 카카오 / 유형: 참조(API 레퍼런스) / 원작 한국어
- **점수: 5/5.** API마다 같은 틀(기본 정보 → 요구 사항 → 설명 → 주요 에러 → 요청 → 응답 → 예제)을 반복한다. 사전 정보는 앞쪽 시퀀스 다이어그램으로 묶었다. 참조 문서의 필수 요소를 모두 갖췄다.
- 잘한 점
  1. **D(사전 정보 앞쪽)·M**: 개별 API 앞에 "시작하기 전에 › 카카오 로그인 과정"을 두고, 시퀀스 다이어그램과 단계 1~3 설명을 붙였다. 세션 유지 시간(기본 24시간, 1달) 같은 조건을 숫자로 밝힌다.
  2. **D(일관된 구조)·E-6**: 모든 API가 같은 순서의 소제목(요청 → 응답 → 예제)을 쓰고, 맨 위 "기본 정보" 표(메서드·URL·인증 방식)도 같다. 인증 방식이 둘이면 "요청: 액세스 토큰 방식 / 요청: 서비스 앱 어드민 키 방식"으로 나란히 둔다.
  3. **L(표)**: 헤더와 본문 필드를 "이름·타입·설명·필수" 표로 정리했다. Deprecated 필드는 표 아래에 대체 필드와 함께 적는다.
  4. **N**: 예제마다 `curl` 요청과 `// HTTP/1.1 200 OK` 주석이 달린 응답 JSON을 짝지어 준다.
  5. **P·D**: API마다 "주요 에러 코드" 표에 코드·설명·HTTP 상태를 넣고, 권장 처리("일시적인 장애 메시지로 처리 권장")를 적는다. 전체 목록은 에러 코드 문서로 링크한다.
- 아쉬운 점
  - 한 페이지에 API 10여 개가 들어 있어 길다(E-3). API별 페이지나 목차 고정이 있으면 더 좋다.
  - "기본 정보"와 "요구 사항" 표 안에 링크 목록이 섞여 표가 읽기 어렵다(L 표는 속성 비교용).
- 골격(발췌, 이후 API마다 같은 틀 반복)
  ```

  ## 시작하기 전에
  ### 카카오 로그인 과정
  ## 카카오 로그인

  ### 토큰 요청       (#### 요청 / 응답 / 예제)
  ### 추가 기능
  ## 로그아웃          (#### 요청: 액세스 토큰 방식 / 요청: 서비스 앱 어드민 키 방식 / 응답 / 예제)
  ## 카카오계정과 함께 로그아웃
  ## 연결 해제
  ## 액세스 토큰 정보 조회
  ## 토큰 갱신

  … (이하 같은 틀)

### 4-2. 에러 코드 (카카오 로그인) — 카카오 developers

- URL: https://developers.kakao.com/docs/latest/ko/kakaologin/trouble-shooting (URL은 trouble-shooting이지만 실제 제목은 "에러 코드")
- 출처: 카카오 / 유형: 참조(에러 코드, 조치 칼럼 포함) / 원작 한국어
- **점수: 5/5.** 에러 코드 표에 **원인**과 **해결 방법** 칼럼이 있고, 해결 방법마다 관련 문서 링크가 붙는다. 대상 독자를 명시해 일반 사용자를 걸러 낸다.
- 잘한 점
  1. **C·E-1**: 도입부 "대상 독자" 블록에서 개발자·운영자용이라고 밝힌다. 로그인이 안 되는 일반 사용자는 해당 서비스 고객센터로 안내한다. 이 문서에 없는 코드는 "참고 문서" 블록에서 다른 문서로 보낸다.
  2. **D(일관된 구조)·L(표)**: 섹션마다 한 줄 설명("…발생할 수 있는 에러 목록입니다") 다음에 같은 열 구성(에러 코드·상태 코드·원인·해결 방법) 표가 온다.
  3. **F(구체)·H**: 해결 방법이 앱 관리 페이지의 메뉴 경로(예: "[카카오 로그인] > [고급]")와 파라미터 이름까지 구체적이다. "재요청합니다" 같은 동사형 어미로 통일했다.
  4. **D(에러 메시지)**: 원인 칸에 실제 에러 메시지 문자열을 함께 적는다(예: `Unsupported response type`). 로그와 바로 대조할 수 있다.
  5. **E-7**: REST API(공통/인가 코드/액세스 토큰/ID 토큰/배송지)와 네이티브 SDK를 H2·H3로 나눠 앵커로 바로 갈 수 있다.
- 아쉬운 점
  - 해결 방법이 "-"로 빈 행이 있다(예: `-102`, `-103`). 조치가 필요 없다면 그 이유를 적어야 한다(E-8).
  - URL 경로(trouble-shooting)와 제목(에러 코드)이 어긋난다(H 일관성).
- 골격(본문 H1 이후)
  ```
  # 에러 코드
    (대상 독자 / 참고 문서 블록)
  ## REST API
  ### 공통
  ### 인가 코드
  ### 액세스 토큰
  ### ID 토큰
  ### 배송지
  ## 네이티브 SDK
  ### 인증
  ### 클라이언트
  ```

### 4-3. debounce — es-toolkit 레퍼런스

- URL: https://es-toolkit.dev/ko/reference/function/debounce.html (비교: `/ko/reference/array/chunk.html`)
- 출처: 토스 오픈소스 es-toolkit / 유형: 참조(함수 레퍼런스) / **병행**(한·영 동시 운영. 영문이 1차일 가능성이 있어 번역본으로 분류되면 번역 허용 1편을 쓴다)
- **점수: 4/5.** 함수 페이지마다 한 줄 정의 → 시그니처 → 언제 쓰는지 → 예제(단순 → 실전 → 고급) → 파라미터 → 반환값 순서로 일관된다. 예제 안의 언어가 섞인 것이 흠이다.
- 잘한 점
  1. **E-1·D(개요)**: H1 바로 아래 한 문장 정의("함수 호출을 지연시키는…")와 시그니처 한 줄을 둔다.
  2. **S·D(활용)**: 사용법 첫 문단이 "언제 쓰는가"("연속된 호출을 하나로 합치고 싶을 때")와 대표 상황(검색창 입력, 창 크기 조절)을 말한다.
  3. **N(점진적)**: 예제가 기본 호출·`cancel`·`flush` → 검색 API 실전 → `AbortSignal` 순서로 어려워진다. 주석이 결과를 설명한다("1초 안에 다시 호출되지 않으면…").
  4. **L(매개변수)·F**: 파라미터마다 이름, 타입, optional 여부, 기본값(`['trailing']`), 옵션 조합별 동작을 적었다. 반환 타입의 메서드도 나열한다.
  5. **E-6**: 모든 함수 페이지가 같은 H2·H3·H4 틀(사용법 › 시그니처 › 파라미터·반환 값·에러)을 써서 예측할 수 있다.
- 아쉬운 점
  - 같은 페이지 예제의 출력 문자열이 '실행됨'과 'Function executed'로 섞였다(H 일관성, 번역 흔적).
  - 파라미터가 표가 아니라 중첩 글머리 목록이라 타입·필수·기본값을 비교하기 어렵다(L 표).
- 골격
  ```
  # debounce
  ## 사용법
  ### `debounce(func, debounceMs, options)`
  #### 파라미터
  #### 반환 값
  (chunk 페이지는 #### 에러, ## 사용해보기 추가)
  ```

### 4-4. API 에러 코드 — 토스페이먼츠 개발자센터

- URL: https://docs.tosspayments.com/reference/error-codes
- 출처: 토스페이먼츠 / 유형: 참조(에러 코드) / 원작 한국어
- **점수: 3/5.** API별 섹션 분할과 에러 객체 설명은 좋다. 하지만 표에 원인·조치 칼럼이 없어서 4-2 카카오와 나란히 놓으면 차이가 분명하다. **"조치 칼럼이 있는가"가 에러 코드 참조 문서의 점수를 가르는 기준**이라는 대비 자료로 남긴다.
- 잘한 점
  1. **D(사전 정보 앞쪽)**: 표에 들어가기 전에 "에러 객체"(`code`, `message`)와 조회 시 에러가 들어가는 위치(`failure` 필드)를 설명한다.
  2. **E-7·E-3**: 코어·브랜드페이·링크페이·부가 API를 H2로, 개별 API(결제 승인, 결제 조회…)를 H3로 나눴다. 앵커로 자기 API의 에러만 볼 수 있다. "전체 에러 목록"도 따로 있다.
  3. **L(표)·H**: 상태 코드·에러 코드·한글 메시지·영문 메시지 4열이 모든 표에서 같고, 상태 코드 순으로 정렬했다.
- 아쉬운 점
  - 원인과 조치 칼럼이 없다. `INVALID_REQUEST` "잘못된 요청입니다"처럼 메시지가 코드를 되풀이할 뿐인 행이 많다(D 참조 + 해결책, F 구체성).
  - 400 아래에 성격이 다른 에러(구매자 카드 문제, 상점 설정 문제)가 섞여 있다. 누가 조치해야 하는지(구매자/상점/토스) 구분이 없다.
- 골격(발췌)
  ```
  # API 에러 코드
    (에러 객체 설명)

## 유형별 추천 1순위

| 유형 | 1순위 | 이유 |
|---|---|---|
| 학습 | **토스페이먼츠 「주문서형 결제 연동하기」** (1-1) | 개요 → 4단계 지도 → 사전 준비 → Client/Server로 표시한 단계 → 결과 확인(성공·실패 응답) 순서로 D 학습 필수 요소를 모두 갖췄다. 단계마다 FAQ와 에러 패널을 붙여 학습과 문제 해결을 결합한 패턴(D 결합)까지 보여 준다. 모범 문서로 옮길 때는 인터랙티브 패널에 있는 코드를 본문 코드 블록으로 꺼내고, 단계를 실제 H2로 만들어야 한다. 단계별 성공 판정 문구는 2순위 앱인토스 「React Native 시작하기」에서 가져온다. |
| How-to | **토스페이먼츠 「장애 인지 가이드」** (2-1) | 번호 + 명령형 H2, 첫 문단의 목적·활용·왜, 수치 기준(30초 2xx), 보안 경고와 대응책, 상황별 판별 코드, 주석 단 JSON, FAQ 분리. How-to에 필요한 요소가 한 문서에 가장 밀도 있게 들어 있다. 빠진 것은 "구독 검증 명령" 하나다. |
| 트러블슈팅 | **카카오 「FAQ › 문제 해결」** (3-1). 간결한 형식은 NHN Cloud(3-2)를 함께 참고 | 증상과 에러 메시지를 그대로 제목으로 쓰고, 정상 동작과 문제를 구분하고, 원인을 분류한 뒤 해결 방안을 낸다. 문서형 트러블슈팅의 핵심 판단이 가장 잘 드러난다. NHN의 "원인 1문장 → 명령" 리듬과 토스 주문서형의 "오류원인 / 해결 방법" 2칸 패널을 형식으로 빌린다. **세 후보 모두 "해결 확인" 단계가 없으므로** 모범 문서에서 새로 채워야 한다. 회고형 글을 쓸 때는 카카오페이 R2DBC(3-4)의 요약 → 재현 → 가설 → 검증 흐름을 참고한다. |
| 참조 | **카카오 「REST API」** (4-1). 에러 코드 문서는 같은 카카오 「에러 코드」(4-2) | API마다 기본 정보 → 요청 → 응답 → 예제 틀이 같고, 사전 정보는 시퀀스 다이어그램으로 앞에 모았다. 필드 표(이름·타입·설명·필수), curl과 응답 예제, API별 주요 에러와 권장 처리까지 갖췄다. 에러 코드 문서는 원인·해결 방법 칼럼이 있는 4-2가 기준이다. 토스 API 에러 코드(4-4)는 "조치 칼럼이 없으면 무엇이 부족한가"를 보여 주는 대비 자료로 쓴다. |
