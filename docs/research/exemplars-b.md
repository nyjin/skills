# 한국어 기술 문서 본보기 후보 B — 설명 / 설계·ADR / 런북 / 장애 보고서

작성일: 2026-10-15. 평가 기준은 `synthesis.md`의 원칙 ID(D·E·F·I·L·M·P·S 등)를 따른다.

## 조사 방법과 주의

- 모든 후보는 본문을 실제로 받아 읽었다. 받은 방식은 `curl` + HTML→텍스트 변환, Medium(당근)은 Cloudflare 차단으로 **RSS `content:encoded` 전문**, PDF는 `pypdf` 추출 또는 직접 열람이다.
- **원래 한국어로 쓴 문서**만 골랐다. 당근 Lynx 글은 영문판이 있으나 한국어판이 먼저 게시됐다(RSS 순서·게시일 기준). LY 한국어 블로그는 일본어 번역 글이 섞여 있어 이번 후보에서 뺐다.
- 블로그 서두 인사·채용 문단은 점수에서 제외했다.
- 인용은 20자 이내로만 했고, 나머지는 바꿔 썼다. 스킬에는 원문을 넣지 않는다.
- 점수: 5 = 그대로 구조 본보기로 쓸 만함, 4 = 일부 패턴 차용 가치 높음, 3 = 특정 요소만 참고.

## 1. 설명 문서 (개념·원리·"어떻게 동작하나")

### E1. Aurora MySQL 인덱스 DDL이 Reader 버퍼풀을 비운다?

- URL: https://medium.com/daangn/aurora-mysql-%EC%9D%B8%EB%8D%B1%EC%8A%A4-ddl%EC%9D%B4-reader-%EB%B2%84%ED%8D%BC%ED%92%80%EC%9D%84-%EB%B9%84%EC%9A%B4%EB%8B%A4-16c6328dea50
- 출처: 당근 기술 블로그(DB팀), 2026-10
- 유형: 설명(원리) + 조사 보고. 주 유형은 설명. 장애 보고서의 "원인 분석" 절 본보기로도 쓸 수 있다.
- **점수: 5**. 원리 설명 → 깨진 가정 → 증거 → 재현 → 원인 → 운영 기준으로 이어지는 흐름이 매우 논리적이다. 모든 주장에 측정값이 붙어 있다.

잘한 점
1. **E-2·S, 도입부에 "깨진 가정"을 둔다.** 누구나 믿는 통념을 한 문장으로 제시하고 "반쪽만 맞았다"고 결론부터 밝힌다. 이어서 이 글에서 다룰 범위(발견→관찰→재현→리포트→fix)를 한 문단으로 예고한다.
2. **D(설명형)·S, 원리를 먼저 깐다.** 캐시 동기화 원리를 다루는 첫 H3에서 Writer/Reader/스토리지 구조와 DDL 알고리즘별 기대 동작을 규칙 두 줄로 정리한다. 그런 다음 "두 번째 줄이 깨진 가정"이라고 짚는다. 독자는 무엇이 예상 밖인지 정확히 알고 본문에 들어간다.
3. **F, 수치와 기준이 구체적이다.** 미사용 인덱스를 고른 기준(4개 노드 × 2주 스냅샷에서 읽기 0)을 밝히고, ReadIOPS·CPU·stale 비율(94~98%)처럼 현상을 숫자로 보여 준다.
4. **M·L, 재현 매트릭스가 있다.** DDL 7종(a~g)을 같은 형식(조회 → DDL → 재조회 → 판정 한 줄)으로 반복하고, 마지막에 요약 그림으로 "정상/예상 밖"을 한 번에 보여 준다. 판정 줄을 `→ 영향 없음`, `→ (⚠️ 예상 외)`로 통일해 훑어보기 쉽다.
5. **P, 안전 경고를 그 자리에 둔다.** 진단 쿼리 자체가 부하를 준다는 주의를 쿼리 바로 아래 괄호로 달고, 공식 문서 경고를 근거로 댄다. 영향 버전 범위(3.08.0~3.14 이전)와 백포트 계획 없음까지 적고, fix 전까지의 운영 기준 두 가지를 제시하며 끝맺는다.

아쉬운 점
- 제목이 질문형이고 본문 H3 일부("버퍼풀 안에서 무슨 일이")가 명사구로 끊겨 있어 E-5(평서문 제목) 기준에는 맞지 않는다.
- 첫 소제목이 H4이고 다음부터 H3이어서 위계가 어긋난다(Medium 변환 탓일 수 있음).

골격
```
(H4) 미사용 인덱스를 정리하다 만난 Aurora 엔진 결함, 그리고 3.14 릴리즈까지
H3 Aurora 는 Reader 의 캐시를 어떻게 동기화할까
H3 발단: 미사용 인덱스 6개
H3 현상: Writer 는 조용한데 Reader 만 튄다
H3 버퍼풀 안에서 무슨 일이: IS_STALE
H3 재현: DDL 종류별로 Reader 버퍼풀은 어떻게 반응할까
  (a~g 케이스는 굵은 소제목, H4 "정리하면 아래와 같아요.")
H3 원인: Aurora MySQL 3.08.0 버전의 결함
H3 해결 방안
H3 마무리
H3 참고
```

### E2. 카카오 안정성 보고서 — 프롤로그 "카카오톡 메시지가 도달하기까지"

- URL: https://t1.kakaocdn.net/kakaocorp/kakaocorp/admin/promise/report/KakaoReliabilityReport_online.pdf (PDF 5~7쪽)
- 출처: 카카오, 『카카오 안정성 보고서』(2023-09)
- 유형: 설명(동작 흐름)
- **점수: 4**. 순수한 "어떻게 동작하나" 문서의 짧은 본보기다. 비개발자도 읽을 수 있게 썼다.

잘한 점
1. **E-1·E-2, 요약 문단 하나로 전체 흐름을 먼저 보여 준다.** 첫 쪽에서 클라이언트 → 프론트엔드 → 릴레이·세션 매니저 → 백엔드 → DB → 수신자의 흐름을 한 문단으로 끝낸다. 다음 쪽부터 단계별로 자세히 풀어 간다.
2. **E-4·L, 단계 번호와 동사형 제목을 쓴다.** "1단계 메시지 보내기"부터 "6단계 메시지 받기"까지 단계마다 "명사 + ~하기" 형태로 맞췄다. H-목록 형태 통일(E-5 같은 수준 같은 형태)의 좋은 예다.
3. **I, 용어를 각주식 사이드바로 정의한다.** 본문 속 번호(1~6)와 여백의 용어 정의(클라이언트, 프론트엔드 서버, 오브젝트 스토리지 등)를 연결해 본문 흐름을 끊지 않는다.
4. **M, 그림 1장이 6단계 전체를 받친다.** "001 카카오톡 메시지를 주고받는 과정" 그림에 단계 번호를 그대로 표시해, 글과 그림이 같은 번호 체계를 쓴다.
5. **S, 단계마다 "왜 필요한가"를 붙인다.** 예를 들어 유효성 확인은 비정상 클라이언트(어뷰징) 때문이고, 접속 정보 서버는 서버당 연결 수 제한 때문이라고 이유를 함께 쓴다.

아쉬운 점
- 수치(지연 시간, 처리량)가 거의 없어 F가 약하다. 대외 보고서라 의도적으로 뺀 것으로 보인다.
- 보고서 지면 레이아웃(단 나눔·사이드바)에 의존하므로 Markdown으로 옮기면 용어 정의를 각주나 표로 바꿔야 한다.

골격
```
프롤로그: 카카오톡 메시지가 도달하기까지   (요약 문단 3개)
  1단계 메시지 보내기
  2단계 유효성 확인하기
  3단계 메시지 요청 전달하기
  4단계 메시지 저장하기
  5단계 채팅방 참여자들에게 메시지 전달하기
  6단계 메시지 받기
  [그림 001] + [용어 사이드바 1~6]
```

### E3. 천만 MAU를 지탱하는 커뮤니티 시스템을 소개해요

- URL: https://medium.com/daangn/%EC%B2%9C%EB%A7%8C-mau%EB%A5%BC-%EC%A7%80%ED%83%B1%ED%95%98%EB%8A%94-%EC%BB%A4%EB%AE%A4%EB%8B%88%ED%8B%B0-%EC%8B%9C%EC%8A%A4%ED%85%9C%EC%9D%84-%EC%86%8C%EA%B0%9C%ED%95%B4%EC%9A%94-090fb4021e20
- 출처: 당근 기술 블로그(커뮤니티실), 2026-07
- 유형: 설명(아키텍처·설계 철학)
- **점수: 4**. "왜 이런 구조가 되었는가"를 요구사항에서 끌어내는 방식이 좋다. 다만 6만 자가 넘고 H4까지 내려가 한 문서 한 주제(E-3)를 넘어선다.

잘한 점
1. **S·D, 요구사항을 먼저 세우고 구조를 거기서 도출한다.** 구조를 결정한 시스템 특성 다섯 가지(지역성·인증 정책 차이, 반복 구성 요소, 전사 플랫폼 의존, 작은 팀, 장기전)를 열거한 뒤, 이 다섯 가지가 곧 아키텍처 요구사항이라고 못 박는다. 독자는 이후 모든 선택을 이 다섯 가지에 비추어 읽게 된다.
2. **F, 규모를 수치 이력으로 보여 준다.** 분리 당시 약 100 RPS, 전국 오픈 때 약 4,000, 현재 약 20,000 RPS를 제시해 "천만"이라는 숫자가 시스템에 무엇을 요구하는지 구체화한다.
3. **S(대안 비교), 선택과 그 대가를 함께 쓴다.** 마이크로서비스 대신 모듈형 모놀리스를 고른 이유와 장점을 쓰고, 모듈을 나누는 것만으로는 독립 배포가 되지 않는다는 조건까지 밝힌다.
4. **E-5, 제목만 읽어도 주장이 보인다.** "…실패를 격리한다"처럼 H4를 주장형 평서문으로 써서 목차만으로 설계 원칙 목록이 된다.
5. **M, 대표 흐름 하나로 구조를 관통한다.** "동네생활 게시글 작성" 한 시나리오로 웹앱→서버앱→이벤트→후속 작업 흐름을 따라가게 한다. 추상 구조 설명 뒤에 구체 사례를 붙이는 전개다(E-4 설명형).

아쉬운 점
- 서두에서 해요체로 인사한 뒤 "이제부터 합니다체로" 바꾼다고 스스로 밝힌다. 의도는 있지만 R-3(한 문서 한 어조) 기준에서는 감점 요소다.
- 분량이 커서 H4가 20개를 넘는다. 개요 문서와 하위 문서로 나누는 편이 E-3에 맞다.

골격
```
H3 천만이라는 숫자는 자랑이기 전에 신호다
H3 서비스마다 푸는 문제는 달라도 필요한 구성 요소는 반복된다
H3 여러 웹앱과 하나의 서버앱이 커뮤니티 시스템을 이룬다
  H4 웹앱은 사용자 경험의 앞단을 책임진다
  H4 하나의 서버앱도 네 개의 실행 단위로 나눠 운영한다
  H4 하나의 서버앱에서도 상태의 경계는 나눈다
  H4 후속 작업은 이벤트로 나눠 서로의 실패를 격리한다
  H4 동네생활 게시글 작성을 통해 아키텍처 흐름을 살펴본다
  H4 후보 목록은 추천과 정책을 거쳐 개인화된 피드가 된다
  H4 여러 서비스에서 반복되는 기능은 컴포넌트로 만들어 함께 쓴다
  H4 계약은 웹앱과 서버앱의 약속을 코드 생성과 자동 검사에 연결한다
H3 단순함은 공짜가 아니다
  H4 (물리적 분리 / 실행 단위 / 모듈화 / 리팩토링 / 패턴·모델링 / 테스트 / 기술 부채) 7개
H3 부하는 성장하기 좋은 동기였다
H3 시스템의 마찰을 줄여야 제품 변화를 사용자에게 더 빨리 전달할 수 있다
H3 더 큰 성장은 시스템의 경계와 개발 방식에도 변화를 요구한다
H3 단순함은 구조만으로 지켜지지 않는다
```

### E4. 당근의 인증은 어떻게 달라져 왔을까요?

- URL: https://medium.com/daangn/%EB%8B%B9%EA%B7%BC%EC%9D%98-%EC%9D%B8%EC%A6%9D%EC%9D%80-%EC%96%B4%EB%96%BB%EA%B2%8C-%EB%8B%AC%EB%9D%BC%EC%A0%B8-%EC%99%94%EC%9D%84%EA%B9%8C%EC%9A%94-a50dd4b7b44c
- 출처: 당근 기술 블로그(Identity Service Team), 2026-08
- 유형: 설명(개념의 발전사)
- **점수: 3**. 시간순 전개(E-4)와 "문제→해결" 반복이 명료한 입문형 설명이지만, 기술 깊이와 수치가 적다.

잘한 점
1. **A·E-1, 주제를 한 줄 정의로 시작한다.** 모든 인증의 목적을 "계정의 주인이 나"임을 확인하는 일로 정의하고, 이후 모든 절을 이 정의에 비추어 전개한다.
2. **E-4, 시간순 + 문제→해결 반복.** SMS 인증 → 계정 분실·사기 문제 → 본인인증 도입 → SSO → 글로벌 → AI 순서로, 각 절이 "어떤 문제가 생겼고 무엇으로 풀었나"라는 같은 틀을 따른다.
3. **I, 약어를 그 자리에서 푼다.** CI, SNA, KYC, MCP를 처음 나올 때 풀어 쓰거나 "※ CI란?" 상자로 정의한다.
4. **S, 채택하지 않은 실험도 적는다.** SNA 인증은 정확도는 좋았지만 기대한 전환율 상승이 검증되지 않아 배포하지 않았다는 결정과 이유를 남긴다.

아쉬운 점
- F가 약하다. 전환율·이탈률 같은 수치를 밝히지 않는다.
- H3 제목에 질문형("글로벌은요?")과 인용형이 섞여 E-5 형태 통일이 깨진다.

골격
```
H3 당근의 초창기 로그인
H3 "이 계정은 분명히 제 것이에요"
H3 본인인증을 도입했어요
H3 (SSO 절)
H3 글로벌은요?
  H4 처음 보는 앱에 전화번호를 알려 주기는 싫어요
  H4 문자가 오지 않아요
  H4 이 사람을 믿어도 될까요?
H3 AI가 당근에 로그인하려면요?
H3 같이 만들어요 (채용, 제외)
```

### D1. 웹뷰 다음의 레일을 깔다: 당근이 Lynx를 선택한 이유

- URL: https://medium.com/daangn/%EC%9B%B9%EB%B7%B0-%EB%8B%A4%EC%9D%8C%EC%9D%98-%EB%A0%88%EC%9D%BC%EC%9D%84-%EA%B9%94%EB%8B%A4-%EB%8B%B9%EA%B7%BC%EC%9D%B4-lynx%EB%A5%BC-%EC%84%A0%ED%83%9D%ED%95%9C-%EC%9D%B4%EC%9C%A0-34dd50abbfb7
- 출처: 당근 기술 블로그(프론트엔드코어팀), 2026-08 (영문판은 이후 별도 게시)
- 유형: 설계 결정 기록(기술 도입 ADR + 도입기)
- **점수: 5**. ADR의 뼈대(문제→조건→후보→대안 비교→결정의 한계→검증 기준→결과→현재 상태)를 블로그 문체로 모두 갖췄다.

잘한 점
1. **S·F, 결정 기준을 체크리스트로 먼저 고정한다.** "새로운 실행 환경에 필요했던 조건" 절에서 조건 5개(첫 프레임에 실제 UI, 화면 단위 적용, 앱과 독립 배포, 3명으로 시작, 웹뷰로 복귀 가능)를 목록으로 둔다. 이후 대안 비교는 모두 이 조건에 대어 본다. 설계 문서의 "목표/비목표"에 해당하며, 비목표(앱 전체 교체가 아님)도 명시한다.
2. **S(대안 비교), 우열이 아니라 적합성으로 비교한다.** React Native·Flutter를 각각 H4로 나눠 장점을 먼저 인정하고, 당근의 운영 모델까지 가는 데 "새로 소유해야 할 책임의 범위"를 기준으로 배제한다.
3. **P, 결정의 한계를 스스로 적는다.** 동일 수준 PoC 비교가 아니었고 성능 순위 평가도 아니었다고 밝힌다. 결정이 어떤 전제 아래 유효한지 드러낸다. ADR의 "결과(Consequences)" 정신에 맞는다.
4. **F, 검증 기준과 결과를 수치로 적는다.** PoC 성공 기준 4개를 미리 목록으로 정하고, 190만 명 50:50 노출, p75 기준 Android 735→610ms(18%), iOS 479→302ms(37%)로 보고한다. 결과가 기대보다 작았다는 평가와 그 이유(최적화 미비)도 함께 쓴다.
5. **Q, 문서에 갱신일을 박는다.** "현재 적용 현황"에 업데이트 날짜를 적고 앞으로 계속 추가하겠다고 밝혀, 결정 기록을 살아 있는 문서로 관리한다.

아쉬운 점
- H3 "Lynx?"처럼 물음표 제목, H4 번호 매김("1. 작고 빠르게…")과 비번호 H4가 섞여 E-5 위계 형태가 들쭉날쭉하다.
- 결정 요약(무엇을 언제 결정했는지)이 글 말미 "다음의 선택지"에 가서야 한 문단으로 나온다. ADR로 옮길 때는 맨 앞 요약이 필요하다.

### D2. App Router의 장점은 우리에게도 장점일까요?

- URL: https://toss.tech/article/52999
- 출처: 토스 기술 블로그(토스뱅크 프론트엔드), 2026-09
- 유형: 설계 결정 기록(**비채택** ADR)
- **점수: 5**. "도입하지 않기로 했다"는 결정을 근거와 함께 남긴 드문 사례다. 결론을 도입부에 먼저 밝히는 역피라미드가 모범적이다.

잘한 점
1. **E-2, 결론을 맨 앞에 둔다.** 도입 다섯 문단 안에 배경(Pages Router 유지보수 모드), 검토 주체, **결론(도입하지 않음)**, 이유 한 줄을 모두 넣고 "어떻게 그 결론에 닿았는지" 따라가겠다고 예고한다.
2. **D·S, 기대 이점 하나당 H2 하나.** 각 H2가 검토한 가설 하나(스트리밍, RSC 활용도, 점진 마이그레이션, 생태계 지원)이고, 절마다 "기대 → 직접 측정 → 이득과 비용" 순서를 반복한다.
3. **F, 측정값으로 판단한다.** FCP가 Chromium 64ms, WebKit 5,065ms였고 우회 후 103ms였다. 레이아웃 이동값은 0.138에서 0.036으로 줄었다. 의견이 아니라 실측 결과로 기대를 기각한다.
4. **L(표)·P, 버그 조건을 표로 좁힌다.** basePath 이중 적용 버그를 "App Router 라우트 구성 × 이동 결과" 3행 표로 정리해 재현 조건을 정확히 특정한다. 관련 공개 이슈와 PR 상태(초안)까지 밝힌다.
5. **S, 마지막 H2가 결정 그 자체다.** "…유지하기로 했어요" 절에서 인정한 이득과 더 컸던 비용을 저울질하고, 앞으로 기술 검토 때 적용할 판단 기준 두 가지를 남긴다.

아쉬운 점
- H2 다섯 개 중 네 개가 질문형이다. 토스 자체 가이드(E-5, 평서문 제목)와도 어긋난다. 본보기로 쓸 때는 "스트리밍 이득 검증"처럼 평서형으로 바꿔야 한다.
- 측정 그래프가 이미지로만 있고 측정 환경(기기·네트워크 조건)이 본문에 없다.

골격
```
(도입: 배경 / 검토 그룹 / 결론 / 예고)
H2 준비된 것부터 보여주면 더 좋을까요?
H2 RSC를 우리 코드에서 얼마나 활용할 수 있을까요?
H2 운영하면서 조금씩 옮길 수 있을까요?
H2 많은 개발자가 쓰면 해결도 빠를까요?

```

### D3. 한꺼번에 짊어지던 배치를 내려놓고, 하나씩 흘려보내는 워크플로로

- URL: https://techblog.woowahan.com/26832/
- 출처: 우아한형제들 기술블로그(주문접수채널 백엔드), 2026-09
- 유형: 설계 문서(직접 구축 vs 도입 결정 + 구조 설명 + 적용 사례)
- **점수: 4**. "배경 → 대안(Temporal) 검토 → 직접 구축 결정 → 구성 → 사례 → 고민한 트레이드오프 → 확장 계획"이 설계 문서 골격과 거의 일치한다.

잘한 점
1. **P, 수치의 성격을 맨 앞에서 밝힌다.** 본문 첫 줄에서 등장 수치·설정값은 예시이며 운영 설정과 다르다고 고지한다. 대외 공개 설계 문서의 안전한 수치 표기 방식이다.
2. **S(대안 비교), 기각 사유를 항목별로 쓴다.** Temporal을 먼저 공정하게 설명한 뒤 부담 4가지(러닝커브, 별도 인프라, 엔진 이슈 대응, 종속 리스크)를 굵은 제목 + 설명 목록으로 쓰고, 이미 가진 자원(코루틴, DocumentDB)으로 대체할 수 있다는 근거로 결정한다.
3. **L·M, 비교표를 쓴다.** Temporal과 Flowkit을 "항목 / Temporal / Flowkit" 표로 대조하고(상태 저장, 재개, 재시도, Signal), 기존 방식과의 차이도 표로 정리한다.
4. **F, 기존 방식의 한계를 수치로 쓴다.** cron이 1분 주기라 지연 판단에 최대 59초 오차가 생긴다는 식으로 문제를 정량화한다.
5. **S, "고민했던 부분"을 독립 H2로 둔다.** 결정론(determinism), 단일 문서 replay 모델, 분산 환경·롤백 안전을 별도 절로 다뤄 결정의 비용을 숨기지 않는다.

아쉬운 점
- 목표/비목표가 명시적인 절로 없다. 이 글의 범위(접수지연 알림 하나만 다룸)가 들어가는 말 끝에 한 문장으로만 나온다.
- 부제가 길고 구어적이다("입맛대로 골라 Claude로 뚝딱"). 제목만 보고 결정 내용을 알기 어렵다.

골격
```
(부제) Temporal 도입은 부담스러웠고, … 워크플로 엔진 개발기
H2 들어가는 말
H2 배경
H2 구성
H2 개발사례 – 접수지연 알림
  H3 기존 방식 – 한꺼번에 훑는 배치
  H3 Flowkit 방식 – 주문 하나가 워크플로 하나
  H3 replay를 한 걸음씩 따라가기
  H3 기존과의 차이
  H3 운영 가시성 – 한 화면에서 보기

  H3 결정론(determinism)이라는 숙명

  H3 보상 트랜잭션(Saga) – @Transactional 없이 걸쳐진 일관성
  H3 여러 API 오케스트레이션 – 비동기 응답 엮기
  H3 그 밖에 – 사람이 개입하는 장기 흐름, 주기 실행, 병렬 처리

```

## 3. 운영 런북 (절차서·운영 가이드·장애 대응 절차)

### R1. 데브시스터즈의 장애 대응 원칙과 방법

- URL: https://tech.devsisters.com/posts/incident-management-principles/
- 출처: 데브시스터즈 기술 블로그(인프라셀). 사내 문서 **전문 공개**.
- 유형: 운영 런북(장애 대응 절차서 + 알람 티어 기준 + 포스트모템 양식)
- **점수: 5**. 블로그 글이 아니라 실제 사내 절차서를 그대로 공개한 문서다. 원칙 → 분류 기준 → 단계별 절차 → 메시지 템플릿 → 사후 양식이 한 문서에 있다. 이번 조사에서 가장 "문서다운" 후보다.

잘한 점
1. **E-1·A, 첫 절이 범위 한 문장이다.** "#개요"에서 이 문서가 무엇을 다루는지 한 문장으로 끝내고, 바로 원칙으로 들어간다.
2. **F, 분류 기준이 측정 가능한 숫자다.** 알람 티어를 최초 대응 시간(FRT)으로 정의한다. Tier 0은 15분 이내, Tier 1은 평일 15분·야간이면 다음 날 오전, Tier 2는 평일 2~3시간이다. 티어마다 "정의 / 인지 수단 / 장애 유형 예시"라는 같은 틀을 반복한다(H 일관성).
3. **J·L, 역할과 행동을 독자 주체로 쓴다.** 지휘자·기록가·공통 역할별로 "해야 할 일"을 목록으로 나누고, 역할 할당 대사 예시까지 준다. 절차는 큰 틀(발생 공유 → 팀 구성 → 해결 → 종료 공유)을 먼저 보여 준 뒤 단계별로 푼다.
4. **N(예시)·C, 복사해 쓸 수 있는 메시지 템플릿.** 장애 발생 메시지와 종료 메시지에 들어갈 필수 항목(서비스명·발생 시간·규모·채널 / 종료 시간·추정 원인·조치·포스트모템 일시)을 나열하고 실제 예문을 붙인다. 비개발 직군도 이해할 표현을 쓰라는 독자 지침도 함께 둔다.
5. **P, 위험한 행동에 경고 패널을 쓴다.** "⚠️" 패널로 변경 작업은 1인이 하되 독단으로 하지 않는다는 규칙과 그 이유(멱등성 미보장)를 강조한다. 경고 패널을 2곳에만 써서 L(절제된 강조 패널)도 지킨다.

아쉬운 점
- H2·H3 앞에 `#`를 텍스트로 붙여(#개요, #원칙) 렌더링된 제목에 기호가 보인다. 이식 시 제거해야 한다.
- 원칙 절이 대괄호 라벨 + 중첩 목록으로 길게 이어져, 원칙별 H3로 나눴다면 훑어보기 더 쉬웠을 것이다.

골격
```

H2 #원칙
   [장애 대응의 목표] [에스컬레이션과 상황 전파] [장애 대응을 위한 환경 준비]
   [장애 감지의 방법] [알람 건전성] [기록과 커뮤니케이션] [장애 회고의 중요성]

  H3 #[Tier 0] 언제든지 대응해야 하는 최우선순위 알람 (<~ FRT 15min)
  H3 #[Tier 1] 최선의 속도로 대응해야 하는 차순위 알람 (…)
  H3 #[Tier 2] 즉각적인 대응이 필요하지는 않지만 개입을 필요로 하는 알람 (…)

### R2. 결제는 계속된다: 결제 담당자가 장애에 대응하는 방법

- URL: https://techblog.woowahan.com/15236/
- 출처: 우아한형제들 기술블로그(결제플랫폼), 2023-12
- 유형: 운영 가이드(도메인 특화 장애 대응 절차)
- **점수: 4**. 블로그 형식이지만 "장애 유형별 조치 표"가 런북의 핵심 요소를 잘 보여 준다.

잘한 점
1. **C·S, 영향부터 설명해 절차의 이유를 세운다.** "결제 장애는 어떤 영향이 있을까?"에서 결제 실패와 실제 출금이 함께 생기고 대사로 다음 날 환불된다는 고객 영향을 먼저 설명한다. 이후 "결제수단 차단이 최우선"이라는 절차 순서가 납득된다.
2. **L(표)·D(문제 해결형), 유형 → 조치 매핑 표.** "카드/은행 장애", "PG사 장애(카드·휴대폰)", "PG사 장애(간편결제)" 3행에 각각 할 조치(공지 문구 등록, 결제수단 비활성화, PG 배분율 조정)를 대응시킨다. 런북의 분기 표 본보기다.
3. **F, 알림 조건을 구체적으로 열거한다.** 실패율 상승, 동일 에러 메시지 반복 비중, 시도 대비 승인 비중 하락, CPU 과부하처럼 무엇을 기준으로 알림을 받는지 밝힌다.
4. **M, 그림마다 번호와 캡션을 단다.** [그림 1]~[그림 7]에 한 줄 설명을 붙여(L 캡션 규칙) 대시보드·워크플로 양식·차단 화면을 보여 준다.
5. **P·Q, 남은 한계를 명시한다.** 결제수단 조치가 아직 담당자 판단에 의존한다는 점과 자동화 계획을 밝힌다.

아쉬운 점

### P1. [토스페이먼츠] DDoS 공격으로 인한 결제서비스 장애 보고서

- URL: https://static.tosspayments.com/public/tosspayments_issue_report_251016.pdf
- 출처: 토스페이먼츠 결제운영팀, 2025-10-16 (가맹점 대상 공문)
- 유형: 장애 보고서(대외 고객용)
- **점수: 4**. 두 쪽 안에 원인 → 영향 → 조치 → 향후 계획을 모두 담았다. 세 차례 장애를 표 하나로 비교한 점이 특히 좋다.

잘한 점
1. **E-2, 원인을 맨 앞에 둔다.** "가. 장애 원인"에서 외부 대규모 DDoS(L7 포함)라고 첫 문장으로 밝힌다.
2. **F·L(표)·M, 3회 장애를 한 표로 비교한다.** 1차·2차·3차를 열로 두고 영향 시간(분 단위 기간 포함: 32분/13분/74분), 공격 범위, 영향 범위, 공격 트래픽량(평시 대비 250배/250배/7,800배)을 행으로 둔다.

4. **F·S, 조치를 차수별로, 계획을 기한별로 쓴다.** 조치는 "1차 이후 / 2차 이후 / 3차 시"로 나누고 각 묶음 끝에 "⇒" 한 줄 요약을 단다. 향후 계획은 즉시(~10.17)·단기(10월 중)·중기('25년 내)·장기('26년 1분기)로 기한을 박는다.
5. **H, 오류 증상을 실제 응답 이름으로 쓴다.** Connect Timeout / Reset, Read Timeout처럼 가맹점이 로그에서 찾을 수 있는 표현을 그대로 쓴다.

아쉬운 점
- 시각별 타임라인(탐지·선언·완화·복구 시각)이 없다. 영향 시간 구간만 있다.

잘한 점
1. **E-4(시간순)·F, 사건 경과를 시각으로 연다.** 발생 시각(15시 19분), 진화까지 약 8시간, 메시지 기능 복구까지 그 뒤 약 2시간, 전체 정상화까지 약 5일로 큰 흐름을 먼저 준다.
2. **S, "그런데 왜?"로 문제를 정확히 세운다.** 데이터는 3곳 이상 분산돼 있었고 DB는 자동·수동 전환됐다는 사실을 먼저 밝힌 뒤, 그런데도 왜 오래 멈췄는지를 질문으로 던진다. 독자가 오해하기 쉬운 지점(데이터 이중화 = 서비스 이중화)을 짚는다.
3. **I, 용어 설명 상자.** 오브젝트 스토리지, 메타 정보 시스템, 캐시 시스템을 "✔️용어 설명" 상자에서 한 줄씩 정의한다.
4. **S, 원인을 구조 차원에서 요약한다.** 판교에만 이중화된 구성 요소(오브젝트 스토리지 메타 정보, 보안키 저장소, 인증 캐시의 약 30%)를 구체적으로 들고, 데이터가 아니라 시스템 전체의 이중화가 부족했다는 한 문장으로 정리한다. 원인 조사 방법(외부 전문가 포함 약 1개월, 주제별 인터뷰)도 밝힌다.
5. **짝 문서(9900)는 대책을 원인과 1:1로 맞춘다.** 기존 DC 보완 / 재난 대비 / 운영도구·서비스 다중화 세 절이 9902의 원인 항목에 대응한다.

아쉬운 점

### P4. LINE의 장애 보고와 후속 절차 문화

- URL: https://engineering.linecorp.com/ko/blog/line-failure-reporting-and-follow-up-process-culture/
- 출처: LINE Engineering(한국어), 2019-11
- 유형: 장애 보고서 템플릿 해설 + 실제 장애 사례 2건(서사형 회고)
- **점수: 3**. 보고서 항목 설명과 액션 아이템 작성법이 실용적이다. 사례는 타임라인 없는 서사라 구조 본보기로는 약하다.

잘한 점
1. **D, 보고서 템플릿 7항목을 정의한다.** 요약 / 탐지 시간 / 영향받은 서비스 / 원인 / 타임라인과 해결 과정 / 해결 과정과 예방책(Jira 포함) / 관련 문서.
2. **P, 미확정 정보는 TBD로 남기고 먼저 공유한다.** 1차 보고는 당일 발송하고, 원인 분석에 몇 주가 걸리면 빈칸을 TBD로 둬도 된다는 규칙이다.
3. **F·J, 액션 아이템을 실행 가능한 문장으로 쓰는 법을 대조로 보여 준다.** 막연한 다짐 대신 "PR 템플릿에 체크리스트를 추가한다" 같은 실행형 문장을 쓰라고 하고, 예방·탐지 개선·대응 개선 세 분류로 자주 나오는 항목을 예시한다(알람 조건 `request failure count > 1000` 같은 구체 기준 포함).
4. **S, 원인을 "시나리오처럼" 쓰라고 한다.** 원인이 된 작업을 하게 된 이유부터 사건이 어떻게 연결됐는지까지 이어서 쓰라는 지침은 기여 요인 서술의 좋은 기준이다.

아쉬운 점
- 사례 2건(전체 동기화 API, friends matrix)에 시각·영향 수치·타임라인이 없다.

골격
```
H1 LINE의 장애 보고와 후속 절차 문화
H2 들어가며
H2 장애를 대하는 방법
H2 장애 처리 프로세스
  H3 장애 탐지 / 장애 전파 / 장애 해결 / 장애 보고 / 장애 회고

  H3 'friends matrix' 데이터의 잦은 업데이트로 발생한 장애
H2 마치며

### P5. (참고) KT 네트워크 장애 원인분석 결과 발표 — 과학기술정보통신부 브리핑

- URL: https://www.korea.kr/news/policyNewsView.do?newsId=156477990
- 출처: 대한민국 정책브리핑, 2021-10-29 (브리핑 녹취)
- 유형: 외부 조사기관의 장애 원인 분석(구두 발표 녹취)
- **점수: 3**. 형식은 구두 발표와 질의응답이라 구조 본보기가 아니다. 다만 **원인 분석 절의 논리 전개**는 매우 좋아서 그 부분만 참고한다.

잘한 점
1. **F·P, 가설을 수치로 기각한다.** "DDoS였나?"를 먼저 검증한다. DNS 트래픽은 평시 대비 22배까지 늘었지만 IP당 질의는 최대 15건, 대역폭 사용은 최대 8%/28%였다. 이를 근거로 두 유형의 DDoS를 각각 배제한다.
2. **S, 인과 사슬을 단계로 설명한다.** 라우터 교체 작업 중 `exit` 누락 → BGP 경로가 IS-IS로 유입 → 평소 1만 개 내외이던 경로 정보에 수십만 개가 유입 → 안전장치 없는 IS-IS로 전국 확산 → 89분 장애.
3. **S, 문제점을 관리적/기술적으로 나눈다.** 승인된 야간 작업을 주간에 함, 관리자 부재, 사전 검증이 사람 검토뿐이었음, 테스트베드·확산 차단 장치 없음을 분류한다. 대책은 단기/중장기로 나눈다.

아쉬운 점
- 문서가 아니라 발표 녹취라 제목 구조와 표가 없다.

골격
```
H1 KT 네트워크 장애 원인분석 결과 발표
(차관 모두발언: 결론 요약)
(국장 발표) 개요(발생·복구 시각, 89분) → 1) DDoS 여부 분석 → 2) 라우팅 오류·확산 분석
 → IPTV·음성 영향 → 문제점(관리적 / 기술적) → 향후 조치(단기 / 중장기) → 피해보상
[질문·답변]
```

### 찾기 어려웠던 점

- **장애 보고서**: 분 단위 타임라인과 기여 요인 분석을 갖춘 한국어 공개 포스트모템은 찾지 못했다. 기업 블로그는 "장애 대응 문화" 소개 글이 대부분이고, 공개 보고서는 대외 공문(토스페이먼츠)이나 대국민 설명(카카오) 수준이다.
- **ADR**: 원래 한국어로 사람이 쓴 성숙한 공개 ADR 저장소는 찾지 못했다. GitHub에서 찾은 한국어 ADR 대부분이 2025~2026년의 템플릿이거나 AI 생성 흔적이 있어, 기술 블로그의 설계 결정 글(D1~D3)이 더 나은 본보기다.
- **런북**: 명령어 수준의 실행 절차서는 공개되지 않는다. 데브시스터즈 문서가 사실상 유일한 "절차서 전문 공개" 사례다.
