### A-1. Hive는 잊으려 했지만, Spark는 기억하고 있었다: 사라진 get_table RPC 복원기

- URL: https://d2.naver.com/helloworld/7314597
- 사이트 / 묶음: NAVER D2 / A
- 유형: 트러블슈팅. 해결안 비교(설계 결정)를 함께 담았다.
- **점수: 5/5.** 증상 → 배경지식 → 원인 → 대안 비교 → 구현 → 검증 → 교훈 흐름이 거의 교과서 수준이다. 첫 단락에서 범위와 읽을거리를 알려 주고, 결정 근거를 표로 남겼다.
- 잘한 점
  1. **E-1 개요 + 범위 선언.** 첫 단락이 "무엇을 다루는가"와 함께 "직접 수정한 코드보다 큰 질문"까지 예고한다. 이어서 기준 버전(`aida-4.2.0`)과 "코드는 축약·편집" 같은 전제를 한 줄로 밝힌다.
  2. **D 트러블슈팅 필수 요소.** 증상을 불릿 4개로 나눴다(되는 클라이언트와 안 되는 클라이언트, 오류 성격, 서버 상태). 원인은 "다음 한 문장으로 요약"한 뒤 굵은 한 문장으로 못 박는다.
  3. **S 대안 비교.** 해결방안 4개를 `해결방안 / 내용 / 판단` 표로 비교하고 채택안에 `[채택]`을 붙였다. 채택 이유에는 원칙(RFC 1122 견고성 원칙)까지 적었다. 독립 ADR이 없을 때 쓸 수 있는 최고의 ADR 본보기다.
  4. **I 약어·용어 첫 등장 풀이.** "스텁(stub, 원격 호출을…)", "프로세서 맵(…짝지어 둔 표)"처럼 처음 나오는 용어를 괄호 안에서 바로 풀이해 흐름을 끊지 않는다.
  5. **M·N 시각화와 검증.** 두 진입점이 하나의 내부 메서드로 수렴하는 ASCII 다이어그램을 넣었다. 검증은 `검증 대상 / 확인할 내용 / 결과` 표로 정리했다. 단위 테스트로는 등록 누락을 못 잡는 이유를 먼저 쓴 것도 좋다(P).
- 아쉬운 점
  - H4 "더 알아보기"가 본문 안에 있어 위계가 깊어진다(E-3). 접기나 부록으로 빼면 좋다.
  - "마치며"의 교훈 불릿이 문장 두세 개로 길어 훑어보기가 어렵다.
- 골격
  - (도입: 오류 메시지 → 1단락 개요 → 전제 1줄)
  - H2 문제 상황: Invalid method name: 'get_table'
  - H2 배경지식: HMS는 어떻게 요청을 처리하는가 — H3 Thrift IDL과 코드 생성 / 메서드 이름 기반 디스패치 / 서버 측 구현: HMSHandler
  - H2 원인 분석: 진화한 API와 뒤처진 클라이언트 — H3 get_table에서 get_table_req로의 전환 / 그런데 Spark는 여전히 레거시 RPC를 부른다
  - H2 해결: 사라진 RPC를 되살리되, 로직은 재사용한다 — H3 1) IDL에 get_table 복원 / 2) Thrift 코드 재생성 / 3) 서버 구현 (H4 더 알아보기)
  - H2 검증
  - H2 마치며
  - H2 참고 자료

### A-2. 스마트스토어센터 Oracle에서 MySQL로의 무중단 전환기

- URL: https://d2.naver.com/helloworld/6512234
- 사이트 / 묶음: NAVER D2 / A
- 유형: 설계·전환기(마이그레이션)
- **점수: 4/5.** 전환 전략, 검증 체계, 함정을 빠짐없이 기록했다. 다만 "왜 이중 쓰기인가"를 다른 전략과 비교하지 않았고, 후반 설정값 나열이 길다.
- 잘한 점
  1. **E-1·S 도입 두 단락.** 동기(리소스 경합, 라이선스 비용)와 결정(MySQL 전환)을 먼저 말하고, 이어서 "이 글에서는 …을 공유합니다"로 범위를 밝힌다.
  2. **S 제약에서 전략으로.** "서비스 중단 불가", "재배포만으로 해결 불가"라는 두 제약에서 무중단과 즉시 롤백이라는 요구를 끌어내고 이중 쓰기를 택했다. 전환 단계 3개를 시간순 불릿으로 정리했다.
  3. **S 기각한 대안을 밝힘(성능 검증 절).** HTTP 트래픽 복사와 Kafka 토픽 복제를 쓰지 않은 이유(타 부서 중복 호출 위험)를 적고 Read 트래픽 복제를 택했다.
  4. **M 다이어그램 캡션.** 이미지 15개 모두에 짧은 캡션(예: "이중 쓰기 아키텍처")을 달았다(L 캡션 규칙).
  5. **P 완료 기준.** 전환을 확인하는 방법으로 모든 전환 대상 쿼리에 식별 주석을 달고 그 주석이 Oracle에 더 이상 들어오지 않는지 감시하는 방법을 구체적으로 적었다.
- 아쉬운 점
  - 전략 수준의 대안(CDC 기반 복제, 일괄 이관 + 다운타임 등)을 비교하지 않았다. S의 "대안과 비교한 선택 이유"가 비어 있다.
  - "HikariCP 설정" 아래 H4 7개가 참조성 나열이라 서사 흐름을 끊는다. 부록이나 별도 참조 문서로 나누는 편이 낫다(E-3).
- 골격
  - (도입 2단락)
  - H2 마이그레이션 준비 및 전략 수립 — H3 전환 전략: 이중 쓰기
  - H2 기술적 도전과 해결 과정 — H3 JPA 이중 쓰기 / MyBatis 이중 쓰기 / 쿼리·DBMS 성능 검증 / 정합성 검증
  - H2 마이그레이션 후 아키텍처 및 검증 — H3 서비스 테스트 및 전환
  - H2 트러블슈팅 및 기타 고려 사항 — H3 Index Merge / 배치 성능 / HikariCP 설정 / 시퀀스와 auto increment
  - H2 마치며

### A-3. C++ std::bit_cast와 reinterpret_cast — 언제 어떤 것을 써야 하는가

- URL: https://d2.naver.com/helloworld/1155434
- 사이트 / 묶음: NAVER D2 / A
- 유형: 설명(개념·원리) + 선택 가이드
- **점수: 4.5/5.** 실패한 시도를 차례로 보여 주며 개념을 쌓고, 마지막에 "언제 무엇을" 표와 플로차트로 닫는다. 설명형의 모범이다.
- 잘한 점
  1. **E-2·C 동기 → 질문 → 범위.** 코드 리뷰에서 본 실제 코드(const 제거)로 시작해 "무엇을 써야 할까요?"라는 질문을 세운다. 이어서 "객체 수명은 다음 글에서"라며 범위 밖을 밝힌다.
  2. **D 설명형 구조.** H3를 시도 1(reinterpret_cast) → 시도 2(union) → 시도 3(memcpy, "정답") 순서로 짜서 대안 비교를 제목 위계로 보여 준다.
  3. **I 첫 등장 풀이.** "미정의 동작(UB, undefined behavior)"처럼 한국어 + 약어 + 원어를 병기한다.
  4. **M·L 결론 표 + 플로차트.** 마지막 절이 `상황 / 올바른 도구` 표와 "선택 플로차트"로 끝나 다시 찾아볼 때 이 절만 봐도 된다.
  5. **P 각주로 근거 분리.** 표준 조항(basic.lval 등)과 예외는 각주로 빼서 본문 흐름을 지킨다.
- 아쉬운 점
  - "정리" 절이 맨 끝에 있다. 선택 표를 도입부 바로 뒤에 요약으로 한 번 더 보여 주면 역피라미드(E-2)가 완성된다.
  - H4 "reinterpret_cast 자체는 UB가 아니다"까지 위계가 내려간다.
- 골격
  - (도입: 팀 맥락 → 문제 코드 → 질문 → 범위)
  - H2 타입 퍼닝: std::bit_cast는 어떤 문제를 풀기 위해 만들어졌는가 — H3 시도 1 / 시도 2 / 시도 3(정답) / bit_cast: memcpy의 구문 편의 / 타입 퍼닝 정리
  - H2 reinterpret_cast를 올바르게 쓰기 위해 알아야 할 것들 — H3 reinterpret_cast와 static_cast / 엄격한 앨리어싱 규칙 / 포인터 ↔ 정수 변환
  - H2 정리: 언제 std::bit_cast, 언제 reinterpret_cast?

### A-4. 서버는 살아있는데 로그인이 안 됩니다 — 장애 회고

- URL: https://velog.io/@devjiji/서버는-살아있는데-로그인이-안-됩니다
- 사이트 / 묶음: Velog / A
- 유형: 장애 회고(개인 서비스, 소규모)
- **점수: 3.5/5.** 3줄 요약, 가설 → 검증으로 범위 좁히기, 현상 원인과 진짜 원인의 분리, 남은 숙제까지 회고 골격이 좋다. 하지만 타임라인·영향 범위·탐지 시각이 없고 어조가 구어체라 사내 보고서 본보기로는 부족하다.
- 잘한 점
  1. **E-2 "0. 3줄 요약".** 증상 / 단서 / 원인과 진짜 교훈을 세 줄로 먼저 준다. 본문을 읽지 않아도 결론을 알 수 있다.
  2. **S 원인을 두 층으로.** "AI에게 물었을 때 나온 원인"(타이머 미설정)과 "내가 정의한 진짜 원인"("사람의 기억에 의존")을 나눠, 재발 방지가 구조 개선으로 이어지게 했다.
  3. **F 판단 기준 명시.** "장애 시점에만 나타나는가?"를 첫 번째 판단 기준으로 내세워 상시 노이즈 로그를 배제한 근거를 보여 준다.
  4. **N 증거 그대로.** 서버 로그, 클라이언트 예외, `certbot certificates` 출력을 그대로 넣고 핵심 줄에 `← ???` 표시를 했다.
  5. **D 후속 조치 분리.** "조치"(cron) → "알게 된 것" → "남은 숙제"(실패 알림 부재) 순서로, 끝나지 않은 위험을 따로 남겼다.
- 아쉬운 점
  - 타임라인(발생·인지·복구 시각)과 영향 범위(사용자 수, 지속 시간)가 없다. 장애 보고서 템플릿의 필수 칸이 비어 있다.
  - "워후!", "샤샤샥" 같은 구어와 헬스장 서사가 정보 밀도를 낮춘다(G).
- 골격
  - (시리즈 안내)
  - H2 0. 3줄 요약
  - H2 1. 접속은 안 되는데, 서버는 살아 있었다
  - H2 2. 로그는 이 장애에 대해 아무 말도 하지 않았다
  - H2 3. 클라이언트 로그가 말하는 것
  - H2 4. 일단 살린다

  3. **D·L 비교 표 → 선택지마다 같은 틀.** 먼저 `観点 × 4方式` 비교 표(실시간성, 데이터량, 비용, 소스 부하, 구현 난이도, UPDATE/DELETE 처리 등 9개 관점)를 두고, 이어지는 방식별 H2 4개를 모두 "정의 → 구현 수단 → 一方で(약점) → 적합한 경우 → 자사 사용 현황" 순서로 썼다(E-6 예측 가능성).
  4. **S·L "どう選ぶか" 결정 표.** `이용 장면 / 데이터량 / 실시간성 / 갱신일시 컬럼·삭제 감지 / 적합한 방식` 표 하나로 조건 → 선택을 역으로 찾게 했다.
  5. **S 권장 진입 순서.** まとめ에서 CDC부터 과하게 만들기보다 단순한 방식부터 시작하라는 의사결정 휴리스틱과 재검토 시점(데이터량 증가, 신선도 요건 변화)을 남긴다.
- 아쉬운 점
  - 첫 두 단락이 개인 취미 이야기라 TL;DR이 세 번째로 밀린다.
  - 결정 표가 본문 맨 뒤에 있다. TL;DR에서 표로 가는 앵커 링크가 있으면 좋다.
- 골격
  - H1 TL;DR
  - H1 はじめに
  - H1 データ取得方式について(+観点別 비교 표) — H2 ゼロコピー / CDC / Create or Replace / クエリベースの増分更新
  - H1 どう選ぶか
  - H1 まとめ

### C-3. システムの負荷の原因を切り分ける方法

- URL: https://qiita.com/k0kubun/items/8ab1dfa7c0359d8e618d
- 사이트 / 묶음: Qiita / C
- 유형: 트러블슈팅 절차(진단 결정 트리, 런북 골격)
- **구조 점수: 4/5.** 제목 위계 자체가 결정 트리다. 조건 분기("…が高い場合 / 低い場合")를 H3 쌍으로 두고, まとめ에서 같은 트리를 중첩 목록으로 다시 그린다. 짧고(약 1,700자) 바로 쓸 수 있다.
- 구조에서 잘한 점
  1. **E-1 후보 목록 먼저.** 첫 절에서 병목 후보 4개에 번호를 매기고, 본문 내내 "「1. CPU使用率」"처럼 그 번호로 가리킨다(H 일관성).
  2. **D·L 분기 쌍 제목.** "…が高い場合 / 低い場合", "…している場合 / していない場合"처럼 H3를 쌍으로 만들어 독자가 자기 상황의 가지만 읽게 한다.
  3. **N 도구 명시.** 각 확인 단계에 쓸 명령(`top`, `sar`, `vmstat`, `netstat -an | wc -l`)을 바로 적는다.
  4. **F 판정 기준 수치.** 로드 애버리지 1 이하는 가볍고 1~3은 약간 무겁다는 식으로 분기 임계값을 숫자로 준다.
  5. **M まとめ = 트리.** 마지막 절이 중첩 목록으로 된 결정 트리라, 다음에는 이 절만 열면 된다.
- 아쉬운 점
  - 2014년 글이라 도구와 수치 기준이 낡았을 수 있다. 작성 시점·환경(前提) 섹션이 없다.
  - 트리를 그림(흐름도)으로 그리면 더 빨리 읽힌다.
- 골격
  - H1 サーバのボトルネックを探る — H2 ロードアベレージを見る — H3 高い場合 / 低い場合
  - H1 特定のホストの問題を解決する — H2 CPU使用率を見る(H3 高い / 低い) / スワップの発生状況を見る(H3 している / していない)
  - H1 TCPコネクション数を確認 — H2 多い場合 / そうでもない場合
  - H1 まとめ

## C(일본) 글에서 한국 기술 문서에 가져올 구조 패턴

1. **도입부 3종 세트: TL;DR → はじめに(독자·동기·범위) → 前提(환경·버전·작성 시점).** 요약을 맨 위에 두고 이어서 독자와 범위를 밝히고, 실행 환경과 "이 정보의 기준 시점"은 별도 소절로 분리한다. (C-2, Qiita Docker) → E-1, C, P
2. **"이 글의 포인트" 박스 + 전체 흐름 한 줄과 그림.** 결론 3개를 박스에 넣고 "전체는 N단계"라는 문장과 흐름 그림을 붙여 지도를 먼저 준다. (C-1) → E-2, M
3. **"범주: 결론" 형식의 H2.** `현상: …` / `원인: …` / `임시 복구: …` / `재발 방지: …`. 범주로 훑을 수 있고 결론도 바로 읽힌다. 장애 보고서와 트러블슈팅 템플릿의 H2 규칙으로 쓰기 좋다. (C-1) → E-5, D
4. **용어 풀이·보충은 접기(`<details>`)로.** 본문 흐름은 숙련자 기준으로 쓰고, 초보용 풀이는 "용어 메모: X"라는 접기 블록에 둔다. 독자 수준이 섞인 문서에서 R-5(생략 vs 상세) 충돌을 푸는 구조적 해법이다. (C-1) → C, I
5. **되돌리기 어려운 함정은 경고 콜아웃으로.** 일반 메모(message)와 위험(alert)을 박스 종류로 구분한다. (C-1) → L 강조 패널, P
6. **조건 분기를 H3 쌍으로("…인 경우 / 아닌 경우").** 진단 절차와 런북에서 독자가 자기 가지만 읽게 하고, 마지막 정리는 같은 트리를 중첩 목록이나 흐름도로 다시 보여 준다. (C-3) → D, L, M
7. **후보·선택지에 번호를 매기고 본문에서 그 번호로 가리키기.** 같은 대상을 늘 같은 이름과 번호로 부른다. (C-3) → H
8. **관점별 비교 표 → 선택지마다 같은 틀(정의·수단·약점·적합 사례·우리 현황) → "어떻게 고르나" 결정 표 → 권장 진입 순서.** 기술 선정 문서와 ADR 사전 자료의 골격이다. (C-2) → S, D, L
9. **임시 복구 H3를 실행 가능한 동사구 단계로.** 회고 안의 복구 절차를 그대로 런북으로 옮길 수 있게 쓴다. 영향 시간 같은 핵심 수치는 H3 제목에 넣는다. (C-1) → L 절차, F
10. **"배운 점" 절을 주제별 H3로 나누기(장애 대응 / 이전).** 교훈을 한 덩어리 불릿으로 쓰지 않고 영역별로 나눠 다시 찾기 쉽게 한다. (C-1) → E-7
11. **설명편과 실전편을 별도 문서로 나누고 서로 링크하기.** 한 문서 한 주제(E-3)를 지키면서 유형 결합(D)을 문서 간 링크로 해결한다. (Qiita VPC) → E-3, D
