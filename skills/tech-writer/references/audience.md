# 독자 파악

문서를 쓰거나 고치기 전에 이 파일을 읽는다. 누가 읽는지에 따라 구조, 용어, 설명 깊이, 시각화 수준이 모두 달라진다. 독자 정보는 config에서 먼저 가져오고, 모자란 것만 묻는다.

## 목차

C-1 쓰기 전에 독자를 정한다 · C-2 다섯 가지를 파악한다 · C-3 같은 독자도 상황마다 필요가 다르다 · C-4 수준별로 전략을 바꾼다 · C-5 독자가 모르는 개념은 정의한다 · config 해석 · eli5 호출 조건

## C-1 쓰기 전에 독자를 정한다

독자를 정하지 않고 쓴 문서는 작성자 자신을 독자로 삼는다. 작성자에게 당연한 배경지식이 독자에게는 없다(지식의 저주). 그래서 첫 단계는 언제나 "이 문서를 누가 읽는가"를 정하는 것이다.

왜: 기술 문서에서 가장 자주 빠뜨리는 단계이고, 빠뜨리면 이후 모든 판단(무엇을 설명하고 무엇을 생략할지)의 기준이 사라진다. [S5, S6, S8]

## C-2 다섯 가지를 파악한다

| 항목 | 묻는 것 | config 필드 |
|---|---|---|
| 역할 | 개발자인가, PM인가, 운영자인가 | `role` |
| 수준 | 이 분야를 얼마나 아는가 | `level` |
| 이미 아는 것 | 설명 없이 써도 되는 개념·도구 | `knows` |
| 목표·질문 | 문서를 읽고 무엇을 하려는가, 무엇을 먼저 알고 싶은가 | `needs` |
| 읽는 상황 | 장애 대응 중인가, 온보딩 중인가, 의사결정 전인가 | `context` |

왜: 역할만으로는 부족하다. 같은 백엔드 개발자라도 신규 입사자와 담당자는 필요한 정보가 다르다. [S4, S8, S2]

## C-3 같은 독자도 상황마다 필요가 다르다

절차를 따라 하는 순간에는 "무엇을, 어떤 순서로" 하는지만 필요하다. 시스템을 처음 배우는 순간에는 "왜 그렇게 동작하는지"가 필요하다. `context`가 있으면 이 구분에 쓴다.

- 장애 대응 중 → 런북형: 명령어와 확인 방법을 앞에, 원리는 링크로 뺀다.
- 온보딩·교육 → 설명형: 배경과 원리를 충분히 쓴다.
- 의사결정 전 → 결론과 영향을 먼저, 근거는 뒤에.

왜: 한 문서에 두 필요를 섞으면 어느 쪽에도 맞지 않는다. [S6]

## C-4 수준별로 전략을 바꾼다

| level | 전략 |
|---|---|
| beginner | 용어를 처음 나올 때 정의한다. 단계를 빠짐없이 쓰고, 예제는 그대로 실행되게 한다. 결과 확인 방법을 준다. |
| intermediate | `knows`에 있는 것은 설명하지 않는다. 핵심 절차와 주의점에 집중하고 세부는 참조 링크로 넘긴다. |
| expert | 결론, 차이점, 제약, 수치만 쓴다. 기본 개념 설명은 뺀다. |
| non-technical | 비유로 개념을 잡고, 구체적인 사실(영향, 일정, 비용)은 그대로 준다. 구현 세부와 전문 용어는 뺀다. 코드 식별자(헤더 이름, API 경로, 클래스 이름)는 본문에 쓰지 않는다. 결정할 사항은 선택지와 각각의 득실, 추천안으로 준다. |

의사결정자(리더, 경영진)가 독자면 non-technical 전략에 "결론과 결정할 사항을 맨 앞에"를 더한다. 이 항목은 출처에 없는 확장이며, eli5 스킬의 직무별 설명 방식과 맞춘 것이다.

왜: 한 수준에 맞춘 문서는 다른 수준에 맞지 않는다. 초보자에게는 빠진 단계가, 숙련자에게는 늘어진 설명이 장애물이다. [S2, S6, S7]

## C-5 독자가 모르는 개념은 정의한다

`knows`에 없는 개념이 처음 나오면 한두 문장으로 정의한다. 정의할 개념이 너무 많으면 독자 설정과 재료가 어긋난 신호다. 이때는 문서를 나누거나(개념 문서 + 작업 문서) 사용자에게 확인한다.

왜: "모두 알겠지"라는 가정이 가장 흔한 실패 원인이다. 독자는 빠진 정보를 추측으로 메우고, 추측은 틀린다. [S7, S8, S3]

## config 해석

`scripts/load_config.py`가 돌려주는 JSON을 다음처럼 쓴다.

| 필드 | 쓰는 곳 |
|---|---|
| `audiences.default` | 요청에 독자가 없을 때의 독자 |
| `audiences.profiles.<이름>` | 위 C-2의 다섯 항목 |
| `style.tone` | 문서 전체 어조 (style.md H-5) |
| `style.loanword_policy`, `style.glossary` | 표기 규칙 (style.md H-1, H-3) |
| `output.*` | 출력 형식과 다이어그램 도구 (formatting.md, visualization.md) |
| `warnings` | 사용자에게 한 줄로 알린다. 작업은 계속한다 |

### 독자를 정하는 순서

1. 요청에 독자가 명시돼 있으면 그 독자를 쓴다("PM용으로", "신규 입사자 대상"). profiles에 같은 역할이 있으면 그 프로필을, 없으면 요청 내용으로 임시 프로필을 만든다.
2. 명시가 없으면 `audiences.default`를 쓴다.
3. 재료와 독자가 명백히 어긋날 때만 한 번 확인한다. 어긋남의 기준은 다음과 같다.
   - non-technical 독자인데 재료가 내부 API·코드 세부뿐이다.
   - expert 독자인데 요청이 "처음 쓰는 사람용 가이드"다.
   - 재료의 핵심 개념 절반 이상이 `knows`에 없다.

확인 질문 예: "기본 독자가 백엔드 개발자(중급)로 설정돼 있습니다. 이 재료는 결제 운영팀이 읽을 내용으로 보이는데, 운영팀 기준으로 쓸까요?"

### config가 없을 때 (최초 인터뷰)

`load_config.py`가 종료 코드 3을 돌려주면 아래 네 가지를 한 번에 묻는다. 객관식 선택지를 주고, 답을 YAML로 만들어 `~/.claude/tech-writing/config.yaml`에 저장한 뒤 다시 실행한다.

1. 문서를 주로 누가 읽는가 (역할)
2. 그 독자는 이 분야를 얼마나 아는가 (beginner / intermediate / expert / non-technical)
3. 설명 없이 써도 되는 기술·도구는 무엇인가
4. 독자가 문서에서 먼저 알고 싶은 것은 무엇인가

답을 저장한 예:

```yaml
audiences:
  default: backend-dev
  profiles:
    backend-dev:
      role: 백엔드 개발자
      level: intermediate
      knows: [Spring Boot, JPA, Kubernetes 배포]
      needs: [설계 의도, 운영 방법, 장애 시 확인할 곳]
style:
  tone: 합니다체
```

어조와 출력 형식은 묻지 않고 기본값(합니다체, markdown)을 쓴다. 사용자가 원하면 설정 모드에서 바꾼다.

## eli5 호출 조건

다음 중 하나에 해당하면 개념을 설명하는 단락을 쓸 때 eli5 스킬을 부른다.

- 독자 level이 non-technical 또는 beginner이고, 재료에 `knows`에 없는 핵심 개념이 3개 이상이다.
- 문서의 목적이 개념 이해인데(설명 문서), 독자 수준과 개념 난이도의 차이가 크다.

eli5에는 설명할 개념과 독자를 넘긴다. 독자는 config `role`을 eli5의 직무 분류에 대응시킨다.

| config role | eli5 독자 |
|---|---|
| 개발자 계열 | Engineer |
| PM, 기획자 | Product Manager |
| 팀장, 리더 | Manager |
| 임원 | Director |
| 디자이너 | Designer |
| 그 외 동료 | Colleague |

eli5의 결과는 그대로 붙이지 않는다. 문서의 어조(config `tone`)와 용어집에 맞춰 다시 쓰고, 비유는 한 개념에 하나만 남긴다. eli5가 설치돼 있지 않으면 C-4의 전략으로 직접 쓴다.
