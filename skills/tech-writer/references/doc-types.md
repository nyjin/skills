# 문서 유형

독자를 정한 다음, 문서 유형을 고를 때 이 파일을 읽는다. 유형이 정해지면 해당 템플릿(`templates/`)과 본보기 한 편(`exemplars/`)만 읽는다.

## 목차

D-1 독자의 목표로 유형을 고른다 · D-2 유형마다 빠지면 안 되는 요소가 있다 · D-3 유형은 결합할 수 있다 · D-4 실무 문서는 네 유형에 대응시킨다 · D-5 여러 페이지 문서는 유형별로 나누고 잇는다 · T-1 매체에 맞춰 형식을 고른다 · T-2 시작하기 진입점을 둔다 · T-3 학습 문서 끝에 다음 단계를 안내한다

## D-1 독자의 목표로 유형을 고른다

작성자가 하고 싶은 말이 아니라 독자가 이 문서로 이루려는 일이 유형을 정한다.

```text
독자는 이 문서로 무엇을 하려는가
├─ 처음 접하는 것을 배우려 한다 ─────────── 학습 (튜토리얼, 시작하기)
├─ 특정 작업을 끝내거나 문제를 풀려 한다 ─── 문제 해결 (how-to, 트러블슈팅, 런북)
├─ 정확한 사실을 찾아 확인하려 한다 ──────── 참조 (API 레퍼런스, 에러 코드, 설정 목록)
├─ 코드가 실제로 어떻게 동작하는지 근거와 함께 알려 한다 ── 설명 (코드 조사 보고)
└─ 왜 그런지 깊이 이해하려 한다 ──────────── 설명 (개념, 원리, 설계 결정)
```

판단이 어려우면 독자가 문서를 펼치기 직전에 던질 질문을 한 문장으로 써 본다. "어떻게 시작하지?"면 학습, "이거 어떻게 해?"·"왜 안 되지?"면 문제 해결, "이 값이 뭐였지?"면 참조, "이건 왜 이렇게 돼 있지?"면 설명이다.

왜: 유형마다 독자가 기대하는 순서와 밀도가 다르다. 유형을 잘못 고르면 문장을 아무리 다듬어도 독자가 원하는 정보에 닿지 못한다. [S3, S9]

## D-2 유형마다 빠지면 안 되는 요소가 있다

| 유형 | 필수 요소 |
|---|---|
| 학습 | 학습 목표, 사전 준비(도구·버전·권한), 번호 단계, 그대로 실행되는 예제, 결과 확인 방법, 다음 단계 |
| 문제 해결 | 문제(증상)와 원인의 구분, 에러 메시지·로그 원문, 바로 적용할 해결책(명령어·설정), 해결 원리 한두 문장, 환경별 차이, 해결 확인 방법 |
| 참조 | 개요, 사전 정보(인증·권한), 일관된 항목 구조(시그니처 → 매개변수 → 반환값 → 오류 → 예제), 앵커로 찾아가기 |
| 설명 | 한 줄 정의, 등장 배경(어떤 문제를 푸는가), 동작 원리, 대안과의 비교, 시각 자료, 실제 활용 |
| 코드 조사 보고 | 결론, 기준(저장소·브랜치 또는 커밋), 결정적인 코드, 근거 링크가 달린 흐름 표, 근거 수준(P-4), 선언과 실제가 다른 곳 |

왜: 필수 요소가 하나 빠지면 독자는 문서를 끝까지 읽고도 목표를 이루지 못한다. 특히 학습 문서의 결과 확인과 문제 해결 문서의 해결 확인이 자주 빠진다. [S3, S2, S7]

## D-3 유형은 결합할 수 있다

한 문서에 주된 유형 하나를 정하고, 다른 유형의 요소는 필요한 만큼만 빌린다. 예를 들어 튜토리얼 중간에 꼭 필요한 개념 설명은 두세 문장으로 넣고 자세한 설명은 설명 문서로 링크한다. 두 유형이 비슷한 비중이면 문서를 나눈다.

왜: 유형 분류는 도구이지 규칙이 아니다. 다만 주된 유형이 없으면 구조가 흐려진다. [S3]

## D-4 실무 문서는 네 유형에 대응시킨다

| 실무 문서 | 주된 유형 | 템플릿 | 본보기 |
|---|---|---|---|
| 튜토리얼, 시작하기, README의 빠른 시작 | 학습 | `templates/tutorial.md` | `exemplars/tutorial.md` |
| how-to 가이드, 연동 가이드 | 문제 해결 | `templates/how-to.md` | `exemplars/how-to.md` |
| 트러블슈팅, FAQ | 문제 해결 (진단) | `templates/troubleshooting.md` | `exemplars/troubleshooting.md` |
| 운영 런북, 절차서 | 문제 해결 (절차) | `templates/runbook.md` | `exemplars/runbook.md` |
| API 레퍼런스, 에러 코드, 설정 목록 | 참조 | `templates/reference.md` | `exemplars/reference.md` |
| 개념 설명, 아키텍처 개요 | 설명 | `templates/explanation.md` | `exemplars/explanation.md` |
| 설계 문서, ADR(Architecture Decision Record, 아키텍처 결정 기록) | 설명 + 결정 기록 | `templates/design-adr.md` | `exemplars/design-adr.md` |
| 장애 보고서, 포스트모템 | 설명 + 타임라인 | `templates/postmortem.md` | `exemplars/postmortem.md` |
| 코드 조사 결과, 값 추적, 영향 범위 조사 | 설명 (근거 중심) | `templates/investigation.md` | `exemplars/investigation.md` |
| 비개발 독자용 기술 설명 | 설명 (non-technical, 중요도순) | `templates/non-technical.md` | `exemplars/non-technical.md` |

README는 단일 유형이 아니다. 맨 위에 한 줄 소개와 빠른 시작(학습), 아래에 설정·명령 목록(참조)을 두고, 긴 내용은 별도 문서로 링크한다.

왜: 실무 문서 이름은 팀마다 다르지만 독자의 목표는 네 가지 안에 들어간다. 대응시켜 두면 필수 요소를 놓치지 않는다. [S2, S3]

## D-5 여러 페이지 문서는 유형별로 나누고 잇는다

한 주제의 문서가 여러 편이면 내비게이션 메뉴를 짠다고 생각하고 나눈다.

```text
docs/
├── start-here.md  ← 학습: 전체 흐름과 첫 실행
├── tutorials/  ← 학습
├── how-to/  ← 문제 해결: 작업별 가이드
├── troubleshooting.md  ← 문제 해결: 증상별 진단
├── concepts/  ← 설명
├── reference/  ← 참조
└── glossary.md  ← 용어집
```

학습 문서에서 간단히 언급한 내용은 how-to나 참조 문서로 링크한다. 같은 내용을 두 곳에 쓰지 않고 한 곳에 쓴 뒤 링크한다(review-checklist.md Q-1).

왜: 한 문서에 다 담으면 아무도 끝까지 읽지 않는다. 나누고 이으면 독자가 자기 목표에 맞는 문서로 바로 간다. [S3]

## T-1 매체에 맞춰 형식을 고른다

| config `output.format` | 맞는 경우 | 주의 |
|---|---|---|
| markdown | 저장소에 두는 문서(README, docs/, ADR) | 코드와 같이 리뷰·버전 관리된다. mermaid가 렌더링된다 |
| confluence | 검색·협업이 중요한 사내 위키 | 개요 + 구분선, 목차 매크로, 패널을 쓴다. 다이어그램은 이미지로 첨부 |
| html | 링크 하나로 공유하는 독립 문서 | 단일 파일, 다이어그램 인라인 |

형식별 문법 차이는 formatting.md의 "형식별 차이" 절을 따른다.

왜: 같은 내용도 놓이는 곳에 따라 읽히는 방식이 다르다. [S7, S11]

## T-2 시작하기 진입점을 둔다

여러 문서로 이뤄진 주제라면 개념 설명 옆에 "시작하기"를 둔다. 처음 온 독자가 무엇부터 읽을지 고민하지 않게 한다. README라면 맨 위의 빠른 시작이 이 역할을 한다.

왜: 첫 성공 경험이 있어야 독자가 다음 문서로 간다. [S10, S3, S2]

## T-3 학습 문서 끝에 다음 단계를 안내한다

튜토리얼과 시작하기 문서는 "다음 단계" 절로 끝낸다. 이어서 읽을 how-to, 개념, 참조 문서를 두세 개 링크한다.

왜: 목표를 이룬 독자는 그다음에 할 일을 찾는다. 그 자리에 길이 없으면 문서 사이를 헤맨다. [S3]
