# AI slop 루브릭

AI가 쓴 문서에서 반복해 나오고 사람 독자의 읽기를 막는 모양을 항목으로 정리한 판정 기준이다. 8단계 검증에서 문서를 판정할 때, 9단계에서 점검 결과를 보고할 때, 보정 모드에서 기준을 다시 잴 때 읽는다.

판: 1 (2026-10-19). 판이 바뀌면 맨 아래 개정 이력에 무엇을 왜 바꿨는지 적는다. 판정 기록에는 항목 ID와 판을 함께 남긴다.

## 목차

판정 방식 · 항목 한눈에 · A 표면 · B 구조 · C 독자 · D 수정 품질 · 보고 형식 · 보정 모드 보고 형식 · 개정 이력

## 판정 방식

항목마다 "해당한다 / 해당하지 않는다"로 판정한다. 1~5점 척도는 쓰지 않는다. 같은 문장을 두고 사람끼리도, AI 실행마다도 점수가 흔들리기 때문이다.

판정 수단은 셋이다.

| 수단 | 누가 | 보고에 붙는 표시 |
|---|---|---|
| 스크립트 | `slop_check.py`가 줄 위치까지 잰다 | 스크립트 |
| 스크립트 지표 | `slop_check.py`가 문서 단위 수치를 기준값과 비교한다. 위치는 가리키지만 판정은 AI가 한다 | 스크립트 지표 |
| AI 판단 | 되말하기 서브에이전트가 이 루브릭으로 읽고 판정한다 | AI 판단 |

항목의 상태는 보정 모드가 정한다. 규칙 수치와 근거는 `scripts/slop_rules.json`이 갖는다.

| 상태 | 뜻 | 8단계에서 |
|---|---|---|
| 게이트 | 본보기·하우스 문서에서 오탐이 0이고, AI가 쓴 문서 3편 이상에서 나왔다 | 모두 고친다 |
| 지시 | slop 문서에 많지만 사람 글에도 나온다 | 위치를 보고 판단한다. 고치지 않으면 이유를 남긴다 |
| 판단 | 기계로 잴 수 없다 | 되말하기에서 판정하고, 해당하면 고친다 |
| 보류 | 근거가 모자라다 | 보고하지 않는다. 보정 모드에서만 잰다 |

C1(번호 참조)과 D1(사라진 사실)은 사용자 규칙이다. slop인지와 상관없이 고치는 규칙이라, 보정 모드는 수치만 보고하고 상태를 바꾸지 않는다.

문서 전체 판정은 세 단계다. 점수는 매기지 않는다. 여러 지표를 하나로 합치면 기술 문서와 기획서처럼 slop이 다르게 나타나는 문서에서 기준이 어긋난다.

| 판정 | 조건 |
|---|---|
| 통과 | 게이트 항목 0, 해당하는 판단 항목 0 |
| 손볼 곳 남음 | 게이트 항목 0. 지시·판단 항목이 남았고 각각 남긴 이유가 있다 |
| 미통과 | 게이트 항목이 남았다 |

## A 표면

### A1 기호로 말을 이은 문장

정의: 산문이나 목록에서 `≠`, `vs`, `=`, `+`로 낱말을 잇는다. 기호가 어떤 관계인지 말하지 않아 독자가 짐작해야 한다.

- 해당: `정산 확정 ≠ 송금 완료`, `회차 배치 vs 스트리밍`, `가맹점 + 정산 담당자에게 알린다`
- 해당하지 않음: 표의 셀과 머리글, 코드, 숫자 계산(`30 + 30분`)

### A2 한글과 영문이 뒤섞인 문장

정의: 백틱과 링크 밖에서 한 문장 안에 한글과 영문이 10번 이상 바뀐다. 산문, 용어, 식별자가 한 줄에 섞여 문장을 읽다가 용어를 해석하기를 되풀이하게 된다.

- 해당: `settlement job은 Kafka topic에서 event를 consume해 DB에 upsert하고 retry는 DLT로 보낸다`
- 해당하지 않음: 식별자를 백틱으로 묶은 문장, 영문 용어가 한두 번 나오는 문장

### A3 굵은 결정 문장으로 여는 문단

정의: 문단이나 인용 상자가 `**정산은 하루 한 번 확정한다.**`처럼 굵은 결정 문장으로 시작하고 그 뒤에 근거가 붙는다. 문단마다 굵은 문장이 앞서면 무엇이 정말 중요한지 드러나지 않는다.

- 해당: `**재시도는 세 번까지 한다.** 네 번째부터는 같은 오류가 반복됐다.`
- 해당하지 않음: `**주의**:` 같은 굵은 낱말 하나, 문장 가운데의 강조, 목록 항목(L-10이 다룬다)

### A4 장식처럼 쓴 강조

정의: 굵게, 대시(—), 괄호 덧붙임이 기준 문서보다 많이 쓰여 강조가 장식이 됐다. 사람도 쓰는 모양이라 수치만으로 판정하지 않는다. 수치가 기준값을 넘으면 많이 쓴 절을 읽고 판단한다.

- 해당: 문장마다 굵은 낱말이 둘 이상이고, 덧붙임 괄호가 문장 끝마다 붙는다
- 해당하지 않음: 경고 하나를 굵게 쓴 문서, 약어를 처음 풀어 쓰는 괄호

### A5 명사 조각으로 끝나는 문장

정의: 산문 문단의 문장이 서술어 없이 명사로 끝난다(`… 확인 필요.`, `… 협의 후 확정.`). 누가 무엇을 하는지 감춘다. 표 셀과 짧은 목록 항목은 해당하지 않는다.

- 해당: `송금 실패 시 재처리 대상 선정 후 담당자 통보.`
- 해당하지 않음: 표 셀의 `확인 필요`, 목록의 `일 1회`

## B 구조

### B1 여러 곳에서 되풀이한 내용

정의: 같은 주장이 다른 절이나 다른 구조(목록과 표)에 다시 나온다. `redundancy.py`의 강한 반복이 위치를 가리킨다.

- 해당: 1절의 단계 목록과 2절의 단계 표가 같은 네 단계를 같은 말로 설명한다
- 해당하지 않음: 요약 절이 본문을 한 줄로 줄인 것, 부록이 본문의 결정을 코드로 보이는 것

### B2 구조만 바꿔 다시 쓴 목록

정의: 같은 대상 셋 이상을 표와 표, 표와 목록으로 속성만 바꿔 다시 쓴다. 한 표의 열을 늘리면 된다.

- 해당: 라이브러리 셋을 역할 표, 쓰는 시점 표, 실행 순서 목록에 차례로 다시 쓴다
- 해당하지 않음: 용어 표와 본문 표가 같은 낱말을 쓰는 것
- 보류 이유: 승인한 문서에서도 같은 모양이 나왔다. 일부러 속성을 나눈 경우와 가르지 못한다

### B3 그림을 글로 다시 옮긴 곳

정의: 그림 바로 뒤에 그림의 선과 상자를 하나씩 글로 다시 설명한다(`초록 선은 …, 파란 점선은 …`). 그림 뒤에는 핵심 한 문장만 둔다.

- 해당: 그림 뒤 목록 다섯 줄이 색깔별 선의 뜻을 하나씩 말한다
- 해당하지 않음: 그림이 보여 주지 못하는 조건(시간 제한, 예외)을 덧붙인 문장

### B4 근거 없이 늘어놓은 결정

정의: 결정을 목록이나 문단으로 잇달아 늘어놓는데, 근거가 없거나 모든 결정 뒤에 같은 틀의 근거가 반복된다. 결정이 셋 이상이면 `결정 | 이유` 표 한 장으로 모은다.

- 해당: 정렬, 페이지 크기, 기본 필터를 문단 셋으로 하나씩 선언하고 각 문단 끝에 "그래서 …로 둔다"를 붙인다
- 해당하지 않음: 결정 하나를 근거와 함께 쓴 문단

## C 독자

### C1 독자가 풀 수 없는 번호 참조

정의: 링크 없는 티켓 키, 결정 기록 번호, 규칙 ID, 다른 문서의 절 번호를 내용 없이 쓴다. 독자는 번호를 외우지 않는다. 티켓 키와 결정 기록 번호는 스크립트가, 규칙 ID와 절 번호는 AI가 판정한다.

- 해당: `ADR 0031 에 따라 …`, `규칙 R-12 를 따른다`, `상위 문서 §4 참고`
- 해당하지 않음: `[PAY-4553](링크)`, 같은 문서 안의 표를 가리키는 "아래 표"

### C2 본문을 차지한 작업 메모

정의: 확인 필요, 미결, 남은 일, 후속 과제 같은 작업 메모가 여러 절에 흩어지거나 본문보다 길다. 독자에게 필요한 것은 지금 정해진 내용이다. 메모는 문서 끝 한 절로 모은다.

- 해당: 절마다 끝에 "확인 필요" 목록이 붙고, 같은 질문이 두 절에 나온다
- 해당하지 않음: 문서 끝 "남은 결정" 절 하나

### C3 본문에 남은 작성 과정

정의: 문서를 쓰고 고친 과정이 본문에 남았다. 변경 이력, "원래는 …였으나 …로 바꿈", 검토 대기 표시 같은 것이다. 독자는 지금의 결론만 필요하다. 이력은 페이지 기록이나 맨 끝에 둔다.

- 해당: `변경 (10/14): 원래는 가맹점 단위로 묶었으나 …`
- 해당하지 않음: 설계 결정 문서의 "고려한 대안" 절

### C4 제목의 질문에 답하지 않은 절

정의: 제목이나 첫 문장이 질문(가능한가, 왜 …인가)을 던지는데 절 안에 답이 없거나, 답 없이 "다만"으로 조건부터 늘어놓는다.

- 해당: `### 부분 환불을 재처리할 수 있나` 아래에 조건 목록만 있고 된다·안 된다가 없다
- 해당하지 않음: 첫 문장에서 답하고 조건을 이어 쓴 절

## D 수정 품질

8단계에서 slop을 고친 뒤에만 판정한다.

### D1 고치면서 사라진 사실

정의: 고치기 전에 있던 식별자(백틱), 수치, 링크, 표 모양, 제목이 고친 뒤에 없다. `slop_check.py --baseline`이 고치기 전 판과 비교한다. 일부러 지운 것이면 보고의 "고친 것"에 이유를 적는다.

### D2 고치면서 바뀐 뜻

정의: 기호를 풀거나 문장을 나누면서 조건, 주체, 시제, 부정이 바뀌었다. 문장이 원래보다 눈에 띄게 늘어진 것도 포함한다.

- 해당: `정산 확정 ≠ 송금 완료`를 `정산이 확정되면 송금이 완료된다`로 바꿨다(부정이 사라짐)
- 해당하지 않음: `정산이 확정돼도 송금이 끝난 것은 아니다`

## 보고 형식

9단계 보고에 아래 블록을 넣는다. 독자는 문서를 맡긴 사람이다. 항목 ID와 규칙 이름은 쓰지 않고 "보고 이름"으로 쓴다. 위치는 절 이름과 짧은 인용으로 쓴다.

```text
### AI slop 점검

판정: <통과 | 손볼 곳 남음 | 미통과> — <한 문장 이유>

| 항목 | 판정 수단 | 처음 → 지금 | 예 (절 · 인용) |
|---|---|---|---|
| <보고 이름> | <스크립트 | 스크립트 지표 | AI 판단> | <n> → <n> | <절> · "<20자 안팎 인용>" |

고친 것
- <보고 이름>: "<고치기 전>" → "<고친 뒤>"   (항목마다 대표 한 줄, 많아야 3줄)

남긴 것
- <보고 이름> · <절>: <남긴 이유>

결정 대기
- <정할 것> — <선택지와 추천>   (구조를 바꾸는 수정. 개선 모드에서만)

전에 사람이 오탐으로 판정한 곳 (다시 걸렸다. 고치지 않아도 된다)   (판정 저장소에 기록이 있을 때만)
- <보고 이름> · <절>: "<인용>" — <그때 남긴 이유>

사람 판정 누적: <보고 이름> <n>건 중 오탐 <k>건, …   (판정 저장소에 기록이 있을 때만)

사실 보존: 식별자·수치·링크·표·제목 <모두 보존 | n개 달라짐 → 목록>
```

블록은 `slop_check.py --baseline <고치기 전> --judgments <판단.json>`이 만든다. 판단 목록의 `outcome`마다 채울 칸과 들어가는 자리는 이렇다.

| outcome | 채울 칸 | 보고에서 |
|---|---|---|
| 고침 | `item`, `before`, `after` | 고친 것 (항목마다 대표 한 줄) |
| 남김, 해당 | `item`, `section`, `quote`, `reason` | 남긴 것 |
| 결정 대기 | `item`, `reason`에 "<정할 것> — <선택지와 추천>" 한 문장 | 결정 대기 |
| 해당 없음 | `item` | AI가 읽고 해당 없다고 본 항목 |

- 표에는 해당한 항목만 넣는다. 0 → 0인 항목은 뺀다.
- 판정 수단 칸은 지우지 않는다. 스크립트가 잰 것과 AI가 판단한 것은 믿을 수 있는 정도가 다르다.
- 고치지 않은 항목은 "남긴 것"이나 "결정 대기" 중 한 곳에 반드시 둔다.
- 2회 고쳐도 게이트 항목이 남으면 더 고치지 않고 "미통과"로 보고한다.

## 보정 모드 보고 형식

보정 모드는 기준을 바꾸자는 제안을 내고, 사용자가 승인해야 반영한다. 통계 용어는 쓰지 않고 두 숫자로 쓴다.

```text
### 기준 점검 (표본 <n>편: 기준 문서 <n>, AI slop 문서 <n>, 검증용 <n>)

| 항목 | 지금 | 제안 | 근거 |
|---|---|---|---|
| <보고 이름> | <게이트 | 지시 | 판단 | 보류> | <유지 | 올림 | 내림 | 임계값 n→m> | 기준 문서 오탐 <n>줄 · AI 문서 <n>편 중 <k>편 · 검증용 <k/n> |

바꿀 이유
- <보고 이름>: <한두 문장>

판정 기록 반영: <n>건 (오탐 <n>, 놓침 <n>)
```

채택 기준은 이렇다. 기준 문서 오탐 0줄, AI slop 문서 3편 이상 적중, 임계값을 한 단계 낮춰도 오탐 0, 검증용 표본에서도 적중. 사람이 쓴 문서에서 나오면 내린다.
