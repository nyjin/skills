# 검증과 유지보수

문서를 넘기기 전에 이 파일을 읽는다. 기계 검사, 사실 검증, 되말하기, 체크리스트 순서로 확인하고 결과를 보고한다.

## 목차

O-1 기계 검사를 돌린다 · O-2 사실을 재료와 대조한다 · O-3 독자 역할로 되말하게 한다 · O-4 유형별 체크리스트 · O-5 공통 체크리스트 · Q-1 정보는 한 곳에 두고 링크한다 · Q-2 쓰지 않는 기능은 지원 중단으로 표시한다 · Q-3 담당자와 갱신일을 남긴다 · 결과 보고 형식

## O-1 기계 검사를 돌린다

1. 문서 구조를 검사한다.

   ```bash
   uv run <스킬 디렉터리(SKILL.md 맨 위 ${CLAUDE_SKILL_DIR} 값)>/scripts/lint_doc.py <문서.md>
   ```

   `error`는 반드시 고친다. `warn`은 고치거나, 고치지 않는 이유를 보고에 적는다(예: 참조 문서라 H4가 필요함).
2. 용어집 위반을 찾는다. config `style.glossary`의 키(바꿔야 할 표기)마다 문서를 검색하고, 코드 블록 밖에서 나오면 값(통일 표기)으로 바꾼다.
3. 다이어그램 렌더링이 성공했는지 확인한다(visualization.md 렌더링 절차).
4. 링크가 가리키는 파일·앵커가 있는지 확인한다(상대 경로 링크).

왜: 사람이 놓치기 쉬운 형식 오류는 기계가 잡게 하고, 사람의 주의는 내용에 쓴다. [S4, S6, S3]

## O-2 사실을 재료와 대조한다

문서에 나온 명령어, 파일 경로, 설정 키, API 이름·경로, 환경 변수, 수치, 링크 주소를 하나씩 재료(코드, 설정 파일, 로그, 사용자 메모)와 대조한다. 링크는 주소가 실제로 그 대상을 가리키는지 확인한다(E-10).

- 재료에서 확인됨 → 그대로 둔다.
- 재료와 다름 → 재료 기준으로 고친다.
- 재료에 없음 → `TODO(확인 필요: <무엇을>)`로 바꾼다.
- 값의 의미(이 칸·변수에 무엇이 들어가는가)를 선언(이름·주석)만 보고 단정한 곳 → 수준을 밝히거나 값을 채우는 쪽을 확인한다(P-4).

명령어는 가능하면 실제로 실행해 본다. 실행이 위험하면(운영 데이터 변경 등) 실행하지 않고 `--help`나 dry-run으로 옵션만 확인한다.

왜: 기능이 글대로 동작하는지 직접 확인하는 것이 정확성을 지키는 유일한 방법이다. [S4, S2]

## O-3 독자 역할로 되말하게 한다

서브에이전트에게 config의 독자 역할을 주고 문서를 읽힌다. 다음 프롬프트를 쓴다.

```text
당신은 다음 독자다.
- 역할: <role>
- 수준: <level>
- 이미 아는 것: <knows>
- 이 문서에서 알고 싶은 것: <needs>
- 읽는 상황: <context>

아래 문서를 이 독자로서 처음 읽는다고 생각하고 답하라. 문서에 없는 지식으로 빈칸을 메우지 마라.
1. 이 문서의 핵심을 3줄로 요약하라.
2. 읽다가 막히거나 다시 읽어야 했던 곳을 인용하고 이유를 써라.
3. 이 독자로서 빠졌다고 느낀 정보를 써라.
4. 문서를 읽고 나서 당신이 할 수 있게 된 일을 한 문장으로 써라.
5. 아래 항목마다 해당하는 곳이 있으면 절 이름과 인용을 쓰고, 없으면 "해당 없음"이라고 써라. 판단이 서지 않으면 해당 없음으로 둔다.
   - 명사 조각으로 끝나는 문장: 산문 문단의 문장이 서술어 없이 명사로 끝난다
   - 근거 없이 늘어놓은 결정: 결정을 셋 이상 잇달아 선언하는데 근거가 없거나 같은 틀의 근거가 반복된다
   - 독자가 풀 수 없는 번호 참조: 규칙 ID, 다른 문서의 절 번호를 내용 없이 쓴다
   - 본문을 차지한 작업 메모: 확인 필요, 남은 일 같은 메모가 여러 절에 흩어지거나 본문보다 길다
   - 본문에 남은 작성 과정: 변경 이력, "원래는 …였으나" 같은 작성 과정이 본문에 있다
   - 제목의 질문에 답하지 않은 절: 제목이 질문인데 절 안에 답이 없다
   - 고치면서 바뀐 뜻: (고친 문장 목록을 줄 때만) 고친 뒤 조건, 주체, 부정이 바뀌었다

<문서 전문>
<고친 문장 목록: 고치기 전 → 고친 뒤 (5번 마지막 항목용, 있을 때만)>
```

답을 받으면 다음을 비교한다.

- 3줄 요약이 작성 의도(개요 E-1)와 같은가. 다르면 개요와 첫 섹션을 고친다.
- 막힌 곳마다 원인을 찾는다: 정의되지 않은 용어(C-5, I-1), 빠진 단계(L-2), 지시어(F-4), 구조(E-6).
- 4번 답이 문서의 목표와 같은가.
- 5번 답은 slop-rubric.md의 판단 항목 판정이다. 해당한 곳을 루브릭 정의와 대조해 맞으면 고치거나 남길 이유를 정하고, 판단 목록 JSON에 옮긴다.

고친 뒤 막힌 곳이 둘 이상이었으면 한 번 더 되말하게 한다. 두 번째에도 같은 곳에서 막히면 보고에 남긴다.

**직접 수행(서브에이전트를 쓸 수 없을 때).** 재료와 작성 의도를 내려놓고 문서 파일만 처음부터 다시 읽는다. 위 프롬프트의 독자라고 가정하고 네 질문의 답을 실제로 써 본다. 특히 2번은 "독자의 `knows`에 없는 용어", "앞 문맥을 기억해야 이해되는 문장", "다음에 무엇을 할지 알 수 없는 단계"를 하나씩 찾는다. 보고에는 "되말하기: 직접 수행"으로 적는다. 다른 사람이 읽는 것보다 약하므로, 가능하면 사용자에게 실제 독자 리뷰를 권한다.

왜: 작성자는 자기 글을 의도대로 읽는다. 다른 사람이 요약한 내용이 의도와 같아야 전달된 것이다. [S6, S4]

## O-4 유형별 체크리스트

**학습**
- [ ] 학습 목표가 맨 앞에 있다.
- [ ] 사전 준비에 버전·권한·데이터가 빠짐없다.
- [ ] 모든 단계가 번호 목록이고 한 단계에 한 동작이다.
- [ ] 예제를 그대로 실행하면 동작한다(또는 TODO로 표시됨).
- [ ] 결과 확인 방법과 다음 단계가 있다.

**how-to**
- [ ] 이 가이드로 할 수 있는 일이 첫 문장에 있다.
- [ ] 절차의 각 단계에 확인 방법이 있다.
- [ ] 실패했을 때 볼 곳이 있다.

**트러블슈팅**
- [ ] 증상에 실제 에러 메시지·로그가 원문 그대로 있다.
- [ ] 증상과 원인을 구분했다.
- [ ] 해결책이 바로 실행할 수 있는 명령·설정이다.
- [ ] 해결 원리를 한두 문장으로 썼다.
- [ ] 해결됐는지 확인하는 방법이 있다.
- [ ] 환경별 차이를 다뤘다(해당할 때).

**참조**
- [ ] 모든 항목이 같은 구조(시그니처 → 매개변수 → 반환값 → 오류 → 예제)다.
- [ ] 매개변수 표에 타입·필수·기본값이 있다.
- [ ] 인증 같은 사전 정보가 앞에 있다.
- [ ] 항목마다 앵커가 있다.

**설명**
- [ ] 첫 문장이 한 줄 정의다.
- [ ] 풀려는 문제(등장 배경)가 원리보다 앞에 있다.
- [ ] 다이어그램이 있고 앞뒤 문장이 있다.
- [ ] 대안과 비교했다.

**설계·ADR(Architecture Decision Record, 아키텍처 결정 기록)**
- [ ] 요약에 결정 내용이 한 문장으로 있다.
- [ ] 목표와 함께 비목표(하지 않을 것)가 있다.
- [ ] 대안을 같은 기준으로 표에서 비교했다.
- [ ] 결정의 이유와 감수하는 비용이 있다.
- [ ] 아키텍처 다이어그램이 있다.

**런북**
- [ ] 언제 이 런북을 쓰는지(발동 조건)가 맨 앞에 있다.
- [ ] 위험한 단계 바로 앞에 경고가 있다.
- [ ] 명령어를 그대로 복사해 실행할 수 있다.
- [ ] 롤백 절차가 있다.
- [ ] 단계마다 성공 확인 방법이 있다.

**코드 조사 보고**
- [ ] 결론이 첫 목록에 있고, 근거 수준을 넘어 단정하지 않는다(P-4).
- [ ] 맨 위에 저장소와 브랜치 또는 커밋 기준이 있다.
- [ ] 선언(이름·주석)과 실제 값이 다른 곳이 주의할 점에 있다.

**포스트모템**
- [ ] 요약에 무엇이, 얼마 동안, 누구에게 영향을 줬는지 있다.
- [ ] 영향이 수치로 있다(시간, 건수, 비율).
- [ ] 타임라인에 시각(시간대 포함)과 사건이 있다.
- [ ] 원인과 유발 요인을 구분했다.
- [ ] 재발 방지 조치마다 담당자와 기한이 있다.
- [ ] 개인을 탓하는 표현이 없다.

## O-5 공통 체크리스트

- [ ] 제목 아래 개요가 있다 (E-1).
- [ ] 결론·가치가 배경보다 앞에 있다 (E-2).
- [ ] 한 문서 한 주제다 (E-3).
- [ ] 제목만 읽어도 내용을 알 수 있다 (E-5).
- [ ] 독자가 모르는 개념은 정의했다 (C-5).
- [ ] 수치·기준이 있고 지시어가 없다 (F-2, F-4).
- [ ] 한 개념 한 용어, 용어집을 지켰다 (H-1).
- [ ] 어조가 하나다 (H-5).
- [ ] 절차는 독자가 주체다 (J-1).
- [ ] 위험한 단계 앞에 경고가 있다 (P-2).
- [ ] 코드 블록에 언어가 있고 설명이 앞에 있다 (L-5).
- [ ] 다이어그램 앞뒤에 문장이 있다 (M-3).
- [ ] 모든 수치에 출처(재료)가 있고, 같은 대상의 수치가 서로 맞는다 (P-1).
- [ ] 절끼리 내용이 겹치지 않고, 절은 자료 종류가 아니라 주제로 나뉜다 (E-3).
- [ ] `redundancy.py`의 고칠 곳 목록(강한 반복, 퍼진 식별자, 코드·그림 옮김)을 모두 정리했거나, 남긴 이유를 보고에 적었다 (E-12).
- [ ] 요약 항목과 본문 절이 1:1로 맞는다 (E-1).
- [ ] 문서 밖을 가리키는 참조(티켓, PR, 저장소, 문서)에 확인한 주소의 링크가 있다. 링크 없는 번호만 남은 곳이 없다 (E-10).
- [ ] 문서 어디에도(부록·접은 블록 포함) 파일 경로·라인 근거와 소스 파일 링크가 없고, 코드는 이름과 역할 설명에 필요한 만큼만 있다. 근거는 "참고" 절의 저장소·PR·티켓 링크로 모았다 (E-11).

구조 장치(요약, 목차, FAQ)를 모두 갖춰도 위 세 항목이 깨지면 좋은 문서가 아니다. 사례는 exemplar-notes.md의 "반례" 절에 있다.

## Q-1 정보는 한 곳에 두고 링크한다

같은 내용(설정 방법, 용어 정의)을 여러 문서에 복사하지 않는다. 가장 알맞은 문서 한 곳에 쓰고 다른 곳에서는 링크한다. 문서를 고칠 때 같은 내용이 다른 곳에도 있으면 사용자에게 알린다.

왜: 복사된 내용은 한쪽만 고쳐져 서로 어긋난다. [S2]

## Q-2 쓰지 않는 기능은 지원 중단으로 표시한다

더 이상 쓰지 않는 기능·API·절차를 문서에서 지우기 전에 "지원 중단(deprecated)"으로 표시하고 대체 방법을 링크한다. 완전히 없어진 뒤에 삭제한다.

왜: 말없이 사라지면 아직 쓰는 사람이 길을 잃고, 표시가 없으면 새 사람이 낡은 방법을 쓴다. [S10]

## Q-3 담당자와 갱신일을 남긴다

저장소 문서는 git 이력이 대신하므로 생략해도 된다. Confluence·HTML처럼 이력이 잘 보이지 않는 곳에서는 문서 맨 아래에 담당자(팀)와 마지막 확인일을 적는다.

왜: 문서가 낡았는지, 누구에게 물어야 하는지 독자가 판단할 수 있어야 한다. [S2, S4, S7]
