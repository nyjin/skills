# 참고 문서 분석 노트

`exemplars/`의 본보기를 쓸 때 참고한 실제 한국어 문서(이하 참고 문서)의 분석이다. 본보기를 고치거나 새 유형을 추가할 때 읽는다. 원문은 옮기지 않았고, 무엇이 좋은지만 원칙 ID에 연결해 적었다. 문서를 작성하는 평소 흐름에서는 이 파일을 읽지 않아도 된다.

## 목차

유형별 참고 문서 · 공통 구조 패턴 · 반례: 구조를 갖췄지만 좋은 문서가 아닌 경우

## 유형별 참고 문서

### 튜토리얼

- 주: [토스페이먼츠 「주문서형 결제 연동하기」](https://docs.tosspayments.com/guides/v2/payment-widget/integration)
- 보조: [앱인토스 「React Native 시작하기」](https://developers-apps-in-toss.toss.im/ai-vibe-coding/tutorials/react-native)

가져온 점
- 개요 다음에 전체 단계 지도(4단계)를 먼저 보여 준다 → E-1, E-2
- 사전 준비를 별도 절로 두고, 단계마다 실행 위치(클라이언트/서버)를 표시한다 → D-2, F-3
- 결과 확인에서 성공 응답과 실패 응답을 모두 보여 준다 → N-1, N-4
- 단계마다 "이렇게 보이면 다음으로" 판정 문구를 둔다(보조 문서) → N-2

보완한 점
- 원문은 핵심 코드가 인터랙티브 패널에만 있다. 본보기는 코드를 본문 코드 블록으로 꺼내고 단계를 실제 H2로 만들었다.

### How-to

- 주: [토스페이먼츠 「장애 인지 가이드」](https://docs.tosspayments.com/guides/v2/status-page)
- 보조: [포트원 「웹훅 연동하기」](https://developers.portone.io/opi/ko/integration/webhook/readme-v2)

가져온 점
- 첫 문단에 목적, 쓰임, 필요한 이유를 모두 담는다 → E-1
- 번호를 붙인 명령형 H2로 절차를 보인다 → E-5, L-1
- 응답 시간 같은 기준을 수치로 정한다 → F-2
- 보안 위험에는 경고와 대응책을 함께 둔다 → P-2
- 자주 묻는 질문은 본문과 분리한다 → L-9

보완한 점
- 원문에는 설정이 끝났는지 검증하는 명령이 없다. 본보기는 "확인 방법" 절을 넣었다.

### 트러블슈팅

- 주: [카카오 developers 「FAQ › 문제 해결」](https://developers.kakao.com/docs/latest/ko/kakaologin/faq)
- 보조: [NHN Cloud 「문제 해결 가이드」](https://docs.nhncloud.com/ko/Compute/Instance/ko/troubleshooting-guide/), [NAVER D2 「사라진 get_table RPC 복원기」](https://d2.naver.com/helloworld/7314597), [Qiita 「負荷の原因を切り分ける方法」](https://qiita.com/k0kubun/items/8ab1dfa7c0359d8e618d)(구조만)

가져온 점
- 증상과 에러 메시지를 그대로 제목에 쓴다 → E-5
- 정상 동작과 문제를 구분한 뒤 원인을 분류한다 → D-2
- 원인 한 문장 다음에 바로 명령을 둔다(NHN) → G-1, L-2
- 해결안 여러 개를 판단 근거와 함께 표로 비교한다(D2) → S-2, L-4
- 진단을 "~인 경우 / 아닌 경우" 쌍으로 나누고, 끝에 같은 분기를 그림으로 다시 정리한다(Qiita) → L-2, M-1

보완한 점
- **세 국내 문서 모두 "해결 확인" 단계가 없었다.** 본보기는 해결 확인과 재발 방지 절을 넣었다.

### 참조

- 주: [카카오 developers 「REST API」](https://developers.kakao.com/docs/latest/ko/kakaologin/rest-api), [「에러 코드」](https://developers.kakao.com/docs/latest/ko/kakaologin/trouble-shooting)
- 대비: [토스페이먼츠 「API 에러 코드」](https://docs.tosspayments.com/reference/error-codes)

가져온 점
- API마다 기본 정보 → 요청 → 응답 → 예제의 같은 틀을 반복한다 → E-6
- 인증 같은 사전 정보를 앞에 모으고 시퀀스 다이어그램으로 보인다 → D-2, M-1
- 필드 표에 이름·타입·필수·설명이 있다 → L-4
- 에러 코드마다 원인과 해결 방법 칼럼이 있다 → P-3

대비 사례
- 조치 칼럼이 없는 에러 코드 표는 "이 코드가 무슨 뜻인지"는 알려 주지만 "그래서 무엇을 할지"는 알려 주지 않는다. 본보기는 대처 칼럼을 필수로 했다.

### 설명

- 주: [카카오 안정성 보고서 프롤로그](https://t1.kakaocdn.net/kakaocorp/kakaocorp/admin/promise/report/KakaoReliabilityReport_online.pdf)(5~7쪽)
- 보조: [당근 「Aurora MySQL 인덱스 DDL이 Reader 버퍼풀을 비운다?」](https://medium.com/daangn/aurora-mysql-%EC%9D%B8%EB%8D%B1%EC%8A%A4-ddl%EC%9D%B4-reader-%EB%B2%84%ED%8D%BC%ED%92%80%EC%9D%84-%EB%B9%84%EC%9A%B4%EB%8B%A4-16c6328dea50)

가져온 점
- 메시지 한 건이 거치는 과정을 단계로 나누고, 그림 하나로 전체를 보인다 → E-4, M-1
- 용어 풀이를 본문 옆(사이드바)으로 빼서 흐름을 끊지 않는다 → C-5, L-9
- 주장마다 수치를 붙이고, 재현 실험으로 검증한다(보조) → F-2, P-1
- 진단 쿼리처럼 부하를 줄 수 있는 작업에는 경고를 둔다(보조) → P-2

보완한 점
- 보조 문서의 목차는 조사 순서(발단 → 현상 → 재현 → 원인)라 설명 문서 골격으로는 맞지 않다. 골격은 주 문서에서, 수치와 검증 방식만 보조 문서에서 가져왔다.

### 설계·ADR

- 주: [당근 「웹뷰 다음의 레일을 깔다: 당근이 Lynx를 선택한 이유」](https://medium.com/daangn/%EC%9B%B9%EB%B7%B0-%EB%8B%A4%EC%9D%8C%EC%9D%98-%EB%A0%88%EC%9D%BC%EC%9D%84-%EA%B9%94%EB%8B%A4-%EB%8B%B9%EA%B7%BC%EC%9D%B4-lynx%EB%A5%BC-%EC%84%A0%ED%83%9D%ED%95%9C-%EC%9D%B4%EC%9C%A0-34dd50abbfb7)
- 보조: [당근 「당근페이 백엔드 아키텍처가 걸어온 여정」](https://medium.com/daangn/%EB%8B%B9%EA%B7%BC%ED%8E%98%EC%9D%B4-%EB%B0%B1%EC%97%94%EB%93%9C-%EC%95%84%ED%82%A4%ED%85%8D%EC%B2%98%EA%B0%80-%EA%B1%B8%EC%96%B4%EC%98%A8-%EC%97%AC%EC%A0%95-98615d5a6b06)(사용자 추천), [토스 「App Router의 장점은 우리에게도 장점일까요?」](https://toss.tech/article/52999), [Zenn 「データ取り込み方式の選び方」](https://zenn.dev/ivry/articles/data-ingestion-pattern-guide)(구조만)

가져온 점
- 결정 기준(조건 5개)을 목록으로 먼저 고정하고, 대안을 모두 그 기준에 대어 본다. 비목표도 적는다 → S-2
- 대안의 장점을 먼저 인정하고 "우리 조건에 맞는가"로 배제한다 → S-2
- 결정이 유효한 전제와 한계를 스스로 적는다 → S-1, P-1
- 성공 기준을 미리 정하고, 결과를 수치로 보고한다. 기대보다 작았던 결과도 적는다 → F-2
- 문서에 갱신일을 적어 살아 있는 문서로 관리한다 → Q-3
- 도입부 한 문단에 여러 단계의 결정 경로를 먼저 보인다(당근페이) → E-1
- 앞 단계의 문제에 번호를 붙이고, 다음 단계의 목표와 "적용 이후"에서 그 번호로 해결을 확인한다(당근페이) → E-6, S-1
- 비교 대상 구조도는 같은 캡션 틀로, 같은 위치에 둔다(당근페이) → M-3, L-8
- 결론을 맨 앞에 둔다. 도입하지 않기로 한 결정도 기록한다(토스) → E-2, S-1
- 관점별 비교 표 → 선택지마다 같은 틀 → "어떻게 고르나" 결정 표 → 권장 시작 순서(Zenn) → S-2, E-6

보완한 점
- 질문형 제목은 평서문으로 바꿨다(E-5).
- 수치를 그림에만 두지 않고 본문 문장에도 적었다(당근페이의 아쉬운 점).

- 주: [데브시스터즈 「장애 대응 원칙과 방법」](https://tech.devsisters.com/posts/incident-management-principles/)

- 공개된 국내 런북에는 명령어 수준의 절차가 거의 없다. 본보기는 명령, 기대 결과, 롤백을 단계마다 넣었다.

### 포스트모템

- 주: [토스페이먼츠 DDoS 장애 보고서](https://static.tosspayments.com/public/tosspayments_issue_report_251016.pdf)
- 보조: 데브시스터즈 문서의 포스트모템 양식, [Zenn 「Error 526」](https://zenn.dev/unsoluble_sugar/articles/6a3fd085a60ec6)(구조만)

가져온 점
- 영향을 기간, 범위, 평시 대비 배수로 비교한 표 → F-2, L-4
- 차수별 조치와 기한별 계획 → 재발 방지 조치의 담당·기한
- 공개하지 않는 정보가 있으면 그 사유를 밝힌다 → P-1
- 직접 원인(Root Cause)과 유발 요인(Trigger)을 분리한다(데브시스터즈) → S-1
- H2를 "범주: 결론" 형태로 쓴다(Zenn) → E-5
- 영향 시간처럼 핵심 수치를 제목에 넣는다(Zenn) → F-2

보완한 점
- **분 단위 타임라인을 갖춘 한국어 공개 보고서는 찾지 못했다.** 본보기는 시각(시간대 표기) | 사건 표를 넣었다.

### 비개발 독자용 설명

- 주: [삼성SDS 「Agentic AI 시대, 기업의 AI 활용 전략은?」](https://www.samsungsds.com/kr/insights/ai-strategy-for-your-company.html)(사용자 추천)
- 보조: [플래텀 「AI가 인용하는 글, 사람이 읽는 글」](https://platum.kr/archives/280126)

가져온 점
- 리드 한 문장 → 요약 상자(결론 / 요소 / 효과 / 한 줄 메시지) → 근거 고지 순서로 연다. 의사결정자는 요약에서 읽기를 멈춰도 된다 → E-1, E-2, C-4
- "바깥(시장·변화)에서 안(우리 선택)"으로 좁혀 가고, 1부 마지막 절이 2부의 질문을 연다 → E-4
- 같은 수준의 소제목을 결론 문장으로 통일해, 소제목만 이어 읽어도 요약이 된다 → E-5
- 그림마다 `[그림 N] 무엇을 보여 주는가 (출처)` 형식을 지킨다 → L-8, M-3
- 주장 바로 뒤에 한계를 둔다 → P-1, S-1
- 독자의 다음 행동으로 설명을 연결한다("누구에게 물어야 하나")(보조) → C-3

보완한 점
- 원문은 요약 상자와 본문 구성이 어긋난다. 본보기는 요약 항목과 본문 H2를 1:1로 맞췄다.
- 원문의 번호 소제목은 실제 제목 태그가 아니어서 목차로 훑을 수 없다. 본보기는 H2·H3로 만들었다.

## 공통 구조 패턴

여러 참고 문서에서 반복해서 나온 구조다. 본보기와 템플릿에 반영했다.

1. **도입부에서 전체 지도를 먼저 준다.** 요약 상자, 결론 문단, 단계 지도, 번호 목차 중 하나로 문서의 끝까지를 첫 화면에 보인다.
2. **요약을 앞과 뒤에 대칭으로 둔다.** 결론 절은 도입의 요약을 다시 짚고, 새 주장을 더하지 않는다.
3. **같은 성격의 하위 단위는 같은 틀로 반복한다.** 두 번째 단위부터 독자가 구조를 예측한다.
4. **절과 절 사이에 이음매를 둔다.** 절 첫 문단에 이 절에서 다룰 것을 나열하거나, 절 끝에서 다음 절의 문제를 예고한다.
5. **권고 뒤에 한계를 둔다.** 원칙마다 짝이 되는 위험을 적거나, 회고에서 남은 문제를 인정한다.
6. **도입부 세트(일본 글).** 요약(TL;DR) → 독자·동기·범위 → 전제(환경, 버전, 기준 시점).
7. **용어 풀이와 보충은 접어 둔다.** 본문은 주 독자 수준으로 쓰고, 다른 수준의 독자를 위한 풀이는 접기 블록에 둔다(R-5 생략 대 상세의 구조적 해법).
8. **설명 문서와 실습 문서를 나누고 서로 링크한다.**

## 반례: 구조를 갖췄지만 좋은 문서가 아닌 경우

사용자가 공유한 글 가운데 두 편은 목차, 요약, FAQ 같은 구조 장치를 모두 갖췄지만 생성형 도구로 쓴 흔적이 있어 참고 문서에서 내용은 제외했다. 구조 패턴("원칙 N가지"를 같은 틀로 반복, 원칙과 1:1로 짝지은 한계 절, 절마다 이음 문단 → 항목 → 정리 한 줄)만 참고했다.

- 위키독스 「쿠버네티스 pod, 2026년 효율적인 컨테이너 관리 핵심 5가지」
- 티스토리 「데브옵스 도입 성공 전략」

드러난 문제와 대응한 검증 항목(review-checklist.md O-5)

| 문제 | 검증 항목 |
|---|---|
| 출처가 없거나 서로 맞지 않는 수치 | 모든 수치에 출처(재료)가 있다 |
| 같은 주제가 여러 절에 반복 | 절끼리 내용이 겹치지 않는다 |
| 절을 주제가 아니라 자료 종류(통계, 전문가 의견)로 나눔 | 절은 주제로 나눈다 |
| 요약과 본문이 어긋남 | 요약 항목과 본문 절이 1:1로 맞는다 |
