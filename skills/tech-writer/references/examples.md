# Don't/Do 예시

원칙을 적용할 때 모양이 잘 떠오르지 않으면 해당 원칙 ID의 예시만 찾아 읽는다. 예시는 원칙 ID(`E-1`) 뒤에 소문자를 붙여(`E-1a`) 구분한다. 형식은 ❌ 고치기 전, ✅ 고친 뒤, 왜(한 줄)다.

예시의 소재(정산 배치, 주문 API, 배포 파이프라인)는 설명을 위해 만든 것이다. 실제 문서에는 재료에서 확인한 이름과 수치만 쓴다.

## 목차

E 정보 구조 · F 명확성·구체성 · G 간결성 · H 일관성·용어 · I 전문 용어·약어 · J 능동·주체 · L 포매팅 · M 시각화 · N 코드 예제 · P 정확성·안전 · S 왜·결정 맥락

## E 정보 구조

### E-1a 개요가 할 수 있는 일을 말한다
```markdown
❌
# 정산 배치 재처리
이 문서는 정산 배치에 관한 문서입니다. 정산 배치는 2022년에 처음 만들어졌고 여러 번 개선되었습니다.

✅
# 정산 배치 재처리
실패한 날짜의 정산을 다시 계산하고 결제사에 다시 보내는 방법을 설명합니다. 이 문서를 따라 하면 15분 안에 하루치 정산을 복구할 수 있습니다.
```
왜: 첫 두 문장을 읽고 이 문서가 지금 자기에게 필요한지 판단할 수 있어야 한다.

### E-2a 연혁보다 얻는 것을 먼저
❌ 주문 캐시는 2023년 트래픽 증가로 도입이 검토되었고, 여러 방식을 비교한 끝에 Redis를 선택했습니다. 주문 조회 응답 시간이 줄었습니다.
✅ 주문 캐시를 쓰면 주문 조회 p95 응답 시간이 420ms에서 60ms로 줄어듭니다. 도입 배경과 방식 비교는 "설계 배경" 절에 있습니다.
왜: 독자가 계속 읽을 이유는 배경이 아니라 자기에게 남는 결과다.

### E-3a H4가 나오면 주제를 나눈다
```markdown
❌
# 주문 서비스 가이드
## 배포
### 운영 배포
#### 카나리 배포 설정
## 장애 대응
### DB 장애
#### 읽기 복제본 전환

✅
# 주문 서비스 배포하기
## 사전 준비
## 카나리 배포
## 전체 배포

(장애 대응은 별도 문서 "주문 서비스 장애 런북"으로 분리하고 링크)
```
왜: 배포와 장애 대응은 다른 상황에 다른 독자가 읽는다. 한 문서에 섞으면 둘 다 찾기 어렵다.

### E-4a 트러블슈팅은 문제부터 확인까지
```markdown
❌
## 원인 분석
## 배경 지식: 커넥션 풀이란
## 에러 메시지
## 해결

✅
## 증상
## 원인
## 해결 방법
## 해결 확인
```
왜: 트러블슈팅 독자는 증상에서 출발한다. 배경 지식은 원인 설명 안에 짧게 넣는다.

### E-5a 제목은 키워드가 든 평서문
❌ `## 배포가 안 될 때는?`
✅ `## 이미지 풀 실패로 배포가 멈출 때`
왜: 물음표 제목은 내용을 숨기고, "배포가 안 될 때"는 원인을 구분하지 못한다.

### E-5b 같은 수준의 제목은 같은 형태로
❌ `## 설치` / `## 설정하는 방법` / `## 실행하기`
✅ `## 설치하기` / `## 설정하기` / `## 실행하기`
왜: 형태가 섞이면 같은 수준의 항목인지 한눈에 알 수 없다.

### E-6a 코드 앞에 설명을 둔다
````markdown
❌
```bash
kubectl rollout undo deployment/order-api -n order
```
이 명령은 직전 버전으로 되돌립니다.

✅
직전 버전으로 되돌립니다.
```bash
kubectl rollout undo deployment/order-api -n order
```
````
왜: 무엇을 하는 명령인지 모르고 읽으면 독자는 명령을 해석부터 해야 한다.

### E-7a 긴 참조 문서에는 목차와 앵커
❌ API 40개를 H2 하나 아래에 이어서 나열하고, 다른 문서에서는 "주문 API 문서 참고"로만 링크한다.
✅ 맨 위에 목차를 두고 API마다 H3 앵커를 만든다. 다른 문서에서는 `order-api.md#주문-취소`처럼 해당 항목으로 바로 링크한다.
왜: 참조 문서는 처음부터 읽히지 않고 찾아서 읽힌다.

### E-8a 독자가 모르는 조건은 빠뜨리지 않는다
❌ `retry-count`: 재시도 횟수입니다.
✅ `retry-count`: 결제사 응답이 5초 안에 오지 않을 때 다시 보내는 횟수입니다. 기본값은 3이고, 3번 모두 실패하면 주문을 `PAYMENT_PENDING` 상태로 둡니다.
왜: 언제 재시도하는지, 끝나면 어떻게 되는지가 빠지면 독자는 값을 바꿀 수 없다.

### E-8b 독자에게 필요 없는 이야기는 뺀다
❌ 이 문제를 찾느라 팀원 세 명이 이틀 밤을 새웠고, 처음에는 네트워크 문제라고 생각해 방화벽 설정을 모두 뒤졌습니다.
✅ 원인은 커넥션 풀 크기(10)가 배치 동시 실행 수(16)보다 작았기 때문입니다.
왜: 작성자의 고생은 독자가 문제를 푸는 데 도움이 되지 않는다(회고 문서가 아니라면).

### E-9a 한 문단에 소주제 하나
❌ 한 문단에 배치 스케줄, 실패 알림 설정, 결제사 API 키 갱신 방법을 이어서 쓴다.
✅ 세 가지를 각각의 문단(또는 H3)으로 나누고, 문단 첫 문장에 그 문단의 요지를 쓴다.
왜: 문단 첫 문장만 훑는 독자도 무엇이 어디 있는지 알 수 있어야 한다.

## F 명확성·구체성

### F-1a 확인된 동작은 단정한다
❌ 설정을 바꾸면 재시작이 필요할 수도 있습니다.
✅ 설정을 바꾼 뒤 `order-api`를 재시작해야 적용됩니다.
왜: "필요할 수도"라고 쓰면 독자는 재시작할지 말지 다시 판단해야 한다.

### F-2a 처리량 기준을 수치로
❌ 주문이 몰리면 정산 배치가 늦어질 수 있습니다.
✅ 주문이 시간당 5만 건을 넘으면 정산 배치가 30분 이상 늦어집니다.
왜: "몰리면"으로는 언제 대응해야 하는지 정할 수 없다.

### F-2b 모르는 수치는 지어내지 않는다
❌ 디스크 사용률이 높으면 알림이 옵니다.
✅ 디스크 사용률이 TODO(확인 필요: 알림 임계값)를 넘으면 `#order-alert` 채널로 알림이 옵니다.
왜: 수치가 필요하지만 재료에 없으면 비워 두는 것이 지어내는 것보다 안전하다.

### F-3a 어디에서 확인하는지 쓴다
❌ 배치가 멈추면 로그부터 봅니다.
✅ 배치가 멈추면 Kibana의 `order-api-*` 인덱스에서 `level:ERROR AND traceId:<요청 ID>`로 검색하세요.
왜: "로그"는 서버 파일, 수집 시스템, 대시보드 중 어디인지 알려 주지 않는다.

### F-4a 지시어 대신 이름을 쓴다
❌ 위 설정을 바꾼 뒤 여기를 참고해 배포하세요.
✅ `batch.chunk-size`를 바꾼 뒤 "정산 배치 배포하기" 문서를 따라 배포하세요.
왜: "위 설정", "여기"는 독자가 앞 문맥을 기억하고 링크를 눌러 봐야만 뜻을 안다.

### F-5a 이중 부정을 긍정으로
❌ 점검 공지 없이 배포하지 않으면 안 됩니다.
✅ 배포 전에 점검 공지를 올립니다.
왜: 부정이 겹치면 한 번에 읽히지 않고, 운영 절차에서는 반대로 읽힐 위험이 있다.

### F-6a 만든 값의 쓰임을 미리 알린다
```markdown
❌
1. 결제사 콘솔에서 API 키를 발급합니다.
...
5. 앞에서 받은 키를 넣습니다.

✅
1. 결제사 콘솔에서 API 키를 발급합니다. 이 키는 5단계에서 시크릿으로 등록합니다.
...
5. 1단계에서 발급한 API 키를 `PG_API_KEY` 시크릿으로 등록합니다.
```
왜: 독자가 값을 어디에 쓰는지 모르면 받아 둔 값을 잃어버리고, 어디서 받았는지 모르면 문서를 거슬러 올라간다.

## G 간결성

### G-1a 절차 한 문장에 동작 하나
❌ 설정 파일을 수정하고 저장한 다음 변경이 반영됐는지 확인하고 필요하면 서버를 재시작해야 합니다.
✅
1. `application.yml`을 수정해 저장합니다.
2. `/actuator/env`에서 값이 바뀌었는지 확인합니다.
3. 값이 그대로면 `order-api`를 재시작합니다.
왜: 한 문장에 동작이 넷이면 독자가 하나를 빠뜨린다.

### G-1b 정의와 부연을 나눈다
❌ 멱등 키는 같은 요청이 여러 번 들어와도 결제가 한 번만 일어나게 하려고 클라이언트가 요청마다 만들어 헤더에 넣는, 24시간 동안 유지되는 고유 문자열입니다.
✅ 멱등 키는 같은 결제 요청을 한 번만 처리하게 하는 고유 문자열입니다. 클라이언트가 요청마다 만들어 `Idempotency-Key` 헤더에 넣고, 서버는 24시간 동안 기억합니다.
왜: 정의가 한 문장에 담겨야 독자가 "무엇인지"를 먼저 잡는다.

### G-2a 진행 안내 문구를 지운다
❌ 앞서 말씀드린 것처럼, 이제부터는 롤백 방법에 대해 알아보도록 하겠습니다.
✅ (문장을 지우고 "롤백하기" 제목만 남긴다)
왜: 제목이 이미 하는 일을 문장이 다시 할 필요는 없다.

### G-3a 겹친 뜻과 꾸밈을 지운다
❌ 배포가 성공적으로 완료되었으며, 매우 안정적으로 잘 동작하고 있습니다.
✅ 배포가 끝났습니다. 배포 후 30분 동안 오류율은 0.1% 이하입니다.
왜: "성공적으로 완료"는 겹친 말이고, "매우 안정적"은 수치로 바꿀 때 정보가 된다.

### G-4a 진행·수행 대신 동사
❌ 데이터 백업 진행 후 스키마 변경 수행 및 애플리케이션 재기동 처리가 필요합니다.
✅ 데이터를 백업하고, 스키마를 바꾼 뒤, 애플리케이션을 다시 시작합니다.
왜: 명사로 뭉친 문장은 누가 무엇을 하는지 감춘다.

## H 일관성·용어

### H-1a 한 대상에는 한 이름
❌ 정산 배치가 실패하면 settlement job 로그를 보고, 정산 작업을 다시 실행하세요.
✅ 정산 배치가 실패하면 정산 배치 로그를 보고, 정산 배치를 다시 실행하세요.
왜: 이름이 셋이면 독자는 대상도 셋이라고 생각한다.

### H-2a 공식 표기를 쓴다
❌ k8s 클러스터의 postgres에 접속합니다.
✅ Kubernetes 클러스터의 PostgreSQL에 접속합니다.
왜: 비공식 표기는 검색되지 않고, 처음 보는 독자는 같은 것인지 확신하지 못한다.

### H-3a 외래어는 정책 하나로
❌ (한 문서 안에서) 프론트엔드 팀과 프런트엔드 저장소를 함께 언급한다.
✅ config `loanword_policy: usage`에 따라 문서 전체에서 "프론트엔드"로 쓴다.
왜: 표기가 섞이면 어느 쪽이 맞는지가 아니라 왜 다른지를 고민하게 만든다.

### H-4a 목록 항목의 형태를 맞춘다
❌ 배포 전 확인 사항: 마이그레이션 적용 / 알림 채널을 확인합니다 / 담당자 대기 중인지
✅ 배포 전 확인 사항: 마이그레이션 적용 여부 / 알림 채널 연결 여부 / 담당자 대기 여부
왜: 형태가 다르면 항목의 성격도 다르다고 오해한다.

### H-5a 어조를 섞지 않는다
❌ 배포 전에 점검 공지를 올리세요. 공지가 올라가면 배포를 시작해요. 배포가 끝나면 모니터링한다.
✅ 배포 전에 점검 공지를 올립니다. 공지가 올라가면 배포를 시작합니다. 배포가 끝나면 30분 동안 오류율을 확인합니다.
왜: 어조가 바뀌면 여러 사람이 이어 붙인 문서처럼 보여 신뢰가 떨어진다.

## I 전문 용어·약어

### I-1a 독자가 모르는 용어는 풀어 쓴다
❌ (독자: PM) 정산 API는 at-least-once 보장이라 컨슈머 쪽 멱등 처리가 필수입니다.
✅ (독자: PM) 정산 결과는 네트워크 문제로 결제사에 두 번 갈 수 있습니다. 그래서 받는 쪽이 같은 정산을 한 번만 반영하도록 처리해 두었습니다.
왜: PM에게 필요한 것은 전달 보장 방식의 이름이 아니라 그 결과(중복 가능성과 대비책)다.

### I-2a 약어는 처음에 풀어 쓴다
❌ DLQ(Dead Letter Queue, 처리에 실패한 메시지를 모아 두는 큐)에 쌓인 메시지는 매일 확인합니다.
✅ 처리에 실패한 메시지를 모아 두는 큐(Dead Letter Queue, DLQ)를 매일 확인합니다. 이후 문단에서는 DLQ로만 쓴다.
왜: 약어를 처음 보는 독자는 검색부터 해야 한다.

### I-3a 은어를 실제 동작으로
❌ 배포 태우고 나서 헬스체크 찔러 보고 이상 없으면 트래픽 붙이세요.
✅ 배포한 뒤 `/health`에 요청을 보내 200 응답을 확인하고, 로드 밸런서에 새 인스턴스를 추가하세요.
왜: "태우다", "찌르다", "붙이다"는 팀마다 뜻이 다르고 처음 온 사람은 알 수 없다.

## J 능동·주체

### J-1a 도구가 아니라 독자를 주어로
❌ 이 스크립트는 정산 데이터의 정합성 검증을 수행합니다.
✅ 이 스크립트를 실행하면 정산 데이터가 주문 데이터와 맞는지 검증할 수 있습니다.
왜: 독자가 할 일(실행)과 얻는 것(검증)이 드러나야 한다.

### J-1b 수동형 지시를 능동형으로
❌ 배포 전에 마이그레이션이 적용되어 있어야 합니다.
✅ 배포 전에 마이그레이션을 적용하세요.
왜: 수동형 지시에서는 누가 적용해야 하는지가 흐려진다.

### J-2a 시스템 동작은 시스템이 주어
❌ 매일 02:00에 독자가 정산 배치가 실행되는 것을 확인할 수 있습니다.
✅ 정산 배치는 매일 02:00에 전날 주문을 집계합니다.
왜: 시스템이 스스로 하는 일을 독자 주체로 바꾸면 오히려 어색하다.

## L 포매팅

### L-1a 순서가 있으면 번호 목록
```markdown
❌
- 점검 공지를 올린다
- 배포한다
- 오류율을 확인한다

✅
1. 점검 공지를 올립니다.
2. 배포합니다.
3. 오류율을 확인합니다.
```
왜: 글머리 목록은 순서를 바꿔도 된다는 신호다.

### L-2a 한 단계에 한 동작, 분기는 나눈다
```markdown
❌
2. 운영 환경이면 승인을 받고 배포하고, 스테이징이면 바로 배포한 뒤 슬랙에 공유합니다.

✅
2. 배포할 환경을 확인합니다.
   - 운영: 3단계로 갑니다.
   - 스테이징: 4단계로 갑니다.
3. 운영 배포 승인을 받습니다.
4. 배포합니다.
5. `#deploy` 채널에 배포 결과를 공유합니다.
```
왜: 조건과 동작이 한 줄에 섞이면 독자가 자기 경우에 해당하는 동작을 놓친다.

### L-3a 목록 중첩은 한 단계까지
❌ 장애 등급 아래 영향 범위, 그 아래 서비스별, 그 아래 지표별로 네 단계 중첩 목록을 만든다.
✅ 장애 등급별 기준을 표 하나로 만든다(열: 등급, 영향 범위, 판단 지표, 대응 시간).
왜: 깊은 중첩은 구조를 감추고, 같은 기준의 비교는 표가 빠르다.

### L-4a 매개변수는 표로
```markdown
❌
`orderId`는 문자열이고 필수입니다. `reason`은 문자열이며 선택이고 기본값은 "고객 요청"입니다.

✅
| 이름 | 타입 | 필수 | 기본값 | 설명 |
|---|---|---|---|---|
| `orderId` | string | 예 | — | 취소할 주문 ID |
| `reason` | string | 아니요 | `고객 요청` | 취소 사유 |
```
왜: 같은 속성을 가진 항목은 표에서 나란히 비교된다.

### L-5a 코드 블록에 언어를 붙인다
````markdown
❌
```
SELECT count(*) FROM settlement WHERE status = 'FAILED';
```

✅
실패한 정산 건수를 셉니다.
```sql
SELECT count(*) FROM settlement WHERE status = 'FAILED';
```
````
왜: 언어가 없으면 강조 표시가 사라지고, 앞 문장이 없으면 무엇을 위한 쿼리인지 모른다.

### L-6a 경고는 위험한 곳에만
❌ 문서 곳곳에 "참고", "팁", "주의" 상자가 일곱 개 있고, 그중 하나가 데이터 삭제 경고다.
✅ 데이터 삭제 단계 앞에만 경고 상자를 두고, 나머지는 본문 문장으로 쓴다.
왜: 상자가 많으면 진짜 경고가 묻힌다.

### L-7a 제목 수준을 건너뛰지 않는다
❌ `## 배포` 바로 아래에 `#### 롤백`
✅ `## 배포` 아래에 `### 롤백`
왜: 제목 수준이 목차를 만든다. 건너뛰면 목차가 깨진다.

### L-8a 시각 자료가 많으면 번호를 붙인다
❌ 그림 여섯 개를 넣고 본문에서 "위 그림처럼", "아래 그림에서"로 가리킨다.
✅ "그림 3. 정산 배치 재시도 흐름"처럼 번호와 캡션을 달고, 본문에서는 "그림 3"으로 가리킨다.
왜: 그림이 많으면 "위 그림"이 어느 것인지 알 수 없다.

### L-9a 긴 로그는 접어 둔다
```markdown
❌
(본문 한가운데에 120줄짜리 스택 트레이스)

✅
오류의 첫 줄은 다음과 같습니다.
`HikariPool-1 - Connection is not available, request timed out after 30000ms.`

<details>
<summary>전체 스택 트레이스</summary>
(120줄)
</details>
```
왜: 판단에 필요한 줄만 보이고 나머지는 필요한 사람이 펼친다.

## M 시각화

### M-1a 흐름은 그림으로
❌ 주문 API가 결제 API를 호출하고, 결제 API는 결제사에 승인을 요청한 뒤 결과를 주문 API에 돌려주며, 주문 API는 승인 결과를 정산 큐에 넣고, 정산 배치는 그 큐를 읽어...(문단 하나로 이어짐)
✅ 한 문장 안내 뒤에 `sequenceDiagram`으로 주문 API, 결제 API, 결제사, 정산 큐, 정산 배치의 호출 순서를 그리고, 그림 뒤에 "승인 결과는 비동기로 정산에 전달된다"는 핵심을 한 문장으로 쓴다.
왜: 다섯 참여자의 순서는 글로 읽으면 머릿속에서 다시 그려야 한다.

### M-2a 연결이 없으면 표로
❌ "운영", "스테이징", "개발" 상자 세 개를 나란히 그리고 상자 안에 각 환경의 DB 크기와 레플리카 수를 적는다.
✅ 환경별 비교 표(열: 환경, DB 크기, 레플리카 수, 배포 승인)를 쓴다.
왜: 상자끼리 연결이 없으면 다이어그램은 표보다 읽기 어렵다.

### M-3a 그림 앞뒤 문장
```markdown
❌
(제목 바로 아래에 다이어그램만 있고, 이어서 다이어그램의 모든 화살표를 문장으로 다시 설명)

✅
다음 그림은 정산 실패 시 재시도 흐름을 보여 줍니다.
(다이어그램)
세 번 실패한 정산은 자동으로 재시도하지 않고 DLQ로 갑니다. 이때부터는 운영자가 직접 재처리합니다.
```
왜: 앞 문장은 무엇을 볼지, 뒤 문장은 무엇을 가져갈지 알려 준다. 화살표를 글로 반복할 필요는 없다.

### M-4a 노드가 많으면 나눈다
❌ 서비스 25개와 큐 8개를 다이어그램 하나에 모두 그린다.
✅ 도메인 단위 개요도(노드 7개) 하나를 본문에 두고, 도메인별 세부도는 각 절에 둔다. 전체 그림이 필요하면 diagram-design으로 그려 SVG로 넣는다.
왜: 노드가 많으면 주된 흐름이 보이지 않는다.

### M-5a 캡처보다 텍스트
❌ 터미널 출력 화면을 캡처해 이미지로 넣는다.
✅ 출력을 `text` 코드 블록으로 붙이고, 확인할 줄을 본문에서 짚는다.
왜: 텍스트는 검색되고 복사되며, 화면 크기와 테마의 영향을 받지 않는다.

## N 코드 예제


✅ 성공 응답 다음에 대표 오류 두 가지를 보인다: 이미 처리 중인 날짜(`409 SETTLEMENT_IN_PROGRESS`), 정산 대상이 없는 날짜(`404 SETTLEMENT_NOT_FOUND`)와 각각의 대처.

## S 왜·결정 맥락

### S-1a 무엇만이 아니라 왜를
❌ 정산 배치의 chunk 크기를 500으로 설정했습니다.
✅ 정산 배치의 chunk 크기를 500으로 설정했습니다. 1,000에서는 결제사 API의 요청 크기 제한(1MB)을 넘는 경우가 있었기 때문입니다.
왜: 이유가 없으면 다음 사람이 성능을 위해 값을 다시 올리고 같은 문제를 만난다.

### S-2a 대안을 같은 기준으로 비교
```markdown
❌
Kafka, SQS, Redis Stream을 검토했고 Kafka가 가장 좋아서 선택했습니다.

✅
| 기준 | Kafka | SQS | Redis Stream |
|---|---|---|---|
| 순서 보장 | 파티션 단위 | FIFO 큐에서만 | 스트림 단위 |
| 재처리(되감기) | 가능 | 불가 | 가능 |
| 운영 부담 | 사내 클러스터 있음 | 없음 | 클러스터 신규 필요 |

재처리가 필수이고 사내 클러스터를 그대로 쓸 수 있어 Kafka를 선택했습니다. SQS는 되감기가 안 돼 탈락했습니다.
```
왜: 기준이 보여야 독자가 결정에 동의하거나, 조건이 바뀌었을 때 다시 판단할 수 있다.

### S-3a 원리보다 풀려는 문제를 먼저
❌ 아웃박스 패턴은 트랜잭션 안에서 이벤트를 테이블에 저장하고 별도 프로세스가 발행하는 방식입니다. (이어서 구현 설명)
✅ 주문 저장은 성공했는데 이벤트 발행이 실패하면 정산에서 주문이 사라집니다. 아웃박스 패턴은 이 문제를 막으려고, 주문과 이벤트를 같은 트랜잭션에서 저장한 뒤 별도 프로세스가 발행합니다.
왜: 문제를 먼저 알아야 원리가 왜 그렇게 생겼는지 납득된다.
