# 기술 문서 작성 (Tech Writer)

독자가 문서를 읽고 목표를 이루도록 기술 문서를 구성하고 쓴다. 기준은 하나다. **이 독자가 이 문서로 무엇을 하려는가.** 독자는 config에서 가져오고, 유형과 구조는 독자의 목표로 정하고, 문장·포매팅·시각화는 그 구조를 독자에게 빨리 전달하는 수단으로 쓴다.

스킬 디렉터리: `${CLAUDE_SKILL_DIR}`

위 값은 스킬을 불러올 때 이 `SKILL.md`가 있는 폴더의 절대 경로로 바뀐다. 아래에 나오는 references 폴더와 scripts 폴더의 경로와 reference 파일에 나오는 "스킬 디렉터리"는 모두 이 폴더 기준이다. 명령은 사용자의 작업 디렉터리에서 실행되므로 스크립트는 반드시 이 절대 경로를 붙여 실행한다. 값이 바뀌지 않고 `${CLAUDE_SKILL_DIR}` 글자 그대로 보이면(변수를 지원하지 않는 버전), 스킬을 불러올 때 표시된 "Base directory"를 대신 쓴다.

## 준비물

| 도구 | 쓰는 곳 | 없을 때 |
|---|---|---|
| `uv` | config 병합(`scripts/load_config.py`), 문서 검사(`scripts/lint_doc.py`, `scripts/redundancy.py`, `scripts/slop_check.py`). PyYAML은 uv가 자동 설치 | 사용자에게 설치를 안내하고, config는 직접 읽어 합친다 |
| Node.js(`npx`) 또는 `mmdc` | mermaid 렌더링(`scripts/render-mermaid.sh`). `mmdc`가 없으면 첫 실행에 npx가 패키지를 내려받느라 1~2분 걸린다 | 다이어그램을 코드 블록으로 두고 보고에 렌더링 미확인을 적는다 |
| korean-proofreader, eli5, diagram-design 스킬 | 문장 교정, 개념 설명, 복잡한 다이어그램 | "연동 스킬" 절의 대체 방법 |
| Atlassian MCP(Model Context Protocol) 서버의 `createConfluencePage`·`updateConfluencePage` 도구(환경에 따라 `mcp__<서버 이름>__createConfluencePage` 형태로 노출) | Confluence 게시(사용자가 요청할 때만) | Markdown 파일로 넘긴다 |

## 모드 판별

| 모드 | 요청 예 | 시작 |
|---|---|---|
| 작성 | "README 만들어줘", "이 장애 메모로 포스트모템 써줘", "이 코드 설계 문서로 정리해줘" | 0단계부터 전체 |
| 개선 | 기존 문서를 주며 "개선해줘", "구조 봐줘", "읽기 어렵대" | 0단계 → "개선 모드" 절 |
| 설정 | "기본 독자를 PM으로", "독자 프로필 추가", "용어집에 추가" | "설정 모드" 절 |
| 보정 | "slop 기준 다시 재 줘", "이 문서들 slop 표본에 넣어", "이 경고는 오탐이야" | "보정 모드" 절 |

문장 몇 개만 다듬어 달라는 요청이면 이 스킬 대신 korean-proofreader를 쓴다.

## 0단계: config 불러오기

```bash
uv run ${CLAUDE_SKILL_DIR}/scripts/load_config.py
```

| 종료 코드 | 뜻 | 할 일 |
|---|---|---|
| 0 | 정상 | 출력 JSON의 `config`를 쓴다. `warnings`가 있으면 한 줄로 알린다 |
| 3 | config 없음, 또는 기본 독자(`audiences.default`) 없음 | `references/audience.md`의 "config가 없을 때" 절에 따라 인터뷰한다. 유저 config 파일이 이미 있으면 그 파일에 `audiences`만 추가하고 다시 실행한다 |
| 2 | config 오류 | `errors`의 파일·줄·메시지를 보여 주고 고칠 내용을 제안한다. 사용자가 동의하면 고치고 다시 실행한다 |

uv가 없으면 사용자에게 설치를 안내하고, 그동안은 config 파일을 직접 읽어 같은 규칙(프로젝트 파일이 유저 파일을 키 단위로 덮어씀)으로 합친다.

## 작성 파이프라인

각 단계는 표시된 파일만 읽는다. 파일 전체를 미리 읽지 않는다.

### 1. 독자와 목적 정하기

읽을 파일: `references/audience.md`

- 요청에 독자가 있으면 그 독자, 없으면 config `audiences.default`.
- 재료와 독자가 명백히 어긋날 때만 한 번 확인한다(기준은 audience.md).
- 독자는 정해졌는데 목적이 모호하면 1~3개만 묻는다. 재료에서 추론할 수 있으면 묻지 않는다.

### 2. 유형 정하기

읽을 파일: `references/doc-types.md`

- 결정 트리로 유형을 고른다.
- 해당 템플릿 `references/templates/<유형>.md`과 본보기 `references/exemplars/<유형>.md` **한 편만** 읽는다. 본보기 한 편이 1,500~3,000 토큰이라, 여러 편을 읽으면 사용자 재료가 들어갈 자리가 줄어든다. 본보기의 소재(정산 배치)는 따라 하지 않고 구조와 밀도만 참고한다. 비개발 독자용 설명이면 `references/exemplars/non-technical.md`를 읽는다.

### 3. 목차 만들기

읽을 파일: `references/structure.md`

- 템플릿 섹션을 독자와 재료에 맞게 고친 목차를 만든다.
- 근거가 충분하면(독자 config와 재료가 맞고, 유형이 분명함) 목차를 보여 주고 바로 진행한다.
- 근거가 약하면(유형이 둘로 갈림, 재료가 부족함, 독자를 추정했음) 목차를 보여 주고 승인을 받는다.

### 4. 초안 쓰기

읽을 파일: `references/structure.md`, `references/style.md`

- 개요(E-1)부터 쓴다. 개요가 써지지 않으면 목적이 아직 불분명한 것이다.
- 재료에서 확인한 사실만 쓴다. 확인 못 한 명령·경로·수치는 `TODO(확인 필요: <무엇을>)`로 둔다(P-1).
- 외부 참조는 실제 주소를 확인해 링크로 달고(E-10), 코드는 이해에 필요한 만큼만 본문에 둔다(E-11). 근거는 끝의 "참고" 절에 저장소·PR·티켓 링크로 모은다.
- 원칙 적용이 막히면 `references/examples.md`에서 그 원칙 ID만 찾아 읽는다.
- 독자 수준과 재료 난이도의 차이가 크면 개념 설명 단락에서 **eli5**를 부른다(조건과 넘길 값은 audience.md "eli5 호출 조건").

### 5. 시각화

읽을 파일: `references/visualization.md`

- 구조·흐름·관계·상태를 글로만 설명한 곳을 찾아 다이어그램으로 바꾼다. 비교·속성은 표로 쓴다.
- 도구는 config `output.format`과 복잡도로 고른다(mermaid / diagram-design).
- mermaid는 `scripts/render-mermaid.sh`로 렌더링해 문법을 확인한다.
- 출력이 confluence나 html이면 다이어그램을 이미지(SVG)로 만들어 `output.assets_dir`에 두고 본문에서 참조한다. 이 형식들은 mermaid 코드 블록을 그림으로 보여 주지 않기 때문이다. 예외: config `confluence_mermaid_macro: true`면 Confluence에는 mermaid 코드를 매크로용으로 넣는다(렌더링 확인은 그대로 한다).
- 런북·설명·설계 문서에 분기 셋 이상의 판단 흐름이나 컴포넌트 관계가 있는데 다이어그램이 0개면, 빼먹은 것이 아닌지 다시 본다.

### 6. 포매팅

읽을 파일: `references/formatting.md`

- 목록·표·코드 블록·경고를 원칙대로 다듬고, 출력 형식(Markdown, Confluence, HTML)에 맞춘다.

### 7. 반복 정리와 문장 교정 — korean-proofreader

먼저 `uv run ${CLAUDE_SKILL_DIR}/scripts/redundancy.py <문서>`로 반복 노출을 정리한다(E-12). 교정 전에 하는 이유는 지울 문장을 교정하는 일을 없애기 위해서다. 교정은 반복 탐지를 가리지 않으므로(형태소 기준으로 비교한다) 8단계에서 다시 재도 같은 결과가 나온다.

그다음 style.md "korean-proofreader에 넘길 때"의 제약을 그대로 넘기고 문단·문장 층위만 맡긴다. 구조에 관한 의견은 적용하지 않고 보고에만 남긴다.

Skill 도구로 korean-proofreader를 부르면 교정 지침이 로드될 뿐 문서가 고쳐지지는 않는다. 로드된 지침의 문단 점검과 문장 점검을 이 문서에 직접 적용한 뒤 다음 단계로 간다. 지침을 불러오기만 하고 넘어가지 않는다. 고친 문장 수(고칠 곳이 없었으면 "수정 없음")를 9단계 보고의 "교정" 줄에 적는다.

### 8. 검증

읽을 파일: `references/review-checklist.md`

네 가지를 모두, 순서대로 한다. 초안을 쓴 직후의 작성자는 자기 글을 의도대로 읽기 때문에, 검증을 건너뛴 문서는 독자가 막히는 곳을 그대로 안고 나간다. 시간이 부족해도 생략하지 말고 범위를 줄인다(예: 되말하기를 핵심 절만).

1. 기계 검사: `uv run ${CLAUDE_SKILL_DIR}/scripts/lint_doc.py <문서>`(코드 조사 보고는 `--type investigation`을 붙인다) — error는 반드시 고친다. warn 가운데 `unlinked-ref`(링크 없는 참조 번호), `code-location`(경로·라인 근거), `file-link`(소스 파일 링크)도 모두 고친다. AI slop 경고는 5번 점검에서 다룬다. 개선 모드의 원본 파일에서 답을 기다리는 결정에 걸린 것만 남기고, 보고에 그 이유를 적는다.
   이어서 `uv run ${CLAUDE_SKILL_DIR}/scripts/redundancy.py <문서>`로 반복 노출을 잰다(E-12). 강한 반복(repeated-claim), 퍼진 식별자(identifier-spread), 코드·그림 옮김(code-transcribed, diagram-transcribed)은 목록의 정의 자리와 할 일대로 고치고 다시 잰다. 비슷한 주장(similar-claim)은 읽어 보고 반복이면 고친다. 남긴 항목은 보고에 이유를 적는다.
2. 사실 검증: 명령·경로·API·설정 키·수치를 재료와 대조한다. 값의 의미는 근거 수준(P-4)까지 확인하고, 수준이 바뀐 결론은 보고에 남긴다.
3. 되말하기: 서브에이전트에게 독자 역할을 주고 3줄 요약과 막힌 곳을 받아 고친다(프롬프트는 O-3). 서브에이전트를 띄울 수 없는 환경이면(이 스킬 자체가 서브에이전트 안에서 실행 중일 때 등) O-3의 "직접 수행" 방법으로 대신한다.
4. 체크리스트: 유형별(O-4)과 공통(O-5).
5. AI slop 점검: `references/slop-rubric.md`를 읽고 아래 순서로 한다. 지표만 맞추고 내용은 그대로인 수정을 막으려고, 판정은 스크립트와 되말하기 서브에이전트가 하고 작성자는 고치기만 한다.
   1. 고치기 전 판을 남긴다. 작성 모드는 7단계를 마친 초안을, 개선 모드는 원본을 scratchpad에 복사한다. 문서 식별자를 정한다(Confluence는 `confluence:<페이지 ID>`, 파일은 `file:<저장소 기준 경로>`). `uv run ${CLAUDE_SKILL_DIR}/scripts/slop_db.py history --source <문서>`로 이 문서에 남은 사람 판정을 읽는다. 전에 사람이 오탐으로 판정한 곳은 다시 걸려도 고치지 않는다.
   2. `uv run ${CLAUDE_SKILL_DIR}/scripts/slop_check.py <문서> --json`을 돌린다. 게이트 항목은 모두 고친다. 지시 항목은 가리킨 곳을 읽고 고치거나 남길 이유를 정한다. 무엇이 게이트인지는 `scripts/slop_rules.json`이 정하므로 이 파일에 목록을 옮겨 적지 않는다.
   3. 판단 항목은 3번 되말하기에서 함께 받는다(O-3의 5번 질문). 판단을 받으려고 서브에이전트를 따로 띄우지 않는다. O-3이 두 번째 되말하기를 요구하면 그때는 5번 질문 가운데 "고치면서 바뀐 뜻"만, 고친 문장 목록과 함께 묻는다.
   4. 고친 뒤 다시 잰다. 고치는 일은 두 번까지만 한다. 두 번째에도 게이트 항목이 남으면 더 고치지 않고 "미통과"로 보고한다.
   5. 고친 것, 남긴 것과 이유, 결정 대기, 판단 결과를 판단 목록 JSON(형식은 slop-rubric.md "보고 형식")으로 적고 `uv run ${CLAUDE_SKILL_DIR}/scripts/slop_check.py <문서> --baseline <고치기 전> --judgments <판단.json> --db <문서 식별자>`의 출력 블록을 9단계 보고에 넣는다.
   6. 최초 판정을 판정 저장소에 남긴다. 같은 인자에 `--json`을 붙인 출력을 파일로 받아 `uv run ${CLAUDE_SKILL_DIR}/scripts/slop_db.py record --source <문서> --check <그 파일> --judgments <판단.json> --doc-file <문서>`를 돌린다. 사람이 나중에 이 판정에 동의하거나 오탐이라고 하면 그 기록이 보정과 다음 실행에 쓰인다.
   - 개선 모드에서 구조가 바뀌는 수정(굵은 결정 문장 여럿을 표로 모으기, 되풀이한 절 합치기, 이미 목록·표에 있는 내용을 그림으로 한 번 더 보이기)은 고치지 않고 "결정 대기"로 둔다.

### 9. 출력과 보고

- 저장 위치: 사용자가 정한 곳. 없으면 Markdown과 Confluence 원고는 저장소의 `docs/`(없으면 만든다), HTML은 현재 디렉터리에 둔다. Confluence는 게시하지 않고 원고만 만든 뒤 게시 여부를 묻는다.
- 다이어그램 이미지와 diagram-design HTML은 config `output.assets_dir`(저장소 루트 기준)에 두고, 문서에서는 **문서 파일 위치 기준 상대 경로**로 링크한다. 예) 문서가 `docs/runbook.md`이고 assets_dir가 `docs/assets`면 `assets/runbook-1.svg`.
- 문서를 넘긴 뒤 아래 형식으로 보고한다. 보고는 문서 본문에 넣지 않는다.

```text
독자: <프로필 이름>(<level>) — <config 출처 또는 요청에서 정함>
유형: <유형> / 템플릿: <파일> / 본보기: <파일>
기계 검사: error 0, warn <n> (<남긴 warn과 이유>)
사실 검증: 확인 <n>개, 수정 <n>개, 확인 필요 <n>개 → <목록> / 근거 수준: <결론>: <선언 → 구현 → 관측 중 거친 수준>
외부 참조: <n>개, 링크 <n>개, 링크 확인 필요 <n>개
중복 노출: 식별자 최대 층 <전>→<후>, 강한 반복 <전>→<후>, 코드·그림 옮김 <전>→<후> (새 문서는 <후>만)
되말하기: <서브에이전트 | 직접 수행>, 3줄 요약 의도와 <일치 | 불일치>, 막힌 곳 <n> → 수정 <n>
다이어그램: <n>개 (<도구>, 렌더링 <성공 | 실패>)
교정: korean-proofreader <고친 문장 n개 | 수정 없음 | 생략(이유)>
제안(적용 안 함): <구조 제안 등>
```

이어서 8단계 5번에서 만든 "AI slop 점검" 블록을 그대로 붙인다. 형식과 쓰는 법은 slop-rubric.md "보고 형식"이 정한다.

## 연동 스킬

| 스킬 | 언제 | 없으면 |
|---|---|---|
| eli5 | 비개발·초급 독자에게 낯선 핵심 개념이 3개 이상일 때, 개념 설명 단락 | audience.md C-4 전략으로 직접 쓴다 |
| diagram-design | 다이어그램이 복잡할 때(노드 12개 초과, 경계, 변경 전후 비교, 의사결정자용 완성도), 또는 config `diagrams: diagram-design`. SVG/PNG로 내보내 문서에 넣는다 | mermaid로 개요도와 세부도를 나눈다 |
| korean-proofreader | 7단계, 항상 | style.md 규칙만 적용하고 보고에 "문장 교정 생략" |

연동 스킬의 결과는 그대로 붙이지 않는다. 문서의 어조(config `tone`), 용어집, 구조에 맞춰 다시 쓴다.

## 개선 모드

기존 문서를 받으면 고치기 전에 문서 전체와 절 하나하나를 모두 읽고 진단한다. 앞쪽 몇 절이나 목차만 보고 판단하면, 순서를 바꾸는 정도의 소극적인 제안에 그치거나 뒤쪽 절의 문제를 놓친다.

1. 0단계와 1단계로 독자를 정한다. 문서에 독자가 드러나 있으면 그것과 config를 비교한다.
2. 전체를 진단한다. 이 문서가 독자의 질문에 답하는 순서인지, 결론과 세부가 같은 층에 섞여 있지 않은지, 한 문서에 주제가 둘 이상인지를 본다(E-2, E-3, E-8). 외부 참조와 코드 노출도 여기서 본다(E-10, E-11). 진단 전에 원본에 `redundancy.py`를 돌려 지표를 남긴다. 고칠 곳 목록의 줄 번호는 절별 진단표의 "문제" 칸에 그대로 옮기고, 미리보기본에 같은 스크립트를 다시 돌려 지표가 줄었는지 확인한다.
3. 절별 진단표를 만든다. H2 절마다, 길면 H3 절마다 한 행이다.

   ```markdown
   | 절 | 담고 있는 것 | 독자에게 필요한가 | 문제 | 제안 |
   |---|---|---|---|---|
   | 3. 구성 요소 | 클래스마다 코드 발췌와 설정 이유 | 이유는 필요, 경로·라인 근거는 불필요 | 결론과 세부가 한 층에 섞임 | 결정 요약 표는 본문, 코드는 부록 |
   ```

4. 재구성 수준을 정한다. 진단에서 드러난 문제를 해결하는 가장 작은 수준을 고른다. 결론과 세부가 같은 층에 섞여 있으면 순서를 바꾸는 것만으로는 풀리지 않는다.

   | 수준 | 고르는 신호 |
   |---|---|
   | 부분 손질 | 구조는 맞고, 문장·포매팅·시각화만 문제다 |
   | 절 재배치 | 절은 맞는데 순서가 독자의 질문 순서와 다르다 |
   | 층 나누기 | 결론과 세부가 한 층에 늘어서 있다. 본문(결론·구조)과 부록(세부)으로 나누거나 문서를 나눈다 |
   | 다시 쓰기 | 유형이나 독자가 원본과 다르다 |

5. 결정이 걸린 일은 사용자에게 묻는다. 대상은 재구성 수준, 어조 변경, 독자 전환, 내용 삭제, 원본이 따르던 관례(근거 표기, 번호 참조 등)를 버리는 일이다. 작성자의 의도가 걸려 있어, 묻지 않고 바꾸면 의도를 망치고 묻지 않고 그대로 두면 문제가 남는다.
   - 질문에는 정할 것, 선택지마다 문서가 어떻게 달라지는지, 추천안과 이유를 쓴다. 한 번에 핵심 결정 하나씩 묻는다.
   - 답을 받기 전에는 그 결정이 걸린 부분을 원본에 적용하지 않는다. 그렇다고 "유지"로 처리하고 넘어가지도 않는다. 결정을 기다리는 항목으로 보고에 남긴다.
   - 사용자에게 물을 수 없는 실행(다른 에이전트가 맡긴 작업 등)이면, 질문을 보고의 "결정 대기" 목록에 적고 미리보기본에는 추천안을 적용해 둔다.
6. 진단표, 제안표, 질문과 함께 제안을 모두 적용한 미리보기본을 별도 파일(`<원래 이름>.proposed.md`)로 만든다. 표만으로는 바뀐 모습을 판단하기 어렵기 때문이다. 원본 파일에는 결정이 필요 없는 수정(사실 정정, 포매팅, 문장 교정, 시각화)만 반영한다.
   - 원본의 어조(합니다체, 서술체 등)를 config와 다르게 바꾸는 것은 결정이 걸린 일이라 5번으로 묻는다.
   - "원문 어조 유지"는 문장 교정을 생략할 이유가 되지 않는다. 어조는 지키고, 띄어쓰기·한 문장 안의 한글·영문·코드 혼용·군더더기는 고친다.
   - 원본에서 독자 행동에 필요 없는 수치(예: 전체 상품 수)에는 TODO를 달지 않는다.
7. 8단계 검증을 하고 보고한다. 보고에는 적용하지 않은 제안, 답을 기다리는 결정, 하지 않은 일과 그 이유를 모두 남긴다. 한 일만 보고하면 사용자는 나머지가 됐다고 믿는다.

## 설정 모드

1. 유저 파일(`~/.claude/tech-writing/config.yaml`, 모든 프로젝트)과 프로젝트 파일(`<저장소>/.tech-writing.yaml`, 이 저장소만) 중 어디를 고칠지 묻는다. 요청에 "이 프로젝트에서만"처럼 드러나 있으면 묻지 않는다.
2. 필드 의미는 `config/default.yaml`의 주석과 audience.md "config 해석" 절을 따른다.
3. 고친 뒤 `load_config.py`를 실행해 종료 코드 0을 확인하고, 바뀐 값을 한 줄로 알린다.

## 보정 모드

AI slop 기준을 다시 잰다. 기준은 문서를 볼수록 바뀌므로, 바뀌는 길을 정해 둔다. 기준을 바꾸자는 제안만 만들고, 사용자가 승인해야 `scripts/slop_rules.json`과 루브릭에 반영한다.

판정 저장소는 로컬 DuckDB 파일(`~/.claude/tech-writing/calibration/slop.duckdb`)이고, 읽고 쓰는 일은 모두 `scripts/slop_db.py` 명령으로 한다. 회사 문서의 인용이 들어가므로 스킬 저장소에 넣지 않는다. 담는 것은 대상 문서, 최초 판정(8단계 5번이 남긴다), 사용자 판정, 기준 변경이다.

1. 사용자가 점검 결과에 판정을 내리면 그때마다 남긴다.
   - "이건 오탐이야", "이건 맞아": `slop_db.py findings --source <문서>`로 찾은 곳 ID를 확인하고 `slop_db.py judge --finding <ID> --verdict <오탐|동의> --note <이유>`
   - "이건 slop인데 안 잡혔어": `slop_db.py miss --source <문서> --item <루브릭 항목 ID> --quote <인용> --section <절>`
   - "이 문서들 표본에 넣어": `slop_db.py doc-add --source <문서> --label <human|approved|slop> --reason <이유>`. 파일 표본은 사본을 저장소 옆 `files/`에 둔다
2. `uv run ${CLAUDE_SKILL_DIR}/scripts/calibrate.py`를 돌린다. Confluence 표본은 confluence-cli로 storage 형식을 받아 Markdown으로 바꾸고 `cache/`에 둔다(`storage2md.py`). 티켓 링크 주소는 환경 변수 `TECH_WRITER_JIRA_BASE`(예: `https://<사이트>/browse/`)로 준다. 주지 않아도 링크 모양은 남아 링크된 티켓 키를 링크 없는 번호로 세지 않는다. 출력은 slop-rubric.md "보정 모드 보고 형식"의 보고, 근거 파일 `calibration-evidence.md`, 제안 파일 `slop_rules.proposed.json`이다.
3. 사용자가 확인할 수 있게 두 가지를 함께 보여 준다. 보고(수치)와, 바꾸자는 항목의 근거 파일 절(기준 문서에서 걸린 줄, AI 문서에서 걸린 줄)이다. 숫자만으로는 정말 그런지 판단할 수 없기 때문이다. 항목마다 승인을 받는다.
4. 승인한 항목만 `uv run ${CLAUDE_SKILL_DIR}/scripts/calibrate.py --apply <항목 ID,…> --by <승인한 사람>`으로 옮기고, 출력되는 "반영한 변경"(전 → 후)을 그대로 보여 준다. 변경은 판정 저장소에도 남는다(`slop_db.py changes`). 승인하지 않은 항목은 바뀌지 않는다.
5. 상태가 바뀌었으면 slop-rubric.md의 판을 올리고, 항목 표와 개정 이력에 무엇을 왜 바꿨는지 적어 그 변경도 보여 준다. 오탐·놓침 사례는 익명화해 `tests/`에 더한다. 근거 파일과 판정 저장소의 문장은 저장소에 옮기지 않는다.

스킬 자체를 고칠 때(skill-creator 평가 등)도 이 저장소를 쓴다. `slop_db.py stats`로 사람 판정이 쌓인 항목을, `slop_db.py history --source <문서>`로 판정이 붙은 문서를 골라 평가 표본으로 삼는다. 사람이 동의한 곳은 잡고 오탐이라고 한 곳은 잡지 않는지가 평가 기준이다.

## 하지 않는 것

- 재료에 없는 명령어, API, 설정 키, 수치를 지어내지 않는다. 독자는 문서를 그대로 실행하므로, 그럴듯한 명령 하나가 운영 사고가 된다.
- 본보기의 소재(정산 배치, 사내 도구 이름)를 사용자 문서에 옮기지 않는다. 본보기는 구조와 밀도의 견본이지 내용의 출처가 아니다.
- 다이어그램에 있는 내용을 글로 다시 늘어놓지 않는다. 같은 정보를 두 번 읽히면 독자는 무엇이 핵심인지 놓친다.
- 한 문서 안에서 어조를 섞지 않는다. 어조가 바뀌면 여러 사람이 이어 붙인 문서처럼 보여 신뢰가 떨어진다.
- 개선 모드에서 동의 없이 구조를 바꾸지 않고, 묻지 않은 채 그대로 두지도 않는다. 구조에는 작성자의 의도가 걸려 있어, 결정이 필요하면 선택지와 추천안을 붙여 묻는다.
- Confluence 게시처럼 바깥에 공개하는 일은 사용자가 요청할 때만, 본문을 보여 준 뒤에 한다. 게시한 문서는 회수해도 이미 읽혔을 수 있다.
